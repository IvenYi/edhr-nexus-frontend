# 候选流程版本读取：实际规模、索引与下一批授权

入口是记录变更页选择“表单变更／表单作废”后加载审批流程版本，对应 `GET /api/v1/workflow/record-control/candidates?businessType=...`。这是流程模板目录规模，不是员工数或一份DHR的表单数。现有 `RecordControlWorkflowService.listPublishedCandidates` 先查询匹配定义，再逐定义查询当前版本；每个版本还读取包含nodes_json/edges_json的完整实体，最后只映射7个选项字段。

## 实际结果

每类有M个应返回版本，另有2个匹配定义分别无current或current为DRAFT且有历史PUBLISHED；草稿定义、另一流程类型/业务类型不进入匹配。D=M+2，因此当前SQL=1+D=M+3，生产一般公式是1+D，不是固定额外3。0、1、10、100、1000每类规模，CHANGE/OBSOLETE各两次独立只读事务，共20观察。

| 返回M | 匹配定义D | 实际SELECT/次 | 第二次调用服务耗时 CHANGE／OBSOLETE |
| ---: | ---: | ---: | ---: |
| 0 | 2 | 3 | 2.16／2.00 ms |
| 1 | 3 | 4 | 2.24／1.79 ms |
| 10 | 12 | 13 | 6.05／6.47 ms |
| 100 | 102 | 103 | 55.93／60.76 ms |
| 1000 | 1002 | 1003 | 463.87／362.46 ms |

1000个全部返回，认证MockMvc响应与服务结果逐字段相同，末项可达；100没有成为数量上限。1000档调用线程累计分配约40.4／40.0 MiB；不是进程峰值。实际测量标签下4504条SELECT、0写入，计划均来自原服务实际auto_explain，不是手写EXPLAIN。HTTP与序列化/fixture工作不计入服务计时分配。

本机热缓存、JIT和计划采集开销影响结果，不是生产页面延迟、SLA、吞吐或并发认证。合成目录的nodes/edges为小数组；确认了查询会取JSON列，但没有量化宽JSON开销。目录元数据不是1000个已真实发布、签署执行的业务流程。

## 索引及兼容边界

1000档每条版本读取已用现有 `uk_wf_def_version(definition_id,version_number)` 左前缀定位再过滤is_current；小目录选择顺扫。外层定义查询在本样本顺扫，不因此自动加索引。新增索引无法消除逐条往返；先改变读取形状，再看实际prepared计划、分布、写入/空间成本是否仍需索引，不预设新索引。

当前Optional先取所有is_current，再判断唯一结果的PUBLISHED状态。本批只证明两个PUBLISHED current时抛现有IncorrectResultSize且10表不变，不能推导全域start的政策或所有混合状态坏数据行为。批读不能只先过滤PUBLISHED便默默隐藏多个current，也不能按最新版本或第一条任取；优化须保留当前列表边界和失败语义，并补相应混合状态测试。显式start对指定版本的检查另归原执行端口，不混为一套新政策。
