# 汇总附件查询量化与方案

在自有PostgreSQL16.15中，使用真实公开DhrSummaryService.submit和真实外层事务、实际Jdbc/父锁/附件文件运行至既有人工三项确认guard。detail、impact、forms、workflow等不相关依赖为替身，七表来自canonical DDL，夹具仅加主键；不是完整业务数据库迁移安装或成功冻结提交。

| 汇总附件数N | 实际显式Jdbc查询数 |
| ---: | ---: |
| 0 | 5 |
| 1 | 7 |
| 10 | 25 |
| 100 | 205 |
| 300 | 605 |

观察范围内为5+2N。5次是DHR关联生产对象读取、生产对象锁、DHR锁、草稿锁、活动附件快照。每附件file另读DHR及原件路径/SHA两次。当前细节读取由替身提供；真实生产还会有detail/影响/来源检查及guard之后的查询，所以不能称完整请求总数。SQL是成功执行的JdbcTemplate查询，不含驱动建连。原始SQL列表保留，查询次数不设永久断言去锁死当前低效实现。

样本为极小真实PNG、本机暖资源；主侧诊断时间约21–408ms，首次初始化/调度也有影响。它只说明重复往返增长，不能推出300个真实附件的完整提交时延、生产SLA或大文件成本。大文件完整SHA、其他源记录和并发锁持有另计。

并发测试在submit已获取生产对象/DHR/草稿锁、读完当前附件快照后暂停，真实attachments.unlink在另一个连接的父DHR FOR UPDATE上进入pg_stat_activity Lock等待；等待时active仍true，释放后unlink提交且历史file仍可读取。只证明这条合法服务写链服从父锁，不覆盖直接SQL、全体入口或全部并发时序。

建议分两批讨论：

1. 下载只复用最后一次已校验的原件元数据中的文件名，预计当前5→4、冻结6→5；两次DHR存在检查和其时点、当前active/版本id+SHA、完整流式摘要及响应均保持。用户选择尚未答复，本批未实施，不承诺省很多时间。
2. 汇总在已有父锁内建立内部读取上下文，避免每附件再读相同DHR，合并附件元数据读取；保留每个文件完整SHA/缺失拒绝、VERIFIED、来源hash、草稿修订和人工确认。一次读还是分块须按实际附件规模/行宽讨论后验证，不自行采用128或取消校验。不使用公共JSON暴露服务器路径，也不复用无父锁的导出路径。

索引判断见review-notes：已有主键与活动集合索引先复用，当前瓶颈证据是往返次数，新增索引不能消除2N。未跑完整安装上的EXPLAIN，不宣称无需任何未来索引。ZIP/PDF累计及单附件数组另列风险，没有因流式SHA完成而关闭。
