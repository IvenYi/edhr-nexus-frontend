# 读取风险、触发条件与具体拆分

入口为系统管理的审计日志页`/system/audit-logs`，个人设置的数据审计页及生产工单/批次的内嵌审计也调用同一controller。源码可证，未执行浏览器/真实HTTP。本批没有前端或样式修改。

当前先查全部匹配审计（含before/after JSON），逐条投影并查当前姓名，再在Java筛选派生菜单/模块/摘要及切页。历史从100→1000→5000，页面只取20行，SELECT仍101→1001→5001；共享/不同/缺失/空操作者四轴均成立。空操作者回退为“-”仍查询一次。打开、翻页、切页大小及输入筛选文本每个字符均可能触发，员工少也会随修改/签署/审批日志增长。React Query的查询key含即时文本，查询按钮主要重置页数。

最终同机共享5000行约3.02秒、调用线程累计分配274.20MiB；1000行JSON文本宽度1024→131072字符时约58.58→305.80MiB。不是常驻内存/峰值/RSS/生产SLA或并发承诺：包含Hibernate统计、StatementInspector及自动SessionMetrics日志开销，且只是单次合成实验。SQL次数与加载量由原生日志佐证，资源数字仅风险信号。

历史去重：`docs/development/branch-review-20261026-w4-lifecycle/findings.md`已记PERF-AUDIT-LIST-MATERIALIZATION-001，包含内存分页/N+1/算术候选。本批将算术子项升级为已复现整改，性能仍open。原始全量加载引入于1ea671cf1da3cff4f3f811ccfec0c44f1c4a86cb（2026-06-15）：同补丁增加派生字段过滤及相关测试。源码结构能说明派生筛选需求，作者未记录性能取舍，不能推断经过容量评估。

建议按两个有限切片推进，等待用户实际选择；未答复不当授权：

1. 先完成派生筛选/分页，仅对当前页批量补当前姓名。`AuditLogPresenter`纯函数负责原有模块/菜单/摘要/动作投影及历史姓名回退；`AuditLogQueryService`负责查询、过滤、计数/排序/分页和本页人员批量读取。保留displayName优先、缺失回退、所有记录可翻页。普通同名账户须先核租户/唯一性语义，不通过first-wins掩盖重复。此步能消除逐行姓名N+1，但仍全量加载审计，不能宣称解决内存分页。
2. 再把派生筛选等价条件放入数据库，内容和COUNT共用同一谓词，数据库分页后只加载本页。先逐项覆盖module/menu/summary空值回退、生产动作、文本大小写/空白、同时间稳定排序、全局/个人/内嵌边界，再选择投影列与索引。不能直接删派生筛选、把过滤放到分页后、先截100条或用抽样冒充完整COUNT。

两个方法域有明确边界，不建立通用动态查询框架。旧structure-plan已有同方向建议，本批补触发、职责、等价条件与验收步骤，不以行数代替拆分方案。现阶段仅局部两项正确性改动，未擅自大重构。

索引边界：canonical已存在action、created_at、(entity_type,entity_id)、operator_id和snapshot_hash索引。代表性lower(type)+entityId+created_at排序实验，当前计划用了idx_audit_entity的entity_id条件并额外排序；临时表达式组合索引消除该排序，块12→5。候选在隔离事务回滚，未进迁移。此实验不是完整JPQL/派生条件/COUNT/多排序方案，不能据此直接新增生产索引；尤其任何索引均不能消除Java逐行补名和全部实体加载。后续须在完整实际查询和代表性分布下评估读收益、写放大及重复索引。

权限/语义证据边界：当前全局与详情仅见authenticated，无controller方法权限；个人入口实际是USER_ACCOUNT/currentUserId目标对象，而非“我作为操作者”的所有事件。未找到足够依据新增全局访问政策，且共享生产入口不能直接套菜单权限。姓名SQL筛历史operatorName，显示优先当前displayName；是否统一尚缺业务定义，本批保持。两项是需补证范围，不包装成已通过或擅改规则。
