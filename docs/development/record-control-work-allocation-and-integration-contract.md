## 1. 文档目的

本文用于协调两个开发上下文共同完成表单变更和表单作废能力，并作为新账号、新 Codex 上下文或新开发者接手时的直接入口。阅读本文后，应能够回答：

- 当前产品要解决什么问题，哪些能力已经完成；
- 哪些工作属于公共流程域，哪些工作属于记录控制执行域；
- 双方分别开发哪些前端、后端、数据、审计和测试内容；
- 双方必须先冻结哪些接口，如何联调；
- 哪些当前源码只是占位或通用骨架，不能当作已完成能力；
- 开发时必须遵守哪些产品、UI、本体和质量规范。

本文不替代业务设计、本体规则或 UI 规范。发生冲突时，按第 2 节的权威顺序处理，不能自行选择对自己实现更方便的旧描述。

## 3. 产品范围与术语

本契约统一使用“表单变更、表单作废、转办、重新分配、退回”。在上下文明确时，前两者可简称“变更、作废”。“更正、普通转办、管理重新分配、拒绝”不作为本模块动作名称。既有 `RecordCorrectionRequest`、`CHANGE`、`OBSOLETE`、`TRANSFER`、`RETURN`、权限码和数据库字段是兼容性技术标识，不因中文术语统一而改名。

### 3.1 模块名称

继伟负责的范围不应只称为“表单变更模块”。准确边界是：

> **记录控制执行域**：同时包含表单变更和表单作废两个独立业务分支。

两类申请共用公共审核引擎，但不共用申请对象、状态落地和最终业务动作：

- **表单变更**：创建新修订；批准后新修订成为唯一当前有效修订，旧修订只读保留。
- **表单作废**：不修改字段值；批准后当前有效修订及来源记录被标记为作废，历史证据保留。

### 3.2 P0 已确认范围

- 只处理表单变更和表单作废；记录本变更、放行后变更属于后续范围。
- 已完成记录不能直接编辑，变更必须形成新修订。
- 变更和作废分别创建独立申请，不把申请字段塞进 `FormInstance`。
- 审核期间来源记录保持原主状态，只增加活动申请标记并锁定冲突申请。
- 申请人必须显式选择类型匹配、自己有权使用且已发布的审核流程版本。
- 申请内容、流程选择和申请人电子签名完成后，点击确认即启动审核；不存在开始节点的保存或提交动作。
- 审核流程支持顺序审批和非嵌套并行审批；并行分支全部批准后才汇合，任一分支退回则本轮退回并使其他本轮待办失效。
- P0 包含受限撤回、转办和重新分配。
- P0 不提供流程终止、强制跳转、跳过、加签或管理员直接批准。
- 流程运行日志与不可变合规审计分层保存，不能互相替代。

### 3.3 尚未关闭的事项及阻断范围

下面的事项性质不同，不能都当作需要用户回答的业务问题，也不能因为尚未关闭而阻塞全部开发：

| ID | 分类 | 当前负责人 | 阻塞的实现 | 不受阻塞的工作 |
| --- | --- | --- | --- | --- |
| `question.record-control-active-form-void-boundary` | 已登记业务问题 | 产品确认，继伟落实 | 活动、打开、已退回、未填报表单的作废资格、动作显隐和后端阻断矩阵 | 已完成记录主路径、领域对象、页面骨架、接口契约和资格校验扩展点 |
| `decision.record-control-managerial-reassignment-signature` | 待确认业务决策 | 产品确认，逸文落实 | 重新分配的签名阻断、签名审计字段和验收场景 | 重新分配的权限、原因、目标资格、不可变审计和页面骨架 |
| `evidence.record-control-non-admin-browser-matrix` | 证据缺口 | 联合验收 | 发布级权限验收结论 | 源码、接口和自动化权限测试 |

在活动表单作废边界确认前，不得把某一种活动表单处理策略写死，也不得用临时前端判断绕过已提交待审或正在运行原表单流程的风险。

### 4.1 不能沿用的当前源码假设

- `WorkflowEngine.createInstance(...)` 通过绑定规则选流程，不满足记录控制“显式选择并冻结版本”。
- 当前任务运行代码使用过 `REJECT`，模板语义使用 `RETURN`；正式对接前必须统一标准动作，不得让两个枚举长期并存。
- 当前并行退回路径可能把实例按终止处理，不符合“本轮退回”的记录控制语义。
- `WorkflowInstanceController` 中存在终止接口，但终止不属于记录控制 P0，不得在记录控制页面暴露。
- 任务动作只保存 `signatureId` 不等于已经验证电子签名真实性、用途、操作者和时效。
- `WorkflowLogController` 的新增、修改、删除接口是历史骨架；正式流程日志只能由运行时写入并对业务页面只读。
- `InstanceList`、`InstanceDetail`、`TaskDetail` 和 `InstanceLogs` 当前展示不足以作为最终 UI 模板，必须按现有统一页面规范重做。

## 5. 总体所有权原则

双方按领域能力切分，而不是简单按“前端/后端”切分：

- **逸文负责流程如何运行。**
- **继伟负责申请是什么，以及批准后记录如何变更或作废。**
- 双方只通过已冻结的启动契约、任务动作契约、结果契约和查询投影对接。
- 不允许继伟在记录控制模块复制一套流程引擎、任务、日志或干预实现。
- 不允许逸文在公共流程模块直接修改记录修订、DHR 完整性或投影冲销等领域数据。

扩展路径采用：

- `configuration`：审核流程模板及节点配置；
- `product-core`：公共流程实例、任务、并行推进、主体解析；
- `standard-action`：审批、退回、撤回、转办、重新分配；
- `transaction-orchestration`：申请确认启动、审批结果落地、锁和审计的一致性编排。

当前不使用 `project-plugin`，也不允许在控制器或页面中散落客户专用分支。

## 6. 逸文的工作：公共流程域

### 6.1 后端能力

逸文负责完成：

1. **显式版本启动**
   - 接收明确的 `workflowDefinitionId` 和 `workflowVersionId`；
   - 校验模板类型为 `RECORD_CONTROL`、分类匹配 `CHANGE/OBSOLETE`、版本已发布且可用；
   - 冻结定义、版本、节点、连线和必要执行快照；
   - 开始节点自动通过，不创建开始任务，直接创建首个审批节点任务。

2. **已发布流程候选查询**
   - 公共流程域是唯一后端实现所有者；
   - 按 `CHANGE/OBSOLETE`、发布状态和当前用户权限筛选可用版本；
   - 记录控制域只消费冻结 DTO 或 Mock，不复制模板筛选逻辑；
   - 申请确认时仍由后端重新校验，候选查询结果不是授权凭证。

3. **审核任务运行时**
   - `APPROVE`：完成当前审批任务并推进；
   - `RETURN`：退回当前审核轮次，失效本轮其他并行待办；
   - `TRANSFER`：当前处理人转给授权候选范围内人员，必须填写原因；
   - 审批主体到达节点时按当前关系解析并冻结候选人快照；
   - 禁止申请人自审；
   - 使用任务版本或等价并发控制防止重复审批。

4. **受限撤回协作能力**
   - 提供由记录控制事务编排调用的撤回接口；
   - 只有当前轮次尚无批准或退回决定时允许；
   - 原子失效当前轮次所有待办；
   - 输出确定的撤回结果，业务锁和拟修订处置由记录控制域完成。

5. **重新分配**
   - 只允许专门权限；
   - 校验目标用户状态、租户/数据范围和可处理资格；
   - 强制原因；
   - 记录原处理人、目标处理人、管理员身份和时间；
   - 不改变节点、流程路径或业务结果。

6. **结果与幂等**
   - 流程批准、退回、撤回等状态变化输出稳定结果事件；
   - 每个结果事件具有唯一 `eventId`；
   - 重复投递不会产生第二次业务落地；
   - 流程实例保存业务类型、业务申请 ID 和审计关联 ID。

7. **签名、权限和审计**
   - 根据已发布节点配置强制执行审批动作电子签名；
   - 验证签名属于当前操作者、当前动作和当前业务；
   - 流程动作写入只读运行日志；现有实现载体是 `WorkflowActionLog`，是否改名必须在阶段 1 单独决定；
   - 合规动作同时写入不可变 `AuditEvent`；
   - 禁止客户通过通用 CRUD 修改或删除运行日志、任务和实例。

### 6.2 前端页面

逸文负责：

- 我的待办和任务详情中的审批、退回、转办；
- 流程实例列表和实例详情；

## 7. 继伟的工作：记录控制执行域

### 7.1 后端对象与持久化

继伟负责设计并实现以下独立领域对象，名称可在实现设计阶段细化，但语义不得合并：

- `RecordCorrectionRequest`：变更申请；
- `RecordVoidRequest`：作废申请；
- `CorrectionRevision`：拟变更及历史修订；
- `ImpactAssessment`：DHR、放行、完整性和补开影响；
- 活动申请锁或等价唯一约束；
- 记录控制申请与流程实例、流程定义版本、签名和审计的引用。

数据库要求：

- Snowflake ID 在前端一律按字符串传输和保存，不能转为 JavaScript `number`；
- 当前有效修订必须唯一；
- 同一来源记录的冲突活动申请必须由数据库约束和事务校验共同阻断；
- 修订、字段差异、签名、申请和审计不物理删除；
- 所有状态变化保留真实前后快照；
- 变更/作废表与公共 workflow 表分别归各自领域维护；
- 双方开始写迁移前先预留不冲突的 Liquibase 编号，不能各自在分支上占用同一编号。

### 7.2 变更后端主路径

继伟负责：

1. 校验来源记录可变更、为已完成且存在当前有效修订；
2. 创建变更申请草稿；
3. 基于当前有效修订创建新修订草稿；
4. 使用稳定 `fieldId`、明细行 ID/字段路径和修订 ID 保存差异，不按显示名称匹配；
5. 生成字段级前后值、修订快照和哈希；
6. 生成 DHR、放行、投影和重汇总影响评估；
7. 确认申请时复核来源修订没有变化、签名有效、流程版本匹配；
8. 审核通过后在同一业务事务中：
   - 新修订变为唯一 `EFFECTIVE`；
   - 旧修订变为 `SUPERSEDED`；
   - 更新当前修订引用；
   - 使旧投影失效或冲销后重新投影；
   - 更新 DHR 待重汇总状态；
   - 写入不可变审计和幂等执行记录；
9. 退回或撤回时不写回来源记录，并按规则作废本轮拟修订、释放业务锁。

### 7.3 作废后端主路径

继伟负责：

1. 校验来源表单作废资格和当前有效修订；
2. 阻断已作废记录、冲突活动申请和当前 P0 明确不允许的路径；
3. 创建独立作废申请，不创建拟变更修订；
4. 保存原因、替代方案和影响评估；
5. 确认申请时复核来源状态、签名和流程版本；
6. 审核通过后：
   - 来源记录和当前有效修订标为作废；
   - 不修改原字段值；
   - 冲销或失效相关投影；
   - 使 DHR 目录证据失效并触发完整性缺项；
   - 需要替代时生成补开待办，不由前端自动创建新表单实例；
   - 保留所有历史、签名和审计；
7. 退回或撤回时不产生作废结果，只更新申请状态并释放业务锁。

活动表单的精确作废资格必须等待开放问题关闭，不能由继伟自行决定。

### 7.4 继伟负责的前端页面

#### 表单变更工作台

- 查询来源记录：批次/工单、产品、表单名称、流水号、DHR 编号和状态；
- 变更申请列表：申请单号、来源记录、原因、状态、当前/拟修订、申请人、提交时间、当前审核节点或审核人；
- 草稿继续编辑和删除；
- 审核中查看和符合条件时撤回；
- 已批准/已应用查看及修订对比；
- 已退回修改后重新提交。

变更向导至少包括：

1. 确认来源记录和当前修订；
2. 填写受控原因分类和必填原因；
3. 只读原文与拟变更内容并列编辑；
4. 自动展示字段级前后对比和标红；
5. 展示 DHR、重汇总和放行影响；
6. 显式选择“表单变更审核”的已发布流程；
7. 申请人电子签名；
8. 点击确认后一次性创建/确认申请并启动审核。

#### 表单作废工作台

- 页面骨架与变更页保持同一产品模式；
- 不显示拟修订编辑器；
- 展示来源记录只读内容、作废原因、替代方案和影响评估；
- 只允许选择“表单作废审核”的已发布流程；
- 申请人签名确认后启动审核；
- 必填证据作废后展示“需补开表单”结果，不自动补实例。

#### 变更与作废审核业务详情

公共任务入口由逸文负责，但业务详情内容由继伟提供可复用组件或查询投影，包括：

- 来源记录只读原文；
- 变更的新旧修订对比；
- 作废的影响评估；
- 原因、申请人签名、关联 DHR 和放行状态；
- 申请状态和业务落地结果。

审批、退回和转办按钮仍由公共任务详情负责，继伟不能在业务详情组件里再写一套任务动作。

## 8. 双方必须冻结的对接契约

以下是正式开发前必须共同确认的契约边界。字段名称是当前建议稿；在写入代码、OpenAPI 和执行契约后才成为已实现事实。

### 8.1 已发布流程候选查询

用途：继伟负责的申请向导展示可选流程。

所有权：公共流程域负责后端查询接口、授权与筛选；记录控制域负责在申请向导中调用该接口，并在公共接口未就绪时只使用遵循同一 DTO 的 Mock。

输入至少包含：

```text
businessType: CHANGE | OBSOLETE
```

公共流程查询不读取来源记录；来源记录资格、申请人身份和业务数据范围由记录控制申请入口负责。候选接口按动作类型要求对应发起权限，不能把候选查询结果当作确认申请时的授权凭证。

输出至少包含：

```text
workflowDefinitionId
workflowVersionId
templateName
templateCode
versionNumber
businessType
status = PUBLISHED
```

规则：

- 只返回类型匹配、已发布、当前用户有权使用的版本；
- 不返回草稿、历史非当前版本或停用模板；
- P0 不自动代选，也不设置默认流程；
- 前端即使过滤，后端确认申请时仍必须重新校验。

已冻结实现：

```text
GET /api/v1/workflow/record-control/candidates?businessType=CHANGE|OBSOLETE
CHANGE    -> record-control.corrections.create
OBSOLETE -> record-control.voids.create
```

### 8.2 记录控制申请确认与流程启动

外部 REST 入口应归记录控制域所有，避免前端分别调用“保存申请”和“创建流程”造成半成功。建议由记录控制应用服务在同一事务中调用公共流程启动服务。

建议命令语义：

```text
ConfirmRecordControlApplicationCommand
  requestId
  requestType: CHANGE | OBSOLETE
  sourceRecordId
  sourceRevisionId
  workflowDefinitionId
  workflowVersionId
  applicantSignatureId
  idempotencyKey
  auditCorrelationId
```

事务顺序：

1. 从认证上下文取得申请人；
2. 锁定申请和来源记录；
3. 校验申请内容、来源状态、来源修订和活动申请冲突；
4. 验证申请人电子签名；
5. 重新校验显式选择的流程定义/版本；
6. 保存申请快照并冻结流程引用；
7. 调用公共流程的显式版本启动服务；
8. 直接创建首个审批任务；
9. 回写 `workflowInstanceId`；
10. 写入业务审计和流程开始日志；
11. 整体提交；任何一步失败都不能留下孤立申请或孤立流程实例。

记录控制域对前端提供的“确认申请”REST 返回至少包含：

```text
requestId
requestNo
requestStatus
workflowInstanceId
workflowStatus
startedAt
```

其中公共流程域的 `RecordControlWorkflowPort.start(StartCommand)` 只返回流程侧能够权威提供的
`requestId / workflowInstanceId / workflowDefinitionId / workflowVersionId / workflowStatus /
currentNodeIds / startedAt / auditCorrelationId / workflowSnapshotHash`。`requestNo` 和
`requestStatus` 由记录控制申请域在同一事务完成后补入外部响应，公共流程域不得反向读取或伪造申请状态。

### 8.3 审批任务动作契约

任务详情只提供以下标准动作：

```text
APPROVE
RETURN
TRANSFER
```

约束：

- `RETURN` 是正式“退回”语义；当前代码中的 `REJECT` 必须在对接前统一或显式映射，不能让业务模块猜测。
- `TRANSFER` 只能由当前任务处理人发起，必须填写原因，不改变业务申请状态和流程路径。
- 动作请求不接受可信的 `operatorId`，操作者必须来自认证上下文。
- 电子签名要求由冻结的节点按钮配置决定。

### 8.4 申请级撤回契约

`WITHDRAW` 由申请人在记录控制申请详情发起，记录控制域拥有外部 REST 入口和申请权限校验；它不是审批节点按钮，也不是任务详情动作。

记录控制确认申请人身份和申请状态后，调用公共流程域的受限撤回协作服务。公共流程域负责校验当前审核轮次尚无批准或退回决定，并原子失效该轮全部待办；记录控制域负责更新申请状态、处置拟修订、释放业务锁和写业务审计。双方使用申请并发版本、流程实例版本或等价机制防止重复撤回。

阶段 1 冻结的调用边界为 `RecordControlWorkflowWithdrawalPort.withdraw(WithdrawCommand)`，返回
唯一的 `WorkflowResultEvent(result = WITHDRAWN)`。该端口的运行时实现属于阶段 4；继伟当前可以按
相同签名提供 Mock，但不得自行新增第二套撤回枚举或从前端直接调用公共流程引擎。

### 8.5 管理干预契约

`MANAGERIAL_REASSIGNMENT` 只从流程干预页面进入，由公共流程域拥有接口和专门权限校验；它不是任务详情动作，也不是审核节点可配置按钮。

重新分配必须校验目标用户、租户/数据范围和处理资格，强制填写原因，记录原处理人、目标处理人、管理员及时间，并保持节点、路径和业务结果不变。是否额外要求电子签名仍是待确认业务决策，在确认前不得静默强制或静默省略。

### 8.6 流程结果事件

公共流程域至少输出：

```text
WorkflowResultEvent
  eventId
  workflowInstanceId
  workflowDefinitionId
  workflowVersionId
  businessType: CHANGE | OBSOLETE
  businessId: 记录控制申请 ID
  result: APPROVED | RETURNED | WITHDRAWN
  occurredAt
  operatorId
  signatureId
  auditCorrelationId
  workflowSnapshotHash
```

规则：

- `APPROVED` 才允许记录控制域执行变更或作废落地；
- `RETURNED` 和 `WITHDRAWN` 不落地来源数据；
- P0 不应为记录控制产生 `TERMINATED` 结果；
- 记录控制域以 `eventId` 幂等消费，同一事件只能落地一次；
- 事件消费与业务落地失败时必须可重试、可审计，不能只靠前端再次点击；
- 采用事务内回调、事务事件还是 outbox，需要在实现设计时确定，但不得改变上述业务语义。

P0 已选择单体内同步事务端口 `RecordControlWorkflowResultHandler`：公共流程在完成事务提交前同步调用记录控制处理器，处理失败则整笔事务回滚。当前不引入 outbox 或异步消息；若后续拆分部署，再以不改变 `WorkflowResultEvent` 载荷和 `eventId` 幂等语义为前提升级传输方式。

### 8.7 业务详情投影

公共任务详情需要读取业务申请摘要，但不能直接依赖记录控制数据库内部结构。继伟应提供稳定查询投影，至少包含：

```text
requestId / requestNo / requestType / requestStatus
sourceRecordId / sourceRevisionId
reasonCode / reasonText
applicant / submittedAt
impactAssessmentSummary
correctionDiffSummary（仅变更）
workflowInstanceId
```

公共流程页面只展示投影并执行标准任务动作，不修改记录控制业务数据。

## 9. 状态与动作责任边界

| 事件 | 公共流程域 | 记录控制执行域 |
| --- | --- | --- |
| 保存申请草稿 | 无动作 | 保存申请/拟修订草稿 |
| 确认申请 | 创建并启动流程、首任务 | 校验、签名、冻结引用、锁定来源记录 |
| 审批 | 完成任务、推进或聚合 | 不提前修改来源记录 |
| 退回 | 结束本轮、失效本轮待办 | 申请进入退回处理，拟修订按规则作废，来源不变 |
| 转办 | 更换当前任务处理人并写日志/审计 | 业务申请状态不变 |
| 重新分配 | 管理员更换处理人并写干预记录/审计 | 业务申请状态不变 |
| 撤回 | 校验轮次并失效待办 | 更新申请、作废拟修订、释放锁，来源不变 |
| 全部批准 | 输出唯一 `APPROVED` 结果 | 幂等执行变更或作废落地 |
| 落地失败 | 保留流程完成事实和关联 ID | 记录失败、可重试，不得重复修改来源数据 |

申请状态和工作流状态必须分开建模，不能把工作流 `RUNNING` 直接当作记录申请的唯一业务状态。

## 11. 权限、签名与审计

### 11.1 权限

阶段 1 已冻结以下权限命名，双方不得另造同义权限码：

- `record-control.corrections`：查看表单变更申请；
- `record-control.corrections.create`：发起表单变更；
- `record-control.voids`：查看表单作废申请；
- `record-control.voids.create`：发起表单作废；
- `record-control.requests.all`：查看全部记录控制申请；
- `workflow.task.approve`：处理审批或退回；
- `workflow.task.transfer`：转办；
- `workflow.logs`：查看流程日志；
- `workflow.intervene`：查看流程干预并执行重新分配。

所有数据查询还要叠加业务数据范围；不能只靠菜单或按钮显隐保护接口。

### 11.2 电子签名

- 申请人签名由记录控制确认事务负责采集和验证；
- 审批人动作签名由公共流程任务运行时负责；
- 签名必须绑定操作者、动作、业务对象、时间和签名证据；
- 保存 `signatureId` 但不验证签名不算完成；
- 转办是否要求签名按已发布节点配置执行；
- 重新分配是否额外要求电子签名尚未被当前决策明确，不得自行默认。

### 11.3 日志和审计

| 数据 | 所有者 | 是否可修改 | 用途 |
| --- | --- | --- | --- |
| `WorkflowActionLog`（当前实体/表） | 公共流程域 | 否 | 页面时间线、运行排查；先收敛为运行时只写、业务页面只读 |
| `WorkflowIntervention` | 公共流程域 | 否 | 重新分配事实 |
| `AuditEvent` | 对应动作领域 | 否 | 不可变合规证据 |
| 申请状态历史 | 记录控制域 | 否 | 业务生命周期追溯 |
| 修订和字段差异 | 记录控制域 | 否 | 证明原值、新值和生效过程 |

同一动作可同时产生运行日志与审计事件，但二者职责不同。双方通过 `workflowInstanceId`、`requestId`、`eventId` 和 `auditCorrelationId` 关联。

本文中的“流程事件日志”是目标业务概念，不代表需要新建 `WorkflowEventLog` 实体。阶段 1 已选择保留并演进现有 `WorkflowActionLog`/`workflow_action_log`，禁止另建第二套并行日志表。外部行为必须收敛为运行时写入、业务页面只读，历史迁移和 API 兼容由公共流程域负责。

## 14. 联合验收清单

### 14.1 变更

- 已完成记录可创建变更草稿，原数据保持只读；
- 确认前必须选择匹配的已发布变更审核流程并完成签名；
- 重复确认只创建一个申请和一个流程实例；
- 审核中来源记录仍显示已完成，同时显示变更审核中标记；
- 串行和并行全部批准后只执行一次新修订生效；
- 任一退回不改变来源数据并失效本轮其他待办；
- 撤回条件按本轮决定校验，成功后释放锁且不落地；
- 新修订唯一有效，旧修订、签名和哈希可追溯；
- 字段差异使用稳定 ID 定位并正确标红；
- DHR 和投影按影响规则更新且有审计。

### 14.2 作废

- 资格校验正确阻断已作废、冲突申请和明确不允许的来源；
- 只可选择已发布的作废审核流程；
- 审核中来源主状态不被改为审核中；
- 批准前字段值、修订和 DHR 证据不变；
- 批准后记录及当前修订作废，字段值不被修改或删除；
- 投影冲销、DHR 证据失效和完整性缺项可追溯；
- 必需证据需要替代时生成补开待办，不自动创建表单实例；
- 退回和撤回不产生作废结果并释放锁。

### 14.3 公共流程与干预

- 申请与流程实例可通过 `requestId/businessId` 双向追溯，并具有同一审计关联 ID；
- 实例冻结用户选择的定义和版本，后续发布新版本不改变在途申请；
- 开始节点不产生任务，首轮任务对应正确审批节点和冻结候选人；
- 到达审批节点时解析并冻结候选人；
- 申请人不能审批自己的申请；
- 转办只允许当前处理人选择授权目标，强制原因；
- 重新分配只允许专门权限，强制原因；
- 转办和重新分配不改变节点、路径或业务结果；
- 日志只读，动作、处理人、时间、意见、签名和原因完整；
- 审计不可修改或删除，并可从申请反查流程、从流程反查申请；
- 不出现记录控制终止、跳过、强制跳转、加签和管理员直接批准入口。

### 14.4 质量与规范

- 前后端单元和集成测试覆盖成功、失败、重复、并发和权限边界；
- 使用当前初始化数据库完整执行迁移；
- 实际浏览器验证桌面主要分辨率、空态、长文本、滚动和错误定位；
- 列表、弹窗、Drawer、状态、操作图标和边距符合当前 UI 规范；
- 本体知识、规则、证据、执行契约和实现锚点同步；
- 全新独立质量实例返回 `qualityResult.result: passed`。
