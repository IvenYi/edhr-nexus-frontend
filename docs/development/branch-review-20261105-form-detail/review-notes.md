# 源码核对、性能边界与拆分方案

## 原始链路

中央 `WorkflowOperationsController.detail` 按form前缀分发，普通表单进入 `FormWorkflowOperations.detail`。该方法先执行 `FROM + visibility` 的一条查询，关联原表单记录、执行、生产对象及工单，再按真实operation/form/copy定位原快照与进度。未授权行不会进入context或姓名查询。source列表同样在共享COUNT／分页前构造领域可见范围，不能将中央用户权限当成所有普通表单内容读取授权。

detail枚举冻结flow节点，仅为ACTIVE进度内的当前APPROVAL节点生成待办；transferAssignees为空时显示“候选人待处理”。非空调用 `name`，按Long解析并通过仓储取当前displayName，缺失保留原ID。同一只读事务使用相同JPA持久化上下文，已读取的现存用户可复用；重复缺失findById不会缓存，不能从循环直接推定所有情况均N次。原生9组数据已分别证实。非数值ID原本会解析失败，本批未将它改为静默fallback或重新定义历史兼容。

历史沿state.history按operationId、formId、copyId过滤；APPROVE／RETURN的任务姓名、意见及signatureId来自当时history，不回查当前账户。当前账户姓名不得替代历史签署身份；也不能把通用WorkflowOperationsQuery的文本ID匹配和“待候选人处理”回退直接搬到此处，两域原解析与回退不同。此批用例只验证历史引用保持，不认证对应电子签名本体或真实签署过程。

`WorkflowResponsibilityService.reassignmentTargets` 经真实代理校验workflow.intervene和活动状态，再从原candidateSnapshot（改派后取originSnapshot）构造原候选文本IN，记录控制另排除申请人；DHR管理员目标仍走其双权限专用分支。新容量观察使用普通GENERAL管理员入口，未声称已经覆盖记录控制/DHR全候选容量；原138相邻回归与本轮结果分别计数。目录保留完整Specification、100数据库上限和写入时即时资格重核。

## 本轮发现与规模

1. `PERF-FORM-DETAIL-CURRENT-NAMES-20261105`：多个当前审批节点涉及不同人员或缺失人员时产生1+N查询。通常只一个当前节点则为2次，同一现存人员由一级缓存控制为2次，空人员仅1次。主要随“当前并行审批节点及不同／缺失人员数”增长，不随全部历史审批数直接增长；大数据合成结果不等同实际日常耗时。方案为本请求只批量取当前涉及人员并保留普通表单原数值解析、空与缺失显示和历史来源，已问用户；本批不实施。
2. `PERF-ORIGIN-CANDIDATE-PARAMETERS-20261105`：候选集合限制正确且有界返回，但每个原候选仍占一个绑定参数，5000候选目录为5007参数。当前测试没有触及驱动最大参数数，也不证明所有更大集合可用。可单独评估文本数组单参数，不能为避参数限制截断候选、缩小授权或先取100再过滤。
3. `PERF-ORIGIN-TEXT-ID-PLAN-20261105`：65005账户、其中5000个带关键字原候选的控制分布，观察SQL重放为1/100/5000候选均Seq Scan，分别返回1/100/100，源扫描匹配1/100/5000。数字主键不能自然用于当前cast文本比较，前后百分号关键字也不等于普通前缀索引。该计划不包含生产并发、冷缓存、通用计划切换或真实租户分布。

索引边界：实际已有user_account主键、(tenant_id,username)唯一索引及avatar索引。先比较保持精确文本身份的谓词／数组方案与表达式索引，不直接把“00042”改成42，也不为一个合成计划加重复索引。若评估表达式索引，应同时测租户规模、状态与锁定选择性、关键词、排序/限100、写放大与空间；数组方案只减少绑定参数，不自动消除文本转换扫描。当前未新建或删除任何索引。

## A23及健壮性复查

| 项目 | 本轮判断 | 处置 |
|---|---|---|
| 循环findById | 条件性N+1，不能忽略一级缓存 | 按重复现存／不同／重复缺失／空分别实测，保留open方案 |
| 先授权再补姓名 | 必要读取边界 | 不为批量查询将其移到可见性校验前 |
| 名单已过滤，写入仍重核资格／状态 | 必要提交保护 | 名单和写入存在时间间隔，不能当过度防御删掉 |
| 目录后置available与SQL资格重复 | 既有A23复查候选 | 本批不借取证删除共享保护；其与require/available的具体职责在W6单独核 |
| 捕获／解析异常 | 原快照和task-key错误统一领域拒绝；state哈希异常转内部错误 | 未凭catch数量增加兜底、静默吞错或重试 |
| 重复visibility字符串计算 | 当前只读安全上下文，不产生人员查询 | 没有性能依据，不为统计重复新增缓存／框架 |
| 全任务／历史列表 | 详情契约中的完整输出 | 不误称内存分页，也不擅自截断历史 |
| active线性包含与每节点progress哈希 | 静态CPU增长候选 | 尚无独立分配/CPU实验，不作为已测缺陷或顺带修改任务状态摘要 |
| 明细原件不变 | 前后比较执行snapshot/state/revision和表单snapshot/values/status | 只读观察不回写历史、候选或签署 |

## 具体抽取次序

若用户选择姓名优化，先在FormWorkflowOperations新增单一私有 `currentAssigneeNames`：输入已授权Context的当前APPROVAL节点与transferAssignees，输出原文本ID至按原Long身份查到的当前姓名映射，空、缺失及解析异常分别保留。不跨请求缓存、不读取全租户人员、不与通用流程姓名方法合并、不把写入name调用顺带改造。

随后可分批抽 `projectNodesAndCurrentTasks`、`projectEdges`、`projectHistory` 三个纯投影方法；历史方法只消费已定位的原历史，不查询账户。若职责和复用足够，再形成 `FormWorkflowReadProjection`。首次拆分先保护当前输出、过滤、顺序、taskState及历史证据，再逐方法移出；不要仅按行数拆类。

写入targets/reassign/requireActive仍由领域编排拥有；work_order→production_object锁序、锁下重读、revision竞争校验、签名、当前责任变更、原history及领域审计保持同事务。回滚只恢复委托或私有读方法，不恢复／修改任何业务历史。这些为具体后续方案，本轮未做大模块重构。
