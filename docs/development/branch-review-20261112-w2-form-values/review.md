## 根因与两项最小优化

原证据校验为每一子表行执行`values.deepCopy()`，而values包含整张子表；即使所有列是普通文本也复制完整图，形成随行数平方增长的分配。blame定位该上下文写法自82d7a56ca（2026-09-17）已存在，并非上轮引入；原件资格SQL自1cfd73483已有。源码能证明组合主表与当前行的用途，作者当时是否有其他考虑没有原始说明，不能替其编造设计理由。

1. 每行仍新建顶层ObjectNode，再setAll主值及当前行；共享的子节点只读。FormReferenceLookup不写传入values，递归也各建新根容器，输入和previous精确内容断言保持。没有省略主表条件／当前行条件、共享可写容器或跨请求缓存。
2. 每次公开五参字段证据校验入口创建局部`Map<Long,List<String>>`，仅其递归调用树共用；objectId在整棵树固定，因此缓存的是当前对象范围SQL返回的原件元数据。仍逐处比较originalName，未缓存“已通过”结果。独立公开调用重新查询；不同顶层字段的独立调用也各自重新查询，不能宣传成整个SAVE全字段只查一次。

原SQL的ID、PRODUCTION_EXECUTION及target_id谓词完全相同，没有跳过不同ID、无权对象、伪造名称或异常；缺失即拒绝，数据库错误继续传播。生产原件的普通删除入口原本禁止删除，复用范围也不跨调用。原调用者事务、锁、签名／字段权限、业务校验和审计代码保持。没有读取文件内容／SHA逻辑变更，没有加人数、行数、文件数上限或新索引。
