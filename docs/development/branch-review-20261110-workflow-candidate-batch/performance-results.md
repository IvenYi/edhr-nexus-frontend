# 候选读取优化与索引边界

记录变更页加载 CHANGE／OBSOLETE 审批流程选项时，旧服务对每个匹配定义查询 current 版本。用户已经明确授权本批批量读取并精简字段；没有再次要求确认。

新服务以一次联合标量查询取定义 ID、版本 ID、名称、编号、版本号、业务类型和版本状态。current 唯一性先于发布过滤，7 个对外字段及数据库名称排序保持。没有 total cap，也没有按“最新”回退选版。

## 主侧实际结果

同一 canonical PostgreSQL 夹具：每类返回 M 个有效候选，另有两个匹配但无可返回当前发布版的定义。旧通式 1+D，此处 D=M+2；新服务全部规模均 1 条 SELECT。

| 每类候选 M | 旧／新 SELECT | 旧第二次服务计时 CHANGE／OBSOLETE | 新第二次服务计时 CHANGE／OBSOLETE |
| ---: | ---: | ---: | ---: |
| 0 | 3／1 | 2.16／2.00 ms | 1.82／1.14 ms |
| 1 | 4／1 | 2.24／1.79 ms | 1.92／0.74 ms |
| 10 | 13／1 | 6.05／6.47 ms | 1.33／2.02 ms |
| 100 | 103／1 | 55.93／60.76 ms | 4.31／3.85 ms |
| 1000 | 1003／1 | 463.87／362.46 ms | 21.91／22.79 ms |

旧数据取 PR78 的真实原件，不重写历史运行；新数据来自 clean `c2691bf7`。20 个观察的完整 7 字段载荷逐项与旧原件一致，每类最大 1000 的末项可达。新服务20调用共20SELECT/20实际 auto_explain，参数原件为 RECORD_CONTROL、CHANGE或OBSOLETE、PUBLISHED；独立对照 Hibernate `?` 与 PG `$1/$2/$3`，没有 ID 参数扩张。

1000 档第二次调用线程累计分配从约40.4／40.0 MiB降到10.4／9.7 MiB。版本图 JSON 不再被 SELECT，另用宽图夹具核实投影边界；不据此宣称已量化真实宽图生产吞吐。以上为本机热缓存、带计划采集的合成数据服务计时和累计分配，不含 HTTP 序列化或前端渲染，不是用户整页响应、进程峰值、并发或 SLA。

同字节最终原生测试用于旧服务反证：14 项中 8 正向通过，6 项查询/列预算真实失败，0错误/跳过。旧服务是目标提交原字节；仓储中虽已有未调用的新查询声明，旧服务实际仍走原逐条实体路径。首轮双草稿夹具导致的2错误另存，修正为验证原DB约束，不能计作代码缺陷。

## 实际计划与索引结论

0–1000 档每次对定义表、版本表各一次 Seq Scan，Hash Join 后按名称排序；不是应用里逐行往返。1000 CHANGE 第二次计划中，版本过滤后2008行，匹配定义1002行，join输出1001行（含一个被service剔除的草稿current），最终DTO1000。排序126KiB、Hash峰值89KiB、单批；全部20计划所有关系扫描 loops=1，无临时块读写。

旧版本逐条读在1000档曾使用现有 `uk_wf_def_version(definition_id,version_number)`；定义已有 `(type,business_type)` 索引。新查询在本夹具选择一次扫描不构成新增索引依据，添加索引也不是消除旧N+1的办法。本批不改schema/索引。

该结论只覆盖当前目录分布；大量历史非current版本、明显偏斜的业务类型、更多租户/定义、冷缓存与并发仍需用实际规模和 prepared 计划评估。若这些分布使版本扫描/排序或缓冲访问显著增长，再比较 current 部分索引或过滤/排序组合索引与写入、空间成本；不能直接加 `UNIQUE WHERE is_current`，因为那会改变本批保留的既有数据约束和失败边界。
