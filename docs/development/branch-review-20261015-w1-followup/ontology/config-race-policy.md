# W1 配置并发：现行冻结政策与实现边界

来源：`31a8074a8962da66b2c4e49f4bf5a1a92724bfa0`；实时目标 `edhr-dev@6379bf105127b05a65695992b008b55c142264f9`。知识0.3.25/schema1.2.0。本批只读，不改知识定义/成熟度/业务政策，不跑Maven/数据库/浏览器，不承担最终独立质量。全部规范引用可按 `policy-index.json` 的精确ID、路径、locator和原文复核。

## 结论

现行规则足以保护**一次实际使用冻结的身份及引用关系一致性**，无需为修复确定的混合引用引入新的发布流程、模板编辑禁令或把冻结时点提前到对象拆分。原始来源没有规定统一的事务开始/请求到达/锁取得时间作为全配置唯一切点；一致快照的锁、重读、隔离级别或重试属于主开发技术选择，应有反例测试保护。

必须区分两种重现：

- 若执行context仍指路线/DHR版本A，实际冻结bindings却使用仅属于新版本B的routeNode/dhrItem/form引用，结果从未满足“所选制程→所选路线/DHR→该目录表单”关系，违反DEC-0001-04/05/06、DEC-0062-03与DEC-0077-12所确认的依据和可追溯身份。可作为确定技术一致性问题处理，不需重问用户。
- 若仅见同一仍可编辑版本的旧名称与新内容，所有引用仍合法，不能只凭“旧context+新绑定”标签就断言违反业务政策。应证明真实身份/版本/关系或本次使用依据不一致；原确认未禁止管理员在START进行期间编辑配置，也没指定全部字段必须取事务开始瞬间的值。

## 终止详情前置当前execution解析：合法入口反证

`DhrInstanceService.detail:249–254`确实先解析当前execution，再于256–262核验并返回终止snapshot。但本批未找到**合法后续写入**能把已终止execution改为不可解析：

1. main生产源码写execution JSON只定位到两个路径：ProductionExecutionService.act:236用已解析/构建ObjectNode.toString保存snapshot/state；DhrFillingService.mutate:115仅用解析后state.toString更新。不存在已发现的任意原JSON字符串回写接口。
2. act:159–179先校验工单/对象状态，已提前结束不能正常执行；mutate:84–96要求生产COMPLETED及summary NOT_STARTED/DRAFT，已终止不满足。
3. 管理员改模板/路线等配置只改主数据，不回写既有execution；无效新配置在builder.json:267–270报错、不会通过事务形成半个新execution。A12受控变更/作废没有发现落地改写execution的消费者；已有record-control阶段端口不能冒称完整受控写入已实现。

因此这是已定位的历史读取依赖或潜在健壮性改进，**当前不构成已证明的可达业务缺陷**。不得用手写坏数据库JSON证明合法流程可触发，也不必为这个未成立前提改业务代码。若主审找到其他合法写入口、真实迁移或类型演进反例，应按实际路径再评估。
