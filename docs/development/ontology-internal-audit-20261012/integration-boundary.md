## 4. 两种“投影”的范围

功能分支的投影是**表单内容追溯索引及业务统计读模型**：它关心字段来源、正式统计生效时间、保存内容查询、真实执行上下文和 DHR 归属。研发本体中的投影则包括知识按内部、客户、运行时范围发布，以及 P1 的语义影响查询。

功能分支的投影开发完成，不能自动证明本体 P1 或全库审计完成；当前目标分支的本体审计完成，也不能替代这个未合并功能的验收。以上是职责和覆盖边界判断，本次没有重新认证功能分支的运行实现。

## 5. 保持 git pull / git push 工作方式的三步集成

1. **形成候选并读新契约。** 在工作已提交或安全保存后获取最新目标与功能分支，将目标正常合入共享功能分支，或使用独立集成分支/工作树组合双方内容。保留朋友的提交历史。AI 显式重读变更后的契约，并记录当次真正的目标、功能和契约提交；单独 fetch 不代表工作文件或 Agent 上下文已更新。
2. **完成受影响知识与实现核对。** 处理投影决策整个 ID 家族及当前引用；按当前已确认规则和真实代码核对投影、使用时快照、表单原始记录、DHR、事实类型及受影响审计修复。保留历史映射和已确认局部替代，生成具体集成候选提交。无需为这个功能再全仓重审与其无关的历史知识。
3. **验收同一候选后正常推送。** 在候选上运行目标新知识校验入口及按风险选定的功能/集成验证，记录 target、feature 和 tested commit，并完成适用独立复核。推送前再次获取目标；若目标变化，先同步并重查影响。目标未变化时，可将已验收候选快进合入 `edhr-dev` 后普通 `git push`。不强制改写共享历史；没有服务器强制保护时，团队纪律与推送后的 CI 只能共同降低风险，不能承诺阻止所有绕过。
