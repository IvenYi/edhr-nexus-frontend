# 有限源码、健壮性和性能范围

## 根因与等价范围

TenantTransferTargets全部公开搜索入口最终组合相同租户、ACTIVE、未锁定、关键词、当前处理人排除及领域传入scope/权限谓词，按displayName和数字id排序。返回类型为List，只消费Page.getContent，无人使用total；实际100及以上匹配人员会由Spring Data为Page多发COUNT。

本次只把findAll(Specification,PageRequest).getContent替换为findBy(Specification, finder -> sortBy原Sort.limit(100).all)。已核实际安装的Spring Data Commons/JPA3.3.0接口与实现，limit保存至TypedQuery.setMaxResults，all调用getResultList而不调用count操作；仍由数据库限量，不在Java对全量stream截断。普通用户管理列表的分页和总数不在此改动范围，这里仅是转办/改派目标目录。

Specification原字节不变：双权限仍两个独立EXISTS以AND组合，原候选、unrestricted、申请人回避仍由领域scope在SQL限量之前过滤。目录自身租户/状态/锁定/搜索/排除与Sort、Map字段及后置available/当前人检查保持，写入require及各领域提交时资格/签名/状态/锁/审计/冻结不改。PR58已合入的当前姓名批量读取保持完整源码。

## A23和规模核查

| 核查 | 结论/处置 |
|---|---|
| 未消费total的COUNT | 当前属于无业务用途的额外读取，移除；不是资格或完整性保护 |
| 完整资格Specification | 必须保留，含双权限/原候选/申请人边界；不为省COUNT简化where |
| 后置available/当前人排除 | 既有重复条件未顺带删除，W6继续按实际上下文核，不凭文本重复视为可删 |
| 写入实时复核 | 名单读取不能授权提交，所有原校验保持，不当过度防御移除 |
| 数据库限量与内存 | 仍最多100实体结果，不靠全量all再Java limit；需原生SQL与服务器参数核实 |
| 同名排序 | 同一displayName时按Long id，不能改按用户名或字符串id排序；新夹具120同名且用户名反向 |
| 5000匹配人员 | 仅证明该分布下不COUNT、有界返回；不是全部权限scope/全文匹配分布或生产SLA |
| 大原候选/文本IDCAST | 无新证据，另做参数与计划审计；不新加表达式/重复索引或缩小业务范围 |

## 抽取与回滚

本批复用已存在的人员资格所有者和Spring Data能力，未增加私有仓储实现、通用查询包装器或策略。域服务继续拥有原候选/申请人/双权限来源，身份目录只消费已组合的条件并做有界读取；不把领域政策搬进框架或UI。

后续可按真正重复的投影/目录读取需求再评估小方法抽取；当前只替换一处终结查询，额外抽象没有收益。回滚范围是该读取和对应优化预算，保持既有资格断言，不恢复历史业务数据。较长模块拆分沿旧具体方案及锁/事务/签名/审计所有权，不借本轮小改大重构。
