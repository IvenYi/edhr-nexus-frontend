# 有限源码、规模与健壮性核查

当前基线fa592169。方法范围：WorkflowOperationsQuery.detail/visibility及Task仓储、TenantTransferTargets.search各入口和最终Page消费；现有资格/写入路径只作保持核对。源码指纹不等于全文件语义完成，固定盘点和历史唯一覆盖分别报告。

## 原件与根因

中央读取接口`GET /api/v1/workflow/operations/instances/{id}`的非form身份进入WorkflowOperationsQuery.detail。实例可见性SQL先执行，随后读取节点、边、任务及日志；任务映射内逐次查询user_account.display_name，故当前4个公共Jdbc查询+N个姓名查询+1个仓储查询=5+N。原生观测确认0/1/100/1000为5/6/105/1005。两个重复有效用户、NULL及已不存在ID各占重复模式；全部姓名仍是N次，不复用已有值。

assigneeName是当前账户目录名，NULL/缺失原样显示“待候选人处理”；当前日志operatorName也优先当前目录，再用存储名字/ID。签署时身份另存signature及snapshot。性能修复不能把当前目录名伪装为历史签署身份，也不能顺带改日志或已删除账户的展示政策。本批按已有行为取证，未将这种显示选择提升为用户新确认的业务规则。

目录使用Spring Data PageRequest(0,100)，消费getContent后返回List。少于100时框架由短页推算而不COUNT；满100则为Page额外计算总数。实际100、101和5000人员均2条Hibernate SQL，其中1条COUNT，而调用方没有使用总数。这不是Java内存分页或把所有人员实体加载后截断；内存结果有100上限，额外聚合的DB成本另计。

## 可实施方案及具体抽取

姓名方案：先保留原tasks.findByInstanceId结果，在同一次只读调用中收集不同的非空assigneeId；按原文本身份一次读取匹配名称，组装Map后复用。只查实际任务中的ID，不读取全租户人员，不把“00042”等非规范旧文本自行改成42而改变旧fallback；保留查到但display_name为空与完全未查到的区别。无有效ID时可不查。读取授权、taskState、签名ID、意见/动作、任务顺序、节点/边及日志来源继续原行为，不缓存到请求之外。

可以将该读取收为WorkflowOperationsQuery的一个小型私有方法，输入任务集合/处理人文本ID集合，输出当前姓名映射；锁、签署、责任变化和事务所有权不移出原服务。不为一个读取建跨域策略或全局名字缓存。将来复用普通表单详情时先核领域授权、来源版本和fallback，不能只因两处字段同名而共用。回滚范围限本小批读投影及其对应验证，不触碰历史记录。

目录方案：以现有Specification和排序直接取最多100条列表/受限查询，避免为Page请求未使用的total；需要在实际Spring Data版本中核API，再用原资格/分页边界和相邻回归验证，不预先新增EntityManager框架、配置或索引。两项可以分批独立回退，无业务政策选择。

以上均为待用户选择的整改建议，未实施。索引边界：既有用户主键无法消除1000次网络往返，文本ID转换的计划另需大分布EXPLAIN；本批没有新增索引证据，未加表达式或重复索引。单次本地耗时依赖缓存、执行顺序、虚拟化及连接，不用精确耗时阈值压测试。
