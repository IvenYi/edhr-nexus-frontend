## 开发时如何由 AI 引导

用户描述要开发的功能即可。开始或恢复相关任务时，主智能体按当前提交读取路线与契约，在同一任务中完成以下工作：

1. **判断是否适合试点。** 核对实际业务价值、已有能力、受影响知识 ID 和缺口。普通功能没有具体试点价值时正常开发，不强制引入 JSON-LD、SHACL 或规则引擎。
2. **给出范围和理由。** 区分语义基础、关系查询、历史解释、标准映射/约束验证和规则执行；说明这个切片解决什么问题、依赖什么、通过后能证明什么。
3. **维护分步计划。** 将最小业务边界、步骤、每步退出证据、回滚方式与下一步行动写入已有 `decisionPackage.ontologyRoadmap.pilotPlan`。用户不填写交接文件。
4. **按证据连续推进。** 先核实当前定义和样本，再实施对应资产、代码与验证。每步简述结果及下一步；在既有授权内继续工作，真正的业务歧义或产品取舍才请求决定。
5. **同步和验收。** 本体角色同步稳定定义、关系及来源，质量角色在交付时独立核对。完成一个局部试点不自动把整个 P0/P1/P2/P3 标成完成。

例如用户提出“继续完善表单流程版本引用与绑定”，AI 应先核对已有领域定义和试点，判断本次是补齐语义、验证标准映射，还是具备规则执行条件。不能仅因出现“表单”就自动加标准，也不能让用户先自行选择路线阶段。具体规则集合应从当前代码、已确认决策和真实使用场景中确定。

JSON-LD/SHACL 的小范围试点可以按明确用途在 P0/P1 实施，但其通过结论仅覆盖实际映射和约束验证。通用规则执行还需要事实来源、规则及目录版本、求值语义、权限、事务、业务动作、失败处理和审计依据；进入生产执行时按实际风险升级验证，并提前落实必要的不可变版本保障。

这一安排是 Agent 在开发任务中的行为契约，不是一个会自行监控所有开发者的后台服务。协作者或新会话需要获取并显式读取最新契约；同步与合并候选要求仍见 [AGENTS.md](../../AGENTS.md)。

## 全量审计具体核对什么

全量范围包含当前有效定义与其历史依据，不只检查最近改过的文件：

- 当前术语、概念、关系、事实、规则和执行契约是否表达一致含义，满足新契约的类型、引用、所有权、适用范围、执行边界及来源要求。
- 决策及声明是否存在部分替代、未同步定义或过期人员说明；历史条目保留原文和来源，明确当前适用内容。
- 实现锚点、原始代码、真实测试和证据是否支持相应声明；有文档或有链接不能替代实际核对。
- 问题、差异、场景与证据是否有明确关联；开放问题不自动变成已确认业务，旧成熟度不自动升级。
- Markdown 原始确认记录、调研依据、历史覆盖说明与 schema 是否和逐 ID 结论相符。

按业务域分批核对，但保持全量分母。优先覆盖投影、表单绑定、执行快照、生产阻断和审计；分别核对表单原始记录、流程工作数据、业务投影、追溯关系、DHR 证据与审计历史的职责、来源和版本边界，然后覆盖其余领域。未合并投影分支按自身提交与实际集成候选单独对账。

一条记录经核对后，按 [统一交接契约](../agents/agent-handoff-contract.md)记录结论：

| 结论 | 后续处置 |
|---|---|
| `consistent` | 保留适用范围、当前决策、实现或来源及实际验证证据 |
| `needs-fix` | 定位已确认错误与修复依据；修复后记录提交和复核结果 |
| `superseded` | 保留历史，明确被谁替代、替代哪些声明和范围 |
| `needs-decision` | 列明真实业务问题；只暂停依赖该问题的工作 |
| `evidence-gap` | 列明缺少的来源、实现或测试及其影响，不标成一致通过 |

`reviewed` 只表示已完成本条语义核对，不表示结论一致或问题已修复。报告要分别给出盘点数、已审数、待审数、结论分布、待修数、已关闭问题和实际运行验证范围。全部条目完成核对之前不能宣称全盘审计完成；完成核对后仍需说明未决和证据缺口，不能笼统宣称全盘符合。

## 如何分批续跑并保留进度

固定基线清单保持原样。实际开展语义审计后，将每批结果保存为 Git 版本化的 JSONL 记录，以 `id + auditedCommit` 定位，至少记下契约基线、语义结论、适用范围、原始证据、问题处置和运行验证范围；无 ID 的文件以 `sourcePath` 定位。初始清单的 `pending` 与已有结果合并后，才是当前进度。

换会话或执行环境时，AI 先读契约、基线清单及已有结果，按尚未核对的 ID 和待关闭问题继续，不要求用户重复整理项目背景。目标提交变化后，保留旧结果及来源，对新增、变化、删除和重新分配的 ID 建立增量映射；关联决策、代码或测试变化也可能使旧结论需要复核，不能只比较记录哈希。

语义修复以已确认依据为前提。对既有规则与代码不一致但业务意图不明的情况，记录 `needs-decision` 或 `evidence-gap`，不默认以代码行为改写业务规则。普通功能继续按影响范围增量维护，不因有全量审计计划而重审全仓或等待无关领域。

## 本切片验证与后续运行验证边界

本切片按 L1 交付，验证内容包括新旧声明同步、历史门禁口径、完整盘点与初始待审状态、正式知识模型校验，以及独立质量复核。使用已有知识模块：

```bash
mvn --batch-mode --no-transfer-progress --file tools/knowledge-model/pom.xml clean test
```

该命令检查知识结构与已有验证场景，不自动完成上述逐条语义对账，也不证明通用规则执行闭环。运行结果、本体角色结果和独立质量结论由本切片提交/PR 的交付说明记录；未经实际执行的浏览器、数据库或业务运行验证不能填为通过。

后续需要本地未推送代码、数据库、内网依赖或真实界面时，在能访问这些资源的执行环境中继续同一 Git 基线和审计记录。公开 GitHub 地址本身不提供本地环境；是否能修改、运行或提交取决于当前已授权的仓库连接与执行能力。
