## 5. 业务语义：必须保留的区分

### 5.1 六类记录不能混为一物

逐条核对并映射：**表单原始记录、流程工作数据、最终业务投影、追溯关系、DHR 证据、审计历史**。同一个字段值可能在多层出现，但来源、冻结时点、可修改范围和修订责任不相同。

不要把 `state_json` 的运行历史直接等同于独立 `audit_event`，也不要因为有 hash 就声称完整历史不可篡改或符合法规认证。必须查写入权限、事务、引用和读取路径。

### 5.2 已确认／已有验收支持的边界

| 事项 | 审查必须保护的含义 |
|---|---|
| 模板设计版本 | 显式选择的版本身份不能静默替换；缓存缺项、真实缺失、请求失败和业务失效是不同状态 |
| 失效版本 | 已失效但存在的 DHR 模板版本仍可设计；不能一概变成禁编辑或自动换版 |
| 使用侧版本 | 现行新增引用有效性校验与已有引用显示分开；失效提示不能自动扩大成“所有新批次禁止生成” |
| 历史冻结 | 按对象/动作确认何时冻结定义、目录、值及证据；模板变化不应无依据改写已冻结历史。不是“创建 DHR 后所有工作数据永远不变” |
| 引用字段 | 主表与当前子表行 dependencies 不混用；候选查询与已选事实分开。不能无业务依据增加“依赖变化就自动清空已选值” |
| 审批 | 配置主体解析、创建时候选来源、可执行候选、实际转办人分别建模；不能以修解析为由重建旧冻结候选 |
| 电子签名 | 普通按钮允许共享终端 A 会话/B 本人签署的既有边界，与本人 `SIGN_FIELD` 不同；以 DEC-0074/0058 等精确范围为准 |
| ID | Snowflake ID 在前端是字符串；不能转换为 Number 再比较、展示、传递或构造查询键 |
| 默认租户 | 当前 MVP 单租户边界保留，不自动启动完整多租户工程，也不放宽已存在的权限与范围过滤 |
| 未决数量下限 | `0<q<1` 是否允许仍按 open-questions 核定；不能用当前代码 `>0` 或旧记录 `>=1` 自行拍板 |

上述边界来自用户历史明确要求及仓库当前来源；执行时须取回原声明和适用范围，尤其是 DEC-0032、0060、0061、0067、0074、0075 及现行替代记录。[S05–S10]

### 5.3 每次冲突采用双向证据链

```text
原始业务确认 / 有效 DEC 声明 / 现行规则
  ↕
真实入口 → 参数 → 权限 → 服务/状态机 → 事务/持久化 → 历史读取
  ↕
测试断言、fixture 和本次实际运行结果
```

分类后再决定：

- **代码偏离明确规则**：修代码；测试若固化旧错误，同步纠正并保留原失败证据。
- **知识记录错误或落后于已确认变更**：更新受影响知识、说明替代范围；代码存在本身不是新规则的批准。
- **资料互相冲突或关键业务未决**：给用户具体操作场景、两种结果、影响和建议；只暂停依赖该决定的部分。
- **实现只是规划中的未来能力**：登记规划/缺口，不擅自扩建。
- **证据不足**：准确登记缺哪一段；不能标一致、也不能包装成已复现缺陷。

所有“符合”结论必须限定到实际审过的条件、入口及对象版本。

**W0 固定清单；W1–W5 按业务域完成语义和代码走查；W6 汇总并实施已确定的有限结构整改；W7 收束实际覆盖及验证。** 结构问题从 W0 开始扫描、每个域同步分析，不等到最后才发现。

每个工作包用“产物＋退出条件”结束，不用估计工时或主观百分比结束。无依赖包可并行；高风险发现立即形成小修复批次，不要求读完所有文件才修，也不因一个修复阻塞全部审查。

### W0｜基线、全量盘点与旧结论去重

实际执行：核对 origin/edhr-dev、合并链、当前工作树；读取契约；用 Git 跟踪文件枚举全部源码、测试、配置和知识；逐个标明归属、类型、是否当前入口、审查深度及排除依据。枚举路由、HTTP入口、后台/定时入口、数据库迁移、关键状态机及有效知识 ID。导入原内审清单和本包初始线索，标明当前待核对。

测试环境只建立一次可复用清单：Node/锁文件、Java21/Maven、PostgreSQL、字体、Playwright、文件存储路径、测试依赖和正常启动命令。记录环境失败与产品失败；不要一上来重做所有旧验收。

产物：`baseline.json`、`coverage.csv`、`ontology-coverage.csv`、`findings.yaml` 初始账本、`NEXT.md`。

退出：当前审查分母明确；所有路径已归类或有待解释项；已合并问题与新待审项分开。清单生成不是语义审查完成。

### W1｜DHR 与记录生命周期

覆盖模板/版本/目录/引用 → 制程绑定 → 工单/对象创建 → 首次 START → 执行/表单记录 → 生产完成/提前结束 → 汇总审核/放行/归档 → 历史读取。

逐对象回答：何时创建，身份和来源在哪里，哪些定义冻结、哪些值仍可变，谁有权变更，失败能否部分写入，查询读当前数据还是相应历史版本。读取、写入、修订和投影要连成链。重点核对 F004、工单关闭审计原子性、历史快照与目录变更、资料齐套和生产完成是否混同。

代码入口线索：`DhrInstanceService`、`ExecutionSnapshotBuilder`、`ProductionExecutionService`、`FormInstanceRecordService`、`DhrSummaryService`、`DhrReviewService`、模板工作区及历史查看页面。以当前 tree 搜索确认路径。

产物：逐对象生命周期矩阵、至少一条完整创建/冻结/历史读取链的源码映射、确认发现/反证/待决清单、对应修复与回归（有明确缺陷时）。

退出：所有本包对象的入口、状态、快照、写入与读取责任已经核对；未实现规划和未决政策单独登记，不能用一个 PDF 或一个样本代表所有历史链。

### W2｜表单建模、设计器、引用与追溯/投影

覆盖字段类型、模型/画布/运行渲染契约、主表与动态行、校验、导入、撤销、草稿、保存、绑定升级、DIRECT/PROCESS、引用候选和已选值。核对数据字段到追溯关系、统计/业务投影的已有实现，缺失的未来报表能力仅登记，不自动建设新平台。

优先核对缺失 fillMode、旧权限例外、共享渲染器对业务页面反向依赖。测试必须覆盖实际入口适配，不能仅以共享组件测试替代页面集成。

产物：字段/表单入口契约矩阵；缺陷及结构提取建议；保存/载入/序列化/撤销和异常恢复的代表性回归。

### W3｜作业/审批流程、身份权限、签署与记录控制

覆盖 WORK、FORM_PROCESS、通用审批各自的定义/版本/节点/条件/任务推进；USER/ROLE/DEPARTMENT、字段 READ_ONLY、冻结候选、转办、已办、会话与实际操作者、签署人和审计人。核对记录更正/作废与原表单/DHR的关系，不把已计划但未确认的管理员重新分配规则直接实现。

优先核对候选来源被转办覆盖、条件旧字段保存/发布、当前实际受限求值器与知识声明边界。已合并身份和引用回归按影响复用；发现授权旁路或证据归属错误才提升新风险。

产物：角色/动作/数据范围矩阵、状态机边界、主体和审计数据链；必要反向、幂等、并发、失败无写入验证。

### W4｜主数据、产品/产品簇制程与生产编排

覆盖产品、产品簇、物料、工序/路线、设备、文档、工厂/车间/产线等实际存在模块；分类、CRUD、版本引用、生失效、删除保护、导入导出；工单拆分、SN/批次、对象上下文、产出统计和跨时点变更。

优先核对产品簇转移对旧对象影响、SN 模板差异、数量未决范围、删除关系与 JSON/外键引用、事务锁顺序与并发。旧表/字段对齐已修，不能重加旧字段；同时不能因一次新库通过就宣称所有旧库迁移通过。

产物：模块/接口与关系矩阵，导入导出及生命周期错误，必要修复、数据库一致性与故障回滚回归。

### W5｜跨域工程、安全、性能及运维可用性

遍历尚未分配的 API、存储、错误处理、日志、上传/下载/预览、共享缓存、分页、大查询、批量导入导出、资源清理、依赖与部署配置。静态检查凭据泄露风险、参数化 SQL、ID 精度、访问范围、上传类型/路径、资源上限和敏感日志。查明实际授权再判越权，不能只看按钮。

性能问题必须有路径和规模条件；能测则给代表性负载/查询证据，不能只写“可能慢”。字体/浏览器作为已有部署前置继承，除非当前场景变化，不再把环境安装变成新的无限主线。依赖缺陷核对锁定版本和实际可达性，不能只按声明的版本范围或扫描器数量判定。

产物：剩余代码覆盖、跨域风险、瓶颈、环境与测试维护清单；已选必要整改。

### W6｜结构审查收束与小批重构

汇总各域模块长度、函数跨度、嵌套/分支、依赖循环、重复实现、状态所有权和修改影响。逐项给出“拆哪里、移到哪里、输入输出、哪些测试保护、预期收益、依赖和回滚”。

顺序优先：纯转换/校验函数 → 稳定组件/查询适配层 → 状态与命令职责 → 控制器/服务边界。具体选择以根因和风险为准，不照顺序机械拆分。

结构检查必须具体：不能将 5,000 行页面搬进 5,000 行 hook；不能为了复用造万能配置框架；不能让一次画布操作变成多个撤销步骤；不能改变版本解析、字段 ID、快照序列化、审计事务和接口响应。纯样式/命名偏好不冒充缺陷。

产物：`refactor-plan.md` 与必要的独立重构 PR。未承诺实施的可选拆分给出明确暂缓理由，不以“全部文件小于N行”作为完成标准。

### W7｜覆盖复核、集成回归与最终交付

复核所有在范围内路径和有效知识条目，无静默遗漏；追踪新 baseline 与审查起点差异，对受影响链路增量检查。对选定修复的真实合并候选运行适用综合验证，检查知识声明、迁移、测试和实际实现的一致性。

产物：完整审查报告、最终覆盖/语义账本、发现与修复映射、独立结果、测试去重摘要、剩余风险与业务问题、明确未实施范围。

退出不是“全部场景都测试了”，而是达到第12节明确承诺的完成标准。

## 8. 发现、整改与证据标准

### 8.1 发现的最小记录

每条必须有：唯一 ID、实际 base/head、领域、严重程度与置信度、有效业务依据、具体文件/函数/行范围、触发条件、预期/实际、影响、已检查的反证、当前验证层级、最小修复建议、验收标准和处置负责人。

必须区分：代码缺陷、知识冲突/过期、测试错误、运行环境、结构建议、未来功能、业务未决和证据缺口。严重程度与证实程度分开；“后果可能严重”不是“已经证实”。

证明途径可以是完整静态路径、失败测试或真实运行；不要求所有 bug 都用浏览器复现。但报告必须写明实际使用哪种证据，不能把 stub/mock 叫真实后端、把方法探针叫完整编译、把代码中的测试断言叫本次运行通过。

### 8.2 实施时的闭环

```text
核对有效规则与完整调用链
→ 确定缺陷及影响
→ 建立能识别旧缺陷的回归（可行时先红后绿）
→ 最小代码/知识修改
→ 实现者测试
→ 本体同步（触发时）
→ 独立质量验证
→ 新提交/PR/证据关联
```

发现测试失败先区分产品错误、过时 fixture、断言表达问题和依赖问题。可以纠正测试错误，但不得删除原业务断言或扩大容差只为通过；解释正确的新前置，并尽量增加不合法前置仍应被拒绝的反向测试。

### 8.3 分支与提交

从核对后的 `edhr-dev` 创建新审查工作分支；旧 PR5/6 仅引用。业务缺陷、知识同步、结构重构分别保持清楚的批次，必要的同功能代码/知识可以同切片提交。每个提交尽量可构建、可验证；不得强推重写共享历史，不把用户无关改动清理掉。

对已经发布的变更采用新 revert/前向修复，不暗中重写历史。数据库写入、迁移和审计不会随代码 revert 自动消失，单独评估。

### 8.4 运行安全

只能在核对过的隔离测试环境执行写入、迁移和破坏性测试；先读测试对数据库的影响，再指定专用库。不得把历史的精确测试对象删除授权扩展到其他环境或真实数据。

禁止在交付包中包含 token、密码、Maven settings、浏览器 profile、数据库目录、真实证件或字体文件。允许输出已脱敏的请求 ID、操作者标识、命令、日志摘要和合成样本。

用户之前要求不使用 GitHub Actions。最终 PR 描述中存在已执行 CI 的历史说明，不等于本次获得新的 Actions 授权。接手时尊重用户在 Codex 会话的最新明确权限；没有新授权时不触发、查询或新增 Actions，不改保护规则，使用本地/云工作区验证。此交接不对用户已完成的历史 CI 行为重新裁决。

## 9. 验证设计：预先约定范围，避免再次循环

每个修复批次开始时由 Codex 主实例固定一份有限验收矩阵：风险/规则、入口、验证层级、required 理由、证据、阻塞范围。质量实例核对其充分性；只有新代码/新证据暴露实质风险时才增项，并说明增项原因，不能不断添加无关发布条件。

| 变更风险 | 默认匹配证据，不是每批强制全套 |
|---|---|
| 文档导航、非业务静态文案 | 链接/内容/范围检查；不跑全系统 |
| 纯函数、序列化、状态派生 | 单元边界、反向控制、必要类型/构建 |
| 页面适配、身份和复杂交互 | 真实组件/请求适配检查＋受影响实际入口；UI端与服务端权限分别验证 |
| 数据写入、生命周期、权限、签署、迁移 | 服务/HTTP集成、真实数据库的关键约束/原子性；适用真实用户流程及独立验证 |
| 跨模块重构/最终候选 | 直接与传递影响回归、综合构建、适用全量及已选E2E |

现有可用命令入口包括 `npm run test:review-batch-01`、`npm run build`、`npm run verify:dhr-template-workspace`；实际更多脚本以当前 package.json 为准，不假设存在 `npm test`。后端 `mvn test` 会依赖生成前端 DHR 打印资源等前置，先读 pom/runner；`-DskipTests package` 只算构建。知识校验入口在 `tools/knowledge-model`，不要改校验器来迁就错误知识。[S11]

全量运行不是每个小修改都重跑。记录唯一 testcase、执行轮次、覆盖范围、失败/错误/跳过；相关聚焦测试与全量重叠时不相加。条件等待夹具的 JUnit 绿不代表人工 UI 通过。

### 受限项的处理规则

- **可定位环境问题**：作一次有限排查和明确恢复方案；仍不通则保留限制，继续不受影响审查。
- **同树/同契约旧证据**：记录对应 SHA/tree、输入、依赖及受影响边界，按具体风险说明可复用之处。
- **等价证据**：Codex 主实例说明风险、分支输入、组合覆盖与未覆盖项；独立质量实例核对。不得只写“成本高，接受”。
- **真实业务歧义/重大风险接受**：直接集中向用户提出，不能交回原 ChatGPT。
- **门禁仍 blocked**：不宣称对应切片已通过，但也不把它变成整个审查无法继续的理由。范围缩减需要相应授权，不偷偷变更 required。

旧 PR 通过证据不覆盖新分支所有场景；新的全分支审查也不应把既有有限合并验收追溯改成“当初不允许合并”。

## 10. Codex 的职责与独立性

Codex 主实例承担真正的主审与实施：亲自读关键源码和原始依据、定缺陷、写修复、处理证据层级及最终技术结论。不得只把报告转发给另一角色，让用户循环问“下一步”。

按照仓库契约使用 `business-knowledge-modeler` 与 `quality-verifier` 的真实专业实例。知识实例处理稳定规则的受影响资产；质量实例不修改待验代码、测试或 fixture。L2 的高风险修复按契约使用未参与修复的全新质量实例。所有调度结果需实际返回；创建了实例不算验收完成。[S12–S14]

若当前环境不支持真实专业调度，不冒充“独立复核”，不把普通新聊天自动当成合格子实例。主实例继续能做的审查、实现和测试，报告准确受限环节；需要更换执行环境时在 Codex 体系内一次性解决，不能又要求用户充当转发员。不能暗改仓库契约解除质量要求。

技术取舍由 Codex 主实例负责，产品政策由用户负责。已经存在明确业务决定的问题，不重复向用户索要同一个确认。

建议维护仓库内 `docs/development/branch-review-20261014/`；若已有同功能目录，复用，不再造第二套体系。本包模板是起点，不是新的质量协议。

### 报告四条进度，不合成虚假总百分比

1. **盘点覆盖**：已分类路径 / 当前 Git 跟踪范围；排除项及理由另列。
2. **源码审查**：完成路径/模块或链路 / 已定分母，注明结构扫描、完整阅读、调用链、运行验证等深度。仅搜索不计深入审查。
3. **语义核对**：已审读知识数、已有源码映射数、一致/冲突/待决/证据不足分别计数；不可把 evidence-gap 算一致。
4. **整改关闭**：本轮选定问题中已修、已验证、已合并、受阻、批准暂缓分别计数。测试通过率不是代码审查完成率。

基线变化后记录 added/changed/removed 与影响范围；不能靠移除未审模块让分母变小。没有分母时写“尚未完成盘点，不能估算百分比”。

每个检查点报告只需：实际读了哪些模块、确认了什么、改了什么、运行了什么、还缺什么、下一项动作是什么。若没有新读取/变更/验证，不能称本轮取得审计进展。

## 12. 完成标准与停止条件

**审查覆盖完成**与**整改/发布就绪**分别给结论：

### 12.1 本次整体审查可以交卷的条件

- 固定基线的全部在范围路径及当前有效知识资产已归类，有可追溯处理状态，没有静默漏项。
- 每条关键业务链都有规则、入口、状态、写入、历史读取、权限/事务和测试映射；真实证据不足明确标出，不能写成已证实一致。
- 每个确认发现都有证据、优先级、处置、相关提交/知识 ID 和验证状态；历史已修项不重复报为当前缺陷。
- 大模块给出当前测量、具体职责边界、提取接口、风险、收益、优先顺序与验收条件，不止是一张行数排行榜。
- 未实现的未来能力、用户待决项、环境缺口、已接受限制和可选优化分别列出。
- 独立质量实例核对覆盖与证据真实性；不能以脚本盘点或 schema 通过替代人工语义审阅。
