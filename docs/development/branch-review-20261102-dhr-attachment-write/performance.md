本批只观测，未修改下载实现、校验、SQL或索引。原始capacity.json、JFR、逐组reads.json、命令/XML/日志以证据清单为准。

单独1项JUnit测试包含12组、84请求；不是84个独立业务用例。每个有效请求完整输出52428800字节并重核SHA256；所有损坏请求均在获得响应体之前抛出原摘要错误。

环境与限制：原生PG16.15/en_US.utf8、自有loopback库，实际Spring service proxy与进程内Controller/FileSystemResource，四张canonical表加手工版本元数据；并非完整DHR冻结流程、真实HTTP/网络/身份授权或浏览器。2GiB测试JVM、暖文件页缓存和稀疏paddedPNG（非完全预热JIT）；16个worker受Hikari默认10连接池制约。64KiB输出校验缓冲，JDBC/断言/JFR和采样有开销。JFR是Java文件路径的逻辑读取，不是物理磁盘吞吐；分配和采样heap不含直接内存/RSS/网络，也不能据单批耗时定生产SLA或线性峰值。

建议下一批先固定缓冲区流式计算完整SHA256，比较通过后再返回资源，保持两遍逻辑读取和当前坏文件拒绝时点；先减少随文件大小增长的堆分配。用户已收到具体观测与下一批选择题，当前仅建议、未实施，不把未答复当批准。元数据上下文复用需另核重复资格读取和并发变化，不能简单删除ensureDhr、摘要或冻结成员校验。无需由本观测直接新增索引。

只有大文件/并发下载才会放大该风险，DHR内表单数量不是这里内存开销的直接尺度。普通小附件占用更低；当前证据不足以承诺任何生产并发上限。
