# 容量、结构与工具边界

首轮独立failed后的并发增量：固定ID排序写锁与改名单行写锁用于保证前值新鲜和避免跨写链字段覆盖，沿原命令事务持有；不是新增性能优化。普通列表和他租户不锁。当前事务还包含既有返回分类聚合，因此大C/D可能扩大持锁与等待时间，需量化讨论，不能以性能理由移出正确性事务或删锁。控制器/仓储仍各司其职，不引入版本列、冲突UI或通用锁框架；三并发组合为有限验证，不冒称所有并发和生产SLA。

增长源仍是分类C、文档D、每文档版本V与历史审计E。本轮排序变化必须按真实对象写不可变证据，不能把必要的每对象审计写入当应删除的N+1。新增原值map在一次已读分类集合上构建，差量快照只含排序；未调用countDocumentsByCategory来填无关数量，未新增逐分类文档SELECT。读返回仍沿原分类聚合；没有新索引/缓存/分页协议或生产容量承诺。

分类改名/空分类删除的countDocumentsByCategory仍findAll后计数，详情逐文件及删除逐版本引用查询等上一批候选保持；本轮移除不可达文档迁移分支不是实施其余性能方案。真实删除保护会沿关系图查下游和锁定目标；未测大D/V时延、堆/GC、复杂引用图与全部并发，不能仅凭本次小合法夹具给容量结论。

具体结构方案继续沿已有所有权：`DocumentAuditSnapshotFactory`接收既有分类名/文件元数据并纯投影，不内部查库；`DocumentCategoryCommandService`如后续确需抽取，应拥有原分类命令事务/每对象审计，与删除Aspect和数据库FK共同保留校验覆盖。Controller保留传输，不能把整文件搬到同体积service；不反向依赖Controller DTO，不新增跨请求缓存。保护测试为原生引用阻断/无引用删除/预检后新增/排序差量与审计失败回滚、既有JWT矩阵和浏览器取消/反馈。按单命令委托分步回滚，无现实复用收益时保留局部实现即可。

UI能力映射：列表/弹窗规范与DESIGN提供维护等价契约；ConfirmDialog→AppDialog拥有预检/取消/焦点，DeletionProtectionDialog拥有阻断清单，SnackbarProvider拥有反馈，页面只提供正确对象及结果文字。中文工业管理场景，无新增日本市场/locale契约、控件、导航、token或通用UX文件。源组件和设备分类兄弟确认都沿共享owner。新提示不引入技术解释。
