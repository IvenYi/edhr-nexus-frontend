# 记录控制申请列表：数据库内部重复扫描

**待讨论，未实施 SQL、索引或权限更改。** 用户已要求性能问题先量化再讨论；本轮实际提问仍未得到答复。此前成员预校验、姓名批读等批准不自动覆盖这个消费者。

用户进入记录控制“变更记录”列表，每页默认展示 20 条时，后端同时计算每条的“是否可查看详情”。申请人和真正系统管理员可直接满足条件；审批人需检查自己是否关联该申请的流程任务。当前把 `workflow_task.instance_id` 的 bigint 转成文本，与申请保存的文本流程 ID 比较。已有普通 bigint 索引不能直接满足这个转型表达式的查找。

它不是 20 次接口查询：应用实际只发 count/page 两条业务 SELECT。但数据库在 page SELECT 内，可能为每个申请再扫描任务表。长时间积累的其他流程任务也会影响这项读取，不能只按一份 DHR 内的表单数量估计。

## 实际证据

自己的 canonical PG16，真实迁移至 0092；调用原 Service SQL，auto_explain JSON，非手写等价 SQL。每档 20 份合成元数据申请、原真实签署申请 1 份，背景任务先入堆、目标 20 任务后入。4 角色 × 3 档，共 12 观察、24 实际查询计划。修正后的主侧结果：

| 背景任务 | 审批人 42 task loops | 每 loop 平均过滤行 | page SQL 本机耗时 |
| --- | ---: | ---: | ---: |
| 0 | 20 | 10 | 0.175 ms |
| 5,000 | 20 | 5,010 | 14.316 ms |
| 20,000 | 20 | 20,010 | 70.223 ms |

2 万档约检查 40 万行；业务 count/page 仍为 2 条。无资格的 44 在这组数据中选择 hashed subplan，扫描 20,021 行一次（9.871 ms）；申请人 41 与超管 1 的任务子计划不执行。不能概括为所有人都扫描 20 次。全新独立 v2 的时间另见其正式报告，结构应优先于单次耗时比较。

早命中旧布局的 2 万档很快（约 0.342 ms），说明物理布局和命中位置影响很大，不表示新代码已优化。原 retry/verified 含错误业务字段，保留但不作为修正后的关联完整性验收；最终计划来自修正字节。

这些是热缓存、本机、带计划采集开销的合成实验，不是生产页面耗时或 SLA；20 份克隆不是 20 个新签署完整业务流程。线程分配数据是调用线程累计分配，不是进程峰值。读操作前后八表摘要相等断言实际执行通过，测量标签下没有 DML；不虚构未输出的摘要字符串。

## 建议下一批方案和索引边界

建议先保留筛选、排序、总数和当前页，只对本页相关流程批量核对资格，避免反复检查无关任务。详情接口仍实时重新判断；列表所有满足条件的记录仍能逐页访问，无 100/200 总量截断。优先保持单语句一致视图和普通资格谓词单一来源，不新增跨请求权限缓存。

必须验证文本 ID 与 bigint 的当前精确比较语义：不能简单把任意旧文本转 bigint，让 `01`、空白、非法内容等变成另一种授权关系。投影与真实详情、终态、当前候选、历史处理人、转办前后、未受保护 ADMIN/停用账号、真实超管矩阵需维持。新增元数据复用也不能绕过真实状态复核。

已有 `idx_wf_task_instance(instance_id)` 及状态/人员/候选索引。先比较页相关 set-based 形状和现有索引的真实 prepared 计划；只有新形状仍证实瓶颈，再评估表达式/组合索引的收益、写入/存储成本、统计与 legacy 文本语义。不自动添加索引，不全表搬到内存，不为减少查询数改变权限、分页或签署规则。

成功标准：同一 fixture 的全部字段、总数、排序和资格一致；4 角色与早/晚命中、多档背景分布均量化；页相关工作量有界或全表检查次数受控，记录参数规模/内存/实际计划；读取不写审计/历史。先取得用户方案答复，再新分支小批实现与独立复验。
