## 真实问题及局部修复

`W3-RECORD-CONFIRMATION-FEEDBACK-001`，medium，承接上批`residual.record-candidate-error-presentation`，不是PR76新引入或第二次记作独立新缺陷。错误Alert在页面层，Modal打开后该层aria-hidden；候选失败还与空数组混淆，且openConfirmation清除通用error会丢掉此前候选失败。最终提交返回错误时同一页面Alert也不可在Dialog内读取。

修复采用已有MUI Alert、Dialog及相邻RecordApprovalDetailPage的Dialog内actionError模式：候选失败独立状态，在换来源/模式时清理，过期effect仍不写入；有错误先显示错误而非“暂无流程”。普通error在Dialog打开时显示于Dialog，关闭时仍显示于页面。未引入另一套弹窗、缓存、重试或验证框架。

| 场景 | 实际覆盖 |
| --- | --- |
| 候选错误在打开前/后发生 | Dialog内可访问alert；之前页面可读取的错误不被打开动作清除；禁止提交，不显示真实空态。 |
| 关闭重开 | 错误仍可读；候选调用次数保持1，无静默重试。 |
| 取消后重新选模式 | 旧错误清除，新的pending不冒充空态；成功后仍须明确选择匹配版本。 |
| 当前POST错误 | Dialog内alert，当前原因/版本及原内存字段不变，来源/修订/明确版本payload正确，仅一个合成POST。 |
| 旧成功/错误/finally及IME/草稿 | 原26场景继续；当前34中保留全部原断言，增加8场景并加强当前错误可访问树与空态断言。 |
| 相邻资格入口 | 原58浏览器场景实际回归，不由新34替代。 |

错误按原服务信息呈现，不宣称真实网络错误后一定未写入或可安全自动重试；未改变原幂等键、签署或密码清理。密码输入断言只是记录控制旧页面内存行为保持，不能从DEC0074“保留表单输入”推导新的凭证存储/长期保留政策。
