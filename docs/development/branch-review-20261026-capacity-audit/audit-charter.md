依据：用户2026-10-26明确要求本次审计不限功能bug及其举例，补齐健壮性、性能和结构审查；新增代码及时增量核对；先判断哪些模块可能有大量数据，再评估风险，性能问题先提出共同讨论，可先不改。本文是本次审计的执行与交付记录，不改变AGENTS/角色契约或产品业务规则。

## 1. 固定总目标与边界

审计edhr-dev当前代码、当前有效知识及必要历史替代链。输出分别包括盘点、实际源码/语义核对、功能缺陷、性能/容量风险、结构建议、测试/环境问题、明确未决/暂缓及最终独立验收；不以PR数量、bug数量、行数降低或schema通过代替完成。

范围包括前后端入口、服务/工具/组件、任务/异步消费者、存储/SQL/初始化/迁移、权限/身份/文件边界、测试/构建/依赖/部署配置、结构化知识和无ID的Markdown原始依据。二进制、生成物、历史证据和第三方缓存仍登记其归属及排除深审理由；跟踪路径数不是业务代码审查分母。新增功能开发、大模块全量重写、业务政策重定、生产合并/部署/数据恢复不在此授权内。

TaskDetail任务处理页/签名密码按用户要求暂缓交其协作者检查；记录控制变更/作废及依赖它的两DHR high/A12保持原暂缓。已有合法后端读取和无依赖审查继续，不以暂缓隐藏未完成，也不以用户说“继续”自动恢复暂缓页整改。

## 4. 新提交的增量审计协议

1. 每次开始/恢复、切换领域或准备独立候选/PR前，显式fetch edhr-dev，记录fullSHA、时间和上次基线。长批次在完成一条主要链/进入下一子批时再检查；收到用户提交提示立即检查。及时检查指活跃任务检查点，不声称未运行时后台持续监听。
2. 对新增/修改/删除/重命名路径分类，优先读取AGENTS/codeplz/角色/交接/架构/知识增量；fetch不等于checkout或角色上下文更新，安全检查点明确同步工作树及通知实际角色。
3. 追直接和必要传递影响：API/DTO/全局错误、schema/查询/索引、权限/缓存、共享组件/codec、业务声明/替代链、执行快照、审计/签名/文件。自动依赖/路径搜索仅候选；记录依据、不能确认的范围和误报。
4. 旧blob相同只保留同一有限范围的历史证据；文件或列明依赖变化先needs-delta，再按方法/声明对照缩小复核。新增路径/知识默认pending；删除/重命名追实际消费者和历史引用，不能静默丢出分母。知识版本号相同不表示内容相同。
5. 共用分支只普通合并或独立候选，不强推。目标变化实质影响本片时整合双方代码并重跑适用检查；不相关文档变化说明依据即可。独立质量接收实际新候选，不拿旧passed盖新组合。
6. 保存旧清单/原件/失败和验收overlay；当前目录注明固定快照而非永远最新。每批登记base/feature/tested/delivery/merge的区别。新增性能/结构发现与原bug去重，避免同一风险拆成多个修复成绩。

## 5. 先建立数据增长模型，再评价危险

逐域区分存量/活跃/单对象峰值/历史累积/并发请求/文件字节；明确增长源、生命周期、归档/删除是否真实实现、受影响API、每请求加载/排序/校验范围，以及已有限制。不得默认主数据永远小，也不默认所有对象会到百万条。模型和合成场景见[data-growth-model.yaml](data-growth-model.yaml)。

规模证据从可靠的行数、实体加载量、应用SQL调用数、读取字节、CPU/内存算法和执行计划开始；时延/堆峰值若未测不得猜。必要时在自建隔离库用多规模对照，测试大小不等于客户真实数据/SLA。耗时受热身、缓存、硬件/索引/并发影响，单请求耗时不能作为生产容量或p95认证。

重点区分：查询结果有LIMIT不代表数据库扫描有界；请求返回5条不代表仅加载5条；一条SQL的相关子查询不等于客户端N+1；JPA一层缓存可能减少某些find，必须查反证；saveAll不保证驱动批量；存在上下文不代表可信/够新，可以删除锁内校验。

## 6. 发现与讨论、修改边界

发现分functional-defect/performance-risk/structural-opportunity/knowledge-mismatch/test-fixture/environment/evidence-gap/business-question，严重性与证实程度分开。性能记录必须有路径、合法触发、增长变量、已证机制、实际观测/静态模型、反证、未证后果、影响范围和至少一个不改变业务的候选方案及代价。

性能状态为candidate → source-confirmed或runtime-observed → pending-discussion → agreed-action/deferred → implemented → independently-verified；讨论前不改查询、索引、分页协议、缓存、写批处理或容量限制，不把讨论中风险改为resolved。先提供可审阅证据，再询问确实影响产品结果的取舍；不要求用户填台账或在角色间传话。

实际critical/high安全/数据完整性缺陷不因“仅性能”而淡化，立即报告实际证据并按已授权缺陷流程处理；不能凭假想大数据OOM就定critical/high。保留权威资格/租户/候选、稳定排序、每次动作审计、签署/原件校验、锁/事务、冻结身份及历史解释；性能改善不能靠删除这些业务职责。

结构建议必须具体说明源职责/目标模块/接口与状态所有权/保护测试/收益/依赖/回滚。以真实可维护性风险或根因为选择依据，不为行数强制拆，不能把5000行页面搬到5000行hook，也不扩成通用框架或新业务能力。

## 7. 每批交付与防漂移检查

开始列范围、已知/待决、选中入口、为何当前优先、未审项目、预计证据。结束分别核对实际base/head、代码/知识/结构/性能发现、真实执行和未执行、当前全量与增量待审、用户暂缓和后续。全量分母不清不给整体百分比；盘点、语义核对、修复和运行验证不混为一列。

实现类批次按门禁取得本体/独立质量正式FINAL；纯分析批次的质量结论只认证审查与证据交付范围，不认证产品已无风险/可承载某容量。所有正式角色FINAL后才结束，准备PR时先实际向用户汇报范围/进度有无漂移。既有性能问题保持开放待讨论，不能为了quality绿改业务或把本批称全审完成。

最终W7退出：所有在范围内入口/有效知识/Markdown来源都有实际审查或有依据的明确例外；新提交/传递影响已处理；确认缺陷有真实处置，性能和结构建议有方案/讨论状态/未实施原因；适用运行/迁移/失败/并发/集成验证与独立结果可复核。用户暂缓/业务待决/证据缺口单列，不算一致通过；不能以“每种场景全部测试”作空泛承诺。
