# eDHR 自主查知识表单 Agent：第二轮可行性验证

日期：2026-11-12。执行级别 L2。范围为内部实验脚本与独立数据库，不开发产品页面，不发布生产 Agent。

## 结论

**“Agent 自主查本体、查关系和业务目录，再直接操作表单模板”已跑通；“只问少量必要问题，自动交付业务正确、版式合格的完整模板”尚未通过。** 下一步应先补语义检查、客户实施上下文和视觉反馈，再开发全局入口。

两种模型均通过实际工具创建、保存并读回三张安速康表单，各重复两次，共 12 个独立任务。OpenAI 本轮字段覆盖和查询行为较稳定，问题较少；DeepSeek 成本较低，但出现漏日期、误解追溯复用约束和一边提问一边按未决含义写入的问题。OpenAI 也有批号含义跨次不一致、旧引用入口和未经明确依据选用签名字段的问题。不能将任一模型直接视为可托管实施人员。

以上是小样本工程诊断，不是统计意义上的模型排名，也不证明知识检索本身带来多少提升：本轮相对第一轮同时改变了布局适配、工具和模型执行方式，未做仅替换检索方式的消融实验。

## 基线与方法

- 功能分支：`codex/ai-experiments`；实验源码/知识基线提交 `fb99234167f526e7f4cc79381af4fb0a77e3c169`。目标 `edhr-dev` 已获取核对至 `3ae01d53dda205de277f4aa09b92fbbb9a337468`。知识模型版本 0.3.25；本轮不修改权威知识或提升成熟度。
- 原件为《刀头生产记录－末道清洁》《标签和说明书打印及领用记录》《报废处理单》。复用第一轮空白脱敏 Excel 的确定性导入：文字、坐标、尺寸和合并区域。原文件与导入摘要在第一轮 manifest 中；未上传生产记录或人员填写值。
- Agent 自行检索 260 个 Git 跟踪 YAML 文件中的 2,849 个 ID 记录，及 6,399 条显式引用/概念关系边。包含未决问题、来源位置、文件摘要、状态、可见性与父决策。它不是 RDF 推理器，也不是已发布的客户知识服务；Markdown 说明、所有源码、附件原件及完整租户事实均未纳入模型工具。
- 初始指令只给通用目标、工具和边界，不给人工挑选的任务规则包、标准配置、旧模型输出或评估答案。搜索是简单关键词检索；模型按需读取记录、查图、查现有用途/追溯目录和引用候选。
- 使用 `deepseek-flash` 与 `gpt-6.1-sol`，均为 `high` 推理、最多 26 轮，每请求最多 20,000 输出 token。两模型工具定义、原表、知识快照和任务相同。供应商模型及接口不同，不能把 reasoning 档位相同解释为内部计算量相同。
- 后端 `127.0.0.1:18092`，独立库 `edhr_ai_agent_20261112_b`；既有前端 `127.0.0.1:15174` 仅用于观察。所有模型写入限于会话创建的模板，不向模型开放任意 HTTP、SQL、文件或 shell。
- 每次任务独立，不继承其他任务已经提出的问题。因此下文累计问题数不是实际客户最终必须回答的问题数；共享实施政策建立后可避免跨表重复询问。

## 配置质量与提问质量

### 可以成立的能力

1. 两模型都能自行找到相关知识和运行目录，形成现有模型/画布格式，写入真实主数据并读回。没有新增“应用到模板”步骤，也没有模拟保存成功。
2. 标签表四个重复记录块和八个留样附件位置均覆盖。静态纸面版本和原文保留，不把预印设备值“无”强行改成输入。
3. OpenAI 两次均为四个物料字段分别关联同一“物料编码”追溯项，符合当前一字段最多一项、同一项可跨字段复用的规则。
4. 两模型后续改名复测均能只修改 NCR 字段名称；其他字段、位置、用途、流程经完整对象比较保持一致。这验证的是绑定目标后的连续编辑动作，不是长期会话记忆或多人协作。

### 真实缺少的实施政策

OpenAI 六次均询问表单是否承担正式统计来源，分别涉及报工、消耗、报废。隔离库没有现场生产上下文、原实施映射或同业务其他来源关系，知识也不能替客户决定。模型因此保留字段、暂缓正式统计绑定。这是合理暂缓，不能因评分中的 `coreBinding=false` 就判为错误；同样，DeepSeek 更早写入绑定也不自动代表更好。

原件的“批号”可能指内部物料批号、供应商批号或生产对象；多日期表需要确定哪一日期供追溯。此类问题影响真正业务含义，应先查客户实施知识，查不到再询问。批号不能仅按字段名相似度决定。

当前知识解释“产品允许什么、如何配置”；它并不包含每个客户“这张表在这条工序中承担什么职责”。少问客户需要补齐这一层，并让 Agent 查询真实关联对象和已确认政策。此次 `template_relations` 只查会话模板、版本、字段和用途，不是全产品实例图遍历。

### 已发现的配置缺陷

- **DeepSeek 错误解释追溯约束。** 标签第一次认为四个字段不能共用“物料编码”，于是提问并漏配。`DEC-0077-42` 和 `rule.form-projection.trace-field-single-binding` 明确允许同一项在不同字段复用。知识已存在，应该自行查证解决。
- **DeepSeek 把明确日期变为待问事项。** 报废第二次漏四个日期，且 `incomplete` 使用“原表没有独立业务日期控件”的解释，混淆纸面标签和已生成控件。属于缺失，不是正常澄清。
- **未决含义已经写入。** DeepSeek 两次报废均询问批号含义，同时已写入 `scrap.materialLotText` 和追溯绑定。第二次还询问 NCR 是否作为关联单据号，却已绑定。标签第二次询问人员栏是否需要电子签名，同时已默认改为签名字段。“已经问了”不能替代暂缓对应动作。
- **OpenAI 也有语义波动。** 清洁第一次暂缓酒精批号追溯、第二次直接绑定内部物料批号；报废第一次暂缓批号含义、第二次直接绑定内部物料批号。不能把某一次较谨慎的行为当作稳定保证。
- **两模型都未稳定遵循新的统一引用入口。** 两次 DeepSeek 清洁及第一次 OpenAI 清洁仍创建 `sourceType: product`；当前 `DEC-0082-15` 指向 `material + referenceMaterialScope: product`。后端兼容接收旧值，不等于新配置符合当前政策。
- **人员引用与签名不稳定。** DeepSeek 标签第一次用人员引用、第二次用签名；OpenAI 使用签名。原件没有为每类人员栏目明确电子签署要求，不能仅凭“GMP 常识”补客户政策。本轮没有实际签署或签名效力验证。
- **标签消耗未闭环。** 两模型均未保存四条正式消耗绑定。OpenAI 明确暂缓并问正式来源；DeepSeek 两次没有准确解释这一未完成项，第二次 `incomplete` 为空，不能据此宣布完整配置。

### 应减少的提问

DeepSeek 询问清洁表无标签空白区是否增加附件、静态“无”是否改设备引用、标签记录超过四条如何扩展、无标签空格是否另有用途、报废是否新增单位等。这些大多属于可选扩展，首轮应按原件完成，不应集中交给客户回答。

OpenAI 的无尘布是否另计消耗也属于可选扩展；没有来源和身份时先保留普通数量字段即可。正式统计来源、批号体系和必要日期口径则应保留为真正待决事项。问题分类是人工语义复核，不是用另一个模型给自己打分；每条原问题和受影响字段均保存在原始 `result.json`。

## 页面与执行闭环的边界

模型输出的局部比例位置由实验编译器转换为当前画布真实支持的细分行列和 `cellRange`，不是只有 JSON 中存在的伪坐标。12 次均通过实际后端保存与读回、字段配置/用途对比和零控件重叠检查。

在既有设计器中打开了两模型各三表的第一次输出，共六份；进入模拟填报，检查清洁数量/NCR 输入和标签实际使用量、八个附件入口。报废复合区已能把原因、说明、签名、独立日期和附件分开。第二次输出未逐张做浏览器视觉验收。没有执行正式提交、实际附件上传、电子签署、生产归集或权限隔离测试；空候选库也不能证明引用实际选值正确。

**零重叠不等于版式合格。** 已观察到清洁表长文字裁切、标签说明行裁切及页码拥挤、报废细网格过多和部分签字标签过窄。原始样式由导入器保留，但模型未收到图像、边框样式或保存后的截图，`inspect_template` 只有结构反馈。因此本轮没有验证视觉自检闭环，也没有一份可据此判为无需人工复核的完整交付。

对已有业务绑定使用独立合成值调用现有 `projection-preview`：DeepSeek 清洁的良/不良数量来源与报废数量可被投影，未把报废误作生产不良数。OpenAI 暂缓的正式统计没有被补写。合成投影只验证解释函数，不证明物料身份、正式统计归属或生产执行。尤其不能将缺乏正式来源依据的绑定升级为“业务正确”。

独立库共保存 18 份模板/版本：12 份正式样本、4 份连续编辑副本、2 份布局重放副本。原生审计记录为模板创建 18、版本创建 18、版本更新 22。数据库与原始实验结果保留，未改业务库。

## 实验工具缺陷与分开复测

初始 12 次进程使用同一份已加载协议和源码。实验中发现的适配器修正没有覆盖初始结果，原始源码与摘要保存在 `source-snapshot.json`、`protocol.json`。

1. 初始证据校验只接受标签单格，错误拒绝 `Sheet1!A4` 和 `A8:C11`。影响三次 OpenAI 任务，模型改成标签引用后才保存成功。此部分额外调用/耗时属于工具限制，不能全部归因模型。当前已接受合法工作表限定坐标和范围，并有聚焦测试。
2. 首次连续编辑要求先调用特定检查工具，尽管查询实际模板关系也已读到目标，仍拒绝改名。OpenAI 未在六轮内完成；原失败保留。移除多余状态门槛后，两模型在新的独立副本复测均通过，操作仍先读取真实目标并检查字段存在。
3. 全局网格细分导致未使用空格增加细线。当前编译器保留未占用空白原格的合并，对 OpenAI 标签、报废两份原输出进行确定性重放，业务模型完全相同、保存读回一致；浏览器仍有细网格，未宣布版式已修好。
4. 当前预算预估补计固定指令和工具描述。预算阈值始终只是保守近似，不是供应商硬上限。首次 DeepSeek 使用 `catalog:scrap.material` 的证据标识仍被拒绝，因为工具没有定义该标识；该失败也保留。

修正后的当前脚本不等于原始 12 次运行源码。不得用当前代码重跑覆盖旧目录；重新比较需要独立批次和重新冻结协议。

## 下一步最小切片

继续保持无新页面，优先解决四件事，而不是先建设通用多 Agent 框架：

1. **提供可查询的客户实施上下文。** 按租户、分类、工序关联记录正式来源职责、批号体系、签署政策及模板角色。已确认一次的政策供其他表复用；未知项保留未知，不能由模型补造。
2. **把关键语义检查放到工具边界。** 原件显式日期不能漏；已存在的多字段追溯复用规则不转问用户；当前引用入口必须符合有效声明；提问涉及未决绑定时对应动作应暂缓。不能只靠提示词要求“谨慎”。
3. **增加真正的版式反馈。** 提供导入图像、保存后的原生预览以及文本裁切/可用尺寸检查，让模型能修正，并评估往返次数。保留原生画布数据，不改成截图表单。
4. **在相同证据上再对比。** OpenAI 作为下一小轮质量基线、DeepSeek 保留成本对照是本轮支持的工程选择；暂不锁定最终生产模型。验证客户政策读取后，是否能少问且正确完成统计绑定，而不是把所有不确定项删除。

暂缓：全局 AI 入口、接管边框、多人锁/冲突处理、长期会话、生产权限、托管、主数据导入和接口工坊。以上均未在本轮实现或验收。

## 证据和门禁

事实分层：原始模型响应、API 读回、源码、审计与截图属于 `original-evidence`；第一轮报告只作 `secondary-reference`；本轮范围与“直接操作模板、不开发页面”属于 `user-confirmed`；模型选择及下一步方案属于 `inference`。
