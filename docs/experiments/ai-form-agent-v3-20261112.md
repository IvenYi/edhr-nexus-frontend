# eDHR 表单 Agent v3：受控工具与预览反馈验证

本轮在 `codex/ai-experiments` 实现内部实验工具，复用现有表单主数据 API 和设计器，没有开发产品页面。调试只用 OpenAI；首轮正式对比暴露引用检查缺口，修复后重新冻结协议，再各跑三张空白脱敏安速康表单。下面以修复后的六次结果为主，保留首轮全部结果，不代表商用验收或模型总体排名。

结论：查询、配置、检查、预览、局部修正的 Agent 闭环已可运行；模型配置的可靠性仍未达到直接交付客户的水平。OpenAI 在本样本上的覆盖和业务缺口披露更完整。DeepSeek 的低成本与工具修正能力值得保留，但少提问包含遗漏和错误推断，不能当作优势。

## 实现了什么

| 能力 | 实际实现 | 边界 |
|---|---|---|
| 适用知识查询 | 按关键词/概念检索原始规则，沿显式关系扩展，返回来源、成熟度、未决问题与关联声明 | 关键词排序与关系扩展，不是通用本体推理器；内部研究知识未发布为 runtime 知识 |
| 局部编辑 | 按字段 key、原文 source、行列尺寸修正；保留未涉及内容；提交前核对当前版本 | 实际 API 仍保存完整设计；先读后写不能代替原子并发控制 |
| 语义检查 | 明确日期遗漏、当前引用入口、字典范围、实际引用查询可用性、未经确认的签名/用途、单字段多追溯项、未决问题与绑定矛盾 | 日期、标签及批号判断为保守启发式，不证明全部语义正确 |
| 预览反馈 | 自动打开实际版本的原生模拟填报，测量静态文字裁切并把截图传回各自模型，再局部修正 | 没有新 UI；未验证打印、真实上传、正式签署和生产提交 |
| 完成约束 | 当前保存版本必须读回、检查、预览，截图必须已送入下一轮；存在已知问题只能报告 partial | 模型仍可能漏报未被工具捕获的问题，需独立验收 |

`get_applicable_knowledge` 至少调用一次是编排要求，不能把这个强制次数当成模型自主检索进步。后续查询内容、关系追踪和修正由模型选择。两个模型收到相同工具、任务、知识来源和截图提示，图像分别使用各自 API 原生输入，没有另一个模型提供视觉答案。接口格式依据 [OpenAI 图像输入文档](https://developers.openai.com/api/docs/guides/images-vision) 和 [DeepSeek 视觉文档](https://api-docs.deepseek.com/guides/vision/)。

客户实施政策在会话外保持为空，模型无权自称已确认。缺少来源职责时，实验工具暂缓对应正式统计绑定；这不是新产品草稿保存规则，也不是“一个工序只能一个正式来源”。DEC-0077-06 允许多个合法来源，DEC-0077-17 允许追溯和统计独立可选，DEC-0077-42 允许不同字段复用同一追溯项。

## 调试与验证方法

13 项聚焦测试通过。真实隔离 API 边界测试覆盖：不可查询的引用配置在建模板前被拒绝、过期 revision、局部修改不损伤其他配置、外部修改检测、修改后旧预览失效、截图送达前不可完成、有裁切不可声明 complete、会话结束后不可继续操作，以及结束时不能清空已保存问题、存在未决不能 complete、needs-input 原样保留问题。该边界测试故意使用预览替身，仅模型运行和原生预览探针作为浏览器证据。

三次 OpenAI 调试均保存、局部修正、重新预览并以 needs-input 结束。独立核心位置覆盖为 15/15、67/67、17/17；静态裁切从 3、10、6 处分别降至 0。一次截图截在弹窗动画期间，随后修复为禁用截图动画，并用真实原生预览复核稳定画面。调试中的 API 参数错误、工具拒绝与早期集成探针失败均保留，没有把这些数据混入正式对比。

正式验收在六次运行前冻结。独立评价器从实际 API 读取版本，与最后一次保存逐项比对；再使用未放入模型上下文的 v1 核心位置诊断、原生网格重叠检查、逐次预览反馈和人工语义/视觉核对。位置覆盖不等于配置准确率，零静态裁切也不等于全部控件或版式合格。

## 正式结果

第一轮六次运行全部保存读回，核心位置两家均为 99/99，最终静态裁切均为 0。然而独立运行查询发现 DeepSeek 标签表的 22 个、报废单的 3 个人员引用使用 `referenceField: name`，实际接口返回 400；OpenAI 已在查询错误后改为 `displayName`。DeepSeek 标签表还以 complete、零问题、零未完成项结束，不能接受为完整配置。报废单自行把申请日期设作追溯日期，也缺少客户口径依据。

这些结果保留在首批目录，未覆盖或追溯改成通过。工具随后加入每种引用配置的实际查询验证；空候选仍为合法配置，参数错误则阻止写入并进入完成检查。修复先执行 OpenAI 调试，第二批使用新的冻结协议和独立 attempt，才作为修复后正式对比。两批成绩分别报告，不合并分母。

修复后的正式运行：

| 模型/表单 | 核心位置 | 实际引用查询 | 静态文字裁切变化 | 提问条数 | 模型自报状态 |
|---|---:|---:|---|---:|---|
| OpenAI 清洁 | 15/15 | 3/3 | 10 → 0 | 3 | needs-input |
| OpenAI 标签 | 67/67 | 28/28 | 13 → 0 | 1 | needs-input |
| OpenAI 报废 | 17/17 | 6/6 | 2 → 0 | 3 | needs-input |
| DeepSeek 清洁 | 15/15 | 3/3 | 11 → 0 → 0 | 2 | needs-input |
| DeepSeek 标签 | 66/67 | 27/27 | 16 → 0 → 0 | 0 | complete，独立核对不接受 |
| DeepSeek 报废 | 17/17 | 5/5 | 11 → 5 → 0 | 2 | needs-input |

六次均实际保存、读回，并完成至少一次局部修改；保存后的原生字段矩形没有重叠。OpenAI 合计 99/99 核心位置、37/37 引用配置查询通过；DeepSeek 98/99、35/35。引用查询通过只说明参数可被运行时接受，不代表实体选择、正式业务归属或投影已经验证。

DeepSeek 的主要问题有原件和实际产物双重证据：

1. 标签表漏建 K59“复核人”输入，原生预览底部仅有静态标签；模型仍报告 complete、零问题、零未完成项。
2. 标签表把“四条独立物料字段复用同一物料编码追溯项”误读为禁止同项多绑，主动跳过该用途；DEC-0077-42 实际限制单个字段最多一个追溯项，允许不同字段复用。工具允许正确配置，但无法保证模型正确解释已读规则。
3. 标签表未配置四条实际使用数量的正式消耗用途，也没有披露来源职责待定。零提问包含漏报，不能解释为不需要客户决策。
4. 报废单直接绑定申请日期为追溯日期，未给出选择该日期而非管理者签字、处理、财务日期的客户依据。OpenAI 保留四个输入，并将用途口径列为待定。

OpenAI 也并非最终交付合格：无尘布消耗问题属于有条件扩展，不应成为建表必答；对正式来源的解释有时把实验工具约束称作“后端要求”，应在产品交互中纠正。两家原生预览仍能看到细碎网格、边框和控件尺寸问题；静态文字裁切为零不能覆盖这些问题。当前检查器没有通用的源表全部填写区识别或完整语义推理能力，因此独立评价器会发现它未拦住的遗漏和错误解释。

知识行为也应分开计量：第二批 DeepSeek 调用适用知识 6 次、独立读取 3 次、独立图谱工具 0 次；OpenAI 分别为 3、13、7 次。适用知识返回中已包含显式关系，因此 0 次独立图谱调用不等于没收到关系信息。这些次数只说明行为，不证明理解正确。

## 真正需要用户决定什么

不补充客户信息也能先建立表单结构、字段、合法引用和有依据的追溯。若要启用相应业务用途，缺少的是以下实施决策，而不是几十个字段参数：

| 决策 | 适用范围 | 处理方式 |
|---|---|---|
| 哪些记录承接正式统计、如何避免重复记载 | 清洁报工、标签实际消耗、报废记录 | 可一次确认三表的职责，存入可查询的客户实施上下文；不强制正式来源唯一 |
| 批号体系 | 清洁表酒精批号、报废单批号 | 确认内部物料、供应商或生产批次/SN 含义；保留普通字段，暂停依赖的用途 |
| 报废日期追溯口径 | 申请、管理者签字、处理、财务四个日期 | 若启用该追溯用途再确认；允许不启用，不能自动强迫四选一 |
| 无尘布是否另计实际消耗及物料身份 | 清洁表更换无尘布数量 | 可选扩展，后置处理，不阻塞当前建表 |

OpenAI 的 7 条中有 1 条可选扩展，其余涉及候选用途的真实缺失依据；不应向客户展示为“建表前必须回答 7 问”。DeepSeek 的 4 条没有覆盖全部缺口。已有实施策略应优先查询、复用，不能每个表单重新询问；当前隔离库未提供这些策略，实验不虚构答案。

## 开销与后续判断

本轮共 4 次 OpenAI 调试、两批各 3 表 × 2 模型正式运行。DeepSeek 没有调试调用。按脚本固定费率和响应 usage 的保守估算，OpenAI 调试约 USD 9.78、两批正式约 USD 14.36；DeepSeek 两批正式合计约 USD 0.36。修复后单批正式约 OpenAI USD 7.00、DeepSeek USD 0.20。该估算未当作实际扣费或最新报价，尤其 OpenAI 未扣减缓存折扣；原始 usage 保留可核算。

建议继续采用 OpenAI 调试工具、DeepSeek 完整回归。下一步应优先补“源表填写区覆盖核对”和“候选业务用途逐项说明依据/暂缓原因”，并让规则校验能明确返回合法复用关系；随后再验证客户实施政策查询与确认后的增量配置。无需先做完整 Agent 页面，也不应以这三个样本选择最终商用模型。

第二批 OpenAI 报废单首次启动遇到旧设计器打包文件并发写入导致的语法错误，尚未产生模型请求或 input 证据。原始启动日志保留；其他进程完成初始化后，以同一冻结协议启动成功。模型运行结束后，打包文件改为进程独立路径，并补齐未来协议中共享 v1 依赖源码的哈希。6 个并行进程验证编译成功，产物 SHA-256 均与修复前相同。该修改不改变模型提示、工具语义或编译产物，执行聚焦验证，没有为路径修复再次消耗模型额度。两批冻结快照没有被改写。

首次独立质量审查为 failed，复现了另一个完成门禁缺陷：已保存三条未决问题时，结束参数可以用空问题列表宣称 complete。已修复为以已保存草稿的问题列表为唯一来源；结束工具不再提供问题替换参数，尝试覆盖会被拒绝，显式增删问题必须走 patch 和复验。真实隔离 API 的三条问题用例及正常完成/needs-input 路径通过。该修复发生在模型比较之后，没有追加付费重跑；上表是原冻结协议下的观察结果，不能声称新完成协议已做过同一轮付费模型验证。六个正式结果的保存问题条数与自报条数一致，本次门禁缺陷的触发证据来自独立负例。

## 交付限制

本轮验证受控 Agent 循环，不验证企业级托管。租户授权、真正的原子并发/任务恢复、审计重放、知识发布、动态子表、正式业务投影、电子签署、打印和更大样本回归仍需后续实现与验收。

工具层已知的语义护栏会影响两个模型的输出，不能把最终没有违规绑定全部归功于模型理解。OpenAI 参与了调试，有开发适配偏差；每家每表只跑一次正式样本，结果不足以估计稳定成功率。完整统计配置还缺少客户实施政策，当前只能验证有依据的配置与未知项的处理。
