# 组织管理 UI 标准

> 适用范围：组织管理菜单下的组织架构、岗位角色、用户管理，以及后续需要复用同类后台工作台形态的系统页面。

数据模块下的工艺建模页面统一沿用系统模块后台工作台标准。工艺建模下挂物料管理、物料类型、工序管理、工艺路线、产品管理、产品簇、文档管理，后续数据类主数据页面默认以这组页面作为列表、查询、字段设置、详情抽屉和数据审计模板。

系统管理下的业务字典页面采用左侧字典列表、右侧字典项列表的双栏工作台。后续出现“分类/主表 + 明细项/子表”的后台页面时，默认复用业务字典的双栏布局、字段设置、列宽持久化、详情抽屉和数据审计交互。

模板建模页面统一沿用工序管理双栏工作台标准。表单模板必须按“模板主档 + 模板版本”建模，新增时同时填写基础信息和版本信息；批记录模板第一阶段只保留同标准的分类、列表、详情和审计能力，后续再组合工艺路线、产品和多个表单模板。

## 基准风格

- 使用 Vue Admin Plus 风格：`#1890ff` 主色、`#f6f8f9` 工作区、白色内容面板、`1px #e4e7ed` 边框、`5px` 圆角、紧凑 14px 字号。
- 页面优先服务内部产品/研发/系统管理员的高频操作，避免营销式卡片、重阴影、大圆角和装饰性背景。
- 内容区以“查询区 + 表格区 + 分页/统计 + 弹窗/抽屉”作为标准后台工作台结构。
- 登录页左侧品牌展示内容必须从系统管理-系统设置读取：系统 Logo、系统名称、登录页副标题、登录页说明和标准卡片均可配置，不允许在登录页组件内硬编码展示文案或卡片。

## 全局顶部栏标准

- 顶部采用两行固定壳层：第一行为名称栏/面包屑，高度 52px；第二行为标签栏，高度 50px；顶部壳层从左侧导航右侧开始，内容区从顶部壳层下方开始。
- 名称栏左侧固定显示折叠菜单图标和当前位置面包屑，面包屑按模块、菜单、页面逐级展示，使用紧凑图标和 `>` 分隔。
- 名称栏右侧固定显示常用工具图标：锁屏、搜索、通知、全屏、语言、主题、刷新，以及头像、账号名和下拉箭头。
- 通知角标使用红色圆角角标，尺寸保持紧凑，不得撑高名称栏。
- 标签栏左侧显示已打开页面标签，不使用固定快捷标签集合；当前页面标签和当前路由联动激活。
- 标签栏默认只保留“首页”标签；用户点击左侧菜单进入页面后，才把对应页面追加到标签栏。
- 首页标签必须固定显示在标签栏最左侧，不参与横向滚动，菜单标签过多时仍然可见。
- 除“首页”以外的标签不展示菜单图标，只显示标签名称和关闭按钮，减少横向占用。
- 新打开或切换到的菜单标签必须自动滚动到可视区域，活动标签锚点跟随当前路由。
- 非首页标签必须支持关闭；关闭当前激活标签后，自动跳转到相邻标签或首页。
- 右键标签时显示操作面板，操作项固定为：刷新、关闭其他、关闭左侧、关闭右侧、关闭全部。
- 标签项尺寸必须一致，不得因 hover 或选中状态改变高度、内边距、外边距或字重；统一使用 40px 高度、固定横向内边距和固定右侧间距。
- 标签 hover 和选中样式必须区分：hover 只使用轻灰背景和主色文字作为提示，选中状态才使用 `#e8f4ff` 背景、`#1890ff` 文字和关闭图标。
- 标签栏右侧显示标签操作入口图标。标签横向溢出时只允许标签栏内部横向滚动，不得撑开页面。
- 左侧深色模块栏和白色功能菜单栏必须从页面顶部到底部贯通，占满视口高度；顶部壳层不得覆盖左侧导航，只占据右侧工作区宽度。
- 左侧深色模块栏中的模块入口高度和最小高度固定为 64px，不得在纵向 flex 容器中被拉伸；选中态、悬停态不得改变模块入口高度。
- 顶部栏自身不得造成页面级横向滚动。

## 查询区标准

- 查询项使用紧凑横向布局，常用字段优先：姓名、账号、状态、手机号、创建时间。
- 数据模块工艺建模页面查询项优先使用名称/编码、状态等领域通用字段；查询区一行内的字段宽度必须受内容区约束，不得撑开页面。
- 日期字段使用起止范围，鼠标点击不应选中文本；开始日期不得晚于结束日期，结束日期不得早于开始日期。
- 查询、重置按钮使用图标 + 文案，按钮高度与输入控件保持一致。
- 同一查询区内的重置和查询按钮必须使用相同尺寸规格；不得出现一个默认尺寸、一个 `size="small"` 的混用。页面可选默认按钮或统一 `size="small"`，但两者高度、最小宽度和图标间距必须一致。
- 查询、重置按钮必须始终居右显示，不能因断点变化回到左侧。
- 查询区宽度必须受页面内容区约束，不得把 `main` 或 `body` 撑出横向滚动条。

## 表格标准

- 表格使用 `size="small"`、`stickyHeader`、固定布局和 `colgroup`。
- 单列表后台工作台必须固定可用工作区高度，当前 AppShell 下使用 `calc(100vh - 142px)`；纵向滚动条必须出现在表格容器内部，不允许由页面内容把主内容区或 `body` 撑出纵向滚动。
- 表格外层容器必须承担横向滚动，页面级 `body`/`documentElement` 不应出现横向滚动条。
- 表头必须在表格容器内保持 sticky，数据行纵向滚动时表头始终显示在数据行上方。
- 表头高度统一为 48px，表头基础样式应挂在 `TableRow` 的 `.MuiTableCell-root` 上，避免选择框或默认 padding 把表头撑高。
- 数据行视觉高度统一为 40px；底部分割线使用单元格内侧阴影绘制，不参与盒模型高度，表格容器可以撑满可用高度，但真实数据行不得因容器剩余高度被拉伸。
- 空数据、加载中、加载失败等非数据行状态必须撑满表格容器，不得只靠固定 `padding` 形成自然高度；仅空态/加载/失败状态的 `Table`、`TableBody`、空态 `TableRow` 和空态 `TableCell` 需要具备可继承的 `height: 100%`，有数据时 `Table` 高度必须回到 `auto`。
- 标准用户列顺序：姓名、账号、手机号、所属组织、岗位角色、状态、创建人、创建时间、更新人、更新时间。
- 标准岗位角色列顺序：岗位角色、描述、是否内置、创建人、创建时间、更新人、更新时间；列表、查询区、新增弹窗和编辑弹窗均不展示岗位编码，岗位编码由后端在提交时自动生成并作为接口唯一编码保存。
- 标准业务字典列顺序：字典名称、字典编码、字典项数、状态、创建人、创建时间、更新人、更新时间。标准字典项列顺序：字典项名称、字典项值、排序、状态、创建人、创建时间、更新人、更新时间。
- 业务字典页面左侧字典列表和右侧字典项列表均必须使用标准表格能力：字段设置、列拖拽排序、列宽拖拽、按当前用户持久化、内部滚动、空态撑满容器和图标操作列。
- 业务字典新增/编辑弹窗中，字典名称和字典编码为必填；字典项新增/编辑弹窗中，字典项名称和字典项值为必填。状态只保留启用、禁用两种业务状态。
- 业务字典和字典项的系统内置数据必须至少禁止删除；若后端限制编辑，前端必须展示后端返回的具体错误，不允许吞掉错误或只提示泛化保存失败。
- 标准工艺建模列必须按领域设置默认列，并统一包含状态、创建人、创建时间、更新人、更新时间。物料管理、产品管理默认包含规格型号、类型/产品簇、单位；工序管理默认包含工序分类、默认工序类型、标准工时、工序通用描述；工艺路线默认包含产品簇；文档管理默认包含版本和文件引用。
- 工艺建模新增/编辑弹窗默认只填写名称和领域字段，不允许手动填写编码；编码由后端在提交时自动生成并作为接口唯一编码保存。工序管理除外：工序编码必须由用户填写，因为工序名称允许重复时只能通过编码区分。
- 工序管理新增/编辑弹窗字段顺序固定为：工序名称、工序编码、工序分类、默认工序类型、状态、标准工时、工序通用描述；工序通用描述放在新增和编辑弹窗字段的最后。
- 模板建模-表单模板新增弹窗必须使用“基础信息”和“版本信息”两张卡片。基础信息包含表单名称、表单编码、表单分类、表单描述；版本信息包含版本、生效时间、失效时间。弹窗底部按钮固定为取消、保存、保存并设计。表单编码和版本均由用户填写，不自动生成。
- 表单模板列表默认字段为：表单名称、表单编码、当前版本、模板分类、生效时间、失效时间、状态、创建人、创建时间、更新人、更新时间。操作列必须提供设计入口。
- 表单模板设计器必须提供模型设计、画布设计、流程设计三个模式，并在顶部提供 PDF、Word、Excel、图片导入入口。模型设计用于字段确认和字段类型调整；画布设计按“图层锚定 + 格式复刻”保留原文件版式还原骨架；流程设计用于后续审核、电子签名和放行流程配置。
- 表单模板后端必须保留版本历史，不允许编辑时覆盖历史版本。设计内容分别保存为模型设计 JSON、画布设计 JSON 和流程设计 JSON，导入文件和设计保存都必须写入数据审计。
- 工艺建模-产品管理是物料管理的派生视图：仅展示物料类型为“半成品”或“产成品”的物料，不提供独立新增、编辑、删除入口；产品管理详情和数据审计必须指向源物料记录，避免出现独立产品表与物料表数据不一致。
- 后端列表、树形或分页 DTO 必须自动返回 `createdBy`、`createdAt`、`updatedBy`、`updatedAt`，前端数据表格必须自动渲染创建人、创建时间、更新人、更新时间，不允许只在详情抽屉里显示。
- 首次创建时如果没有独立更新人或更新时间，后端返回和前端归一化都必须将更新人、更新时间回填为创建人、创建时间。
- 字段列支持拖拽宽度，列宽按当前用户持久化，选择列和操作列固定宽度。
- 表格工具栏左侧必须提供字段设置入口；字段设置弹层展示所有可配置数据字段，支持拖拽排序和勾选显隐，操作后必须立即同步表格 `colgroup`、表头、表体和空态 `colSpan`，并按当前用户持久化。字段设置作为后续表格页面的标准能力和复用模板，所有新增后台表格默认按此交互实现。
- 操作列固定在右侧，左侧分隔必须使用从表头到表体贯通的阴影效果，使用图标按钮和 Tooltip，不使用行内文字按钮。
- 阴影由表格容器或独立覆盖层统一绘制，覆盖操作列宽度，不得在每行操作单元格上重复绘制。
- 行点击打开右侧详情抽屉；复选框和操作按钮必须阻止事件冒泡。
- 主子表列表的父行点击默认用于展开或收起子数据行；父行中承载详情入口的核心业务名称列必须使用蓝色可点击文字样式，点击后打开当前父行详情抽屉，并阻止事件冒泡，避免同时触发展开或收起。
- 组织字段显示完整路径，单行截断并通过 `title` 暴露完整文本。
- 系统内置数据必须具备前后端双层保护：例如系统管理员用户、系统管理员岗位角色默认存在，不允许删除；操作列按钮置灰并通过 Tooltip 或 Snackbar 告知原因，后端删除接口也必须拒绝。
- 危险级联删除必须在二次确认中列出受影响对象和确认后的数据变化；例如删除岗位角色时，应先展示仍挂载该角色的账号，并明确确认后这些账号的岗位角色将置空、账户状态会变成禁用。

## 岗位角色权限标准

- 岗位角色的操作列必须提供“菜单权限设置”图标按钮，点击后打开独立权限弹窗，不与新增/编辑基础信息弹窗混用。
- 权限弹窗按“模块权限 -> 菜单权限 -> 功能权限 / 数据权限”分层展示。左侧为模块权限，中间为当前模块下的菜单权限，右侧展示当前菜单的功能权限和数据权限。
- 权限弹窗中的模块、分组和菜单名称必须复用当前左侧菜单的数据源；若左侧菜单通过菜单管理被调整，权限弹窗展示也必须同步变化。保存时再将菜单路径映射到后端权限编码和权限 ID。
- 模块权限用于整组勾选或取消该模块下全部菜单与功能；菜单权限用于勾选或取消该菜单及其下挂功能；半选状态必须清楚表达部分授权。
- 功能权限来自后端 `Permission.type !== PAGE` 的权限数据，通常对应按钮、操作或流程动作。
- 数据权限作为每个菜单下的标准设置区，默认选项为：全部数据、本组织及下级、本组织、仅本人、自定义。若当前阶段尚未接入角色维度数据权限后端表，也必须先保留 UI 和规范位置，后续可替换为真实接口保存。
- 保存权限时必须继续保存菜单/功能权限 ID；数据权限接入真实后端前，不得声称已完成跨用户生效的数据范围控制。

## 分页标准

- 分页器固定使用“总数 + 分页 + 每页条数选择”布局，并放在表格面板底部。
- 每页条数选项统一为 20、50、100、200。
- 切换每页条数后必须回到第一页，避免页码越界导致表格空白。

## 用户表单标准

- 用户字段统一使用“账号”，不使用“用户名”。
- 新增/编辑弹窗使用 `DialogContent dividers`，字段控件高度为 40px，控件间距保持 12px 左右。
- 账号、姓名、所属组织、岗位角色为必填项。
- 编辑用户时账号禁用。
- 岗位角色为单选，但接口契约继续使用 `roleIds` 数组。
- 组织下拉显示公司/部门/班组路径，不显示组织编码。
- 邮箱和手机号保存前做格式校验；校验或后端错误用右上角 Snackbar 明确提示。

## 个人设置标准

- 个人设置从顶部用户操作栏进入，面包屑只显示“个人设置”，不额外增加“个人中心”等父级。
- 用户头像支持上传图片文件；上传成功后必须写入当前用户资料，并通过统一用户变更事件同步顶部用户操作栏和个人设置页。无头像时使用用户名称第一个字作为头像内容，头像背景沿用顶部栏蓝色。头像上传入口使用头像右下角相机图标，不再额外展示“上传头像”文字按钮。点击头像必须打开头像裁剪弹窗。头像裁剪弹窗必须支持上传或更换图片、鼠标拖拽定位、缩放滑块放大缩小、取消和保存；保存头像前必须在前端生成统一尺寸的裁剪文件，再复用头像上传接口保存。
- 左侧个人资料卡右上角必须提供蓝色“修改密码”文字按钮，点击后用模态框完成密码修改，不在右侧基础信息区展示独立密码卡片。
- 左侧个人资料卡头像下方展示姓名和所属组织，不展示个人简介或额外描述。所属组织显示当前用户主组织路径，无组织时显示“-”；所属组织不得再放在下方信息行中。信息行顺序固定为姓名、账号、角色、手机、邮箱。信息行下方使用分割线单独展示“电子签名”区域，电子签名图标和标题必须与上方信息行对齐，标题行右侧必须使用统一状态徽标展示“未认证”“已认证”或“已过期”；虚线方框内展示签名状态、认证于、失效于以及蓝色文字操作按钮，未认证时按钮为“认证”，已认证或已过期时按钮为“重新认证”。
- 个人设置基础信息不展示昵称、标签、生日和个人简介字段；基础信息表单只展示姓名、性别、邮箱、手机。姓名和性别必须位于同一行；邮箱和手机必须位于同一行，邮箱使用常规输入框，不再通过绑定邮箱弹窗维护。邮箱和手机保存前前端和后端都要做格式校验，并与系统模块的用户管理数据同步更新。保存成功后必须同步当前用户查询缓存和本地用户资料，页面刷新后仍能显示最新数据。
- 个人设置的账号绑定 Tab 按顺序展示微信、企业微信、钉钉、飞书四类绑定；不再展示邮箱、QQ、支付宝、微博、Github、Paypal 等其它绑定项。账号绑定图标必须逐一使用对应平台的专属识别图标，不得用业务包、云、团队等通用占位图标替代。已绑定账号右侧使用蓝色“更换绑定”文字按钮，未绑定账号右侧使用蓝色“添加绑定”文字按钮。
- 个人设置页面整体不得出现右侧页面级滚动条；右侧内容区滚动条只能出现在基本信息内容容器内部。右侧基础信息区域不展示生日和个人简介。
- 当前用户必须提供密码修改功能，入口固定为左侧个人资料卡右上角蓝色文字按钮。密码修改模态框字段为当前密码、新密码、确认密码；保存前校验当前密码、新密码非空以及两次新密码一致，错误和成功提示统一使用右上角 Snackbar。密码修改审计只记录“密码已修改”等事实，不记录明文或哈希。
- 个人设置中凡是用户操作导致用户行数据变化，例如基础信息、头像、电子签名、密码修改，都必须写入数据审计。
- 个人设置必须提供“数据审计”和“登录日志”两个只读 Tab。个人设置数据审计 Tab 必须通过后端当前用户专用接口按目标用户查询，即 `entityType=USER_ACCOUNT` 且 `entityId=当前用户 ID`；当前用户自己在个人设置页里做的改动，以及管理员或其他授权用户在用户管理等位置改动该用户资料的记录，都必须一起展示，不允许仅按操作人过滤。个人设置登录日志 Tab 必须通过后端当前用户专用接口按当前账号过滤，只展示当前账号自己的登录和登出历史。两类数据都不得在前端调用系统总列表后再做筛选。
- 右侧基本信息 Tab 中不再展示独立电子签名卡片。左侧电子签名区域必须在虚线方框中提供蓝色“认证”或“重新认证”文字按钮，并在虚线框下方展示电子签名授权通知书 PDF 区域；授权通知书文件条从左到右固定为“PDF 标签、完整文件名、预览”，文件类型必须标识为 PDF，不得展示额外签名图标、外链图标或下载按钮，预览按钮文案只叫“预览”。授权通知书使用 `/auth/me` 或签名认证成功响应中的文件 ID 生成 `/api/v1/files/{id}/preview` 在线预览，个人设置页不提供授权通知书下载入口。预览弹窗标题“授权通知书预览”和右上角关闭 X 图标必须位于同一行，关闭图标居右显示，弹窗底部不再提供“关闭”文字按钮。每次电子签名认证生成的授权通知书 PDF 必须采用表格版式，并包含授权通知书标题、身份证正反面图片、授权人姓名、授权人系统账号、勾选的 3 项协议内容、授权人签字（手写签名图片）、授权认证时间、授权截止时间、快照指纹、授权认证时间戳和授权截止时间戳。电子签认证失效时间必须来自系统设置-安全设置 Tab 中的电子签名策略“签名密码修改周期”，前后端均按 1-30 天归一，不允许固定写死为一年。电子签名认证必须在模态框内完成，不得在基础信息表单中散落密码、签名声明或证件材料输入项。认证弹窗必须包含手写签名板、电子签名密码、当前系统登录密码、身份证正反面上传和三段声明逐条确认；手写签名板必须在画板内显示当前用户名灰色指引，用户名灰色指引字号必须足够大，指导用户按姓名临摹签署，指引不得写入签名图片；电子签名密码必须由用户单独设置并单独存储哈希，当前系统登录密码只用于本次身份校验，不得作为电子签名密码保存；身份证正反面上传暂时只限制图片文件类型，不得在电子签认证链路中执行正反面识别或身份证内容预检；签名含义不再作为用户可编辑字段展示；电子签名密码和当前系统登录密码都必须支持眼睛图标切换明文显示。三段声明未全部确认时认证按钮必须置灰，手写签名、证件正反面、电子签名密码或当前系统登录密码缺失时也不得提交；三段声明的整行容器必须支持点击切换，复选框点击不得触发行容器二次切换。
- 电子签名相关文件上传接口必须返回字符串类型的 `fileId`，前端也必须优先使用字符串 `fileId` 提交签名认证，避免 Snowflake 64 位 ID 被 JavaScript 数字精度截断导致认证接口 400。
- 个人电子签名不得实现成普通文本字段。签名确认必须要求当前账号登录密码二次认证、电子签名密码单独存储、明确签名含义和本人真实意愿确认，并落库保存签名人、签名账号、认证方式、电子签名密码哈希、手写签名文件引用、身份证正反面文件引用、三段确认声明、签名时间、签名目标、目标快照、快照哈希和审计记录。
- 电子签名能力按中国电子签名法、FDA 21 CFR Part 11 等要求落实身份认证、意愿确认、记录绑定和可追溯技术控制；页面和代码不得宣称系统或客户质量体系已自动完成法律/法规认证。

## 详情抽屉标准

- 行点击打开右侧全高抽屉，抽屉覆盖固定顶部栏和标签栏，不预留固定 header 空白；抽屉层级必须高于 AppShell 顶部栏，避免 Tab、关闭按钮等交互被顶部标签栏截获。
- 抽屉的容器 `sx` 和 `PaperProps.sx` 必须分开维护：backdrop/容器可设置 `top/bottom/zIndex`，但 Paper 不得继承这组定位样式，否则会出现抽屉面板从视口右侧外部开始、Tab 无法点击的问题。标准 Paper 只保留宽度/高度和必要的动画覆盖。
- 抽屉标题为“信息查看”，默认进入“数据信息” Tab。
- Tab 固定为“数据信息”和“数据审计”。
- 数据信息至少包含：基本信息、页面领域信息、系统信息。用户管理的页面领域信息为组织与角色；岗位角色的页面领域信息为系统内置标识、描述和权限摘要等角色属性。
- 工艺建模页面的数据信息至少包含名称、系统编码、状态、描述和该页面领域字段；领域字段不得在列表、抽屉和审计中直接暴露无法理解的技术字段。
- 系统信息包含创建人、创建时间、更新人、更新时间。
- 首次创建时如果没有独立更新人或更新时间，更新人和更新时间显示创建人和创建时间。

## 审计标准

- 审计数据必须来自后端真实审计接口，不在前端伪造“当前快照”。
- 安全管理下的审计日志列表必须明确展示：操作人、账号、操作时间、操作动作、触发方式、功能模块、菜单、具体功能；字段顺序不得随意缺省，后续审计类列表默认沿用该顺序。操作数据不在列表中展示，必须放入详情抽屉的数据审计区域。
- 审计日志中的功能模块必须展示最左侧模块栏名称，例如系统内的组织管理、系统管理、安全管理下页面都显示为“系统”，不得显示二级目录名称。
- 审计日志中的菜单必须展示为“一级目录 · 二级目录”，例如“系统管理 · 系统设置”；具体功能只展示功能名称，不允许拼接菜单名称。
- 审计日志查询区必须至少支持按操作人、账号、操作动作、功能模块、菜单筛选；筛选条件必须传到后端分页接口，不允许只在当前页数据上做前端过滤。
- 审计事件后端契约必须保存并返回 `operatorDisplayName`、`operatorAccount`、`operationTime`、`actionLabel`、`triggerMethod`、`triggerMethodLabel`、`moduleName`、`menuName`、`functionName`、`dataSummary`、`contentBefore`、`contentAfter`、`snapshotHash` 等字段，确保能回答“什么人、什么账号、什么时间、以什么方式、在哪个模块/菜单/功能、操作了什么数据、前后变化是什么”，并能校验前后快照是否被改动。
- 只要行数据因为用户操作发生改变，就必须写入数据审计；新增、编辑、删除、状态变更、菜单权限设置、重置密码、移出组织等动作都属于审计范围。
- 用户审计按 `entityType: USER_ACCOUNT` 和当前用户 ID 查询。
- 岗位角色审计按 `entityType: ROLE` 和当前岗位角色 ID 查询；新增写入完整快照，修改只写入发生变化的字段。
- 业务字典审计按 `entityType: BUSINESS_DICTIONARY` 和当前业务字典 ID 查询；字典项审计按 `entityType: BUSINESS_DICTIONARY_ITEM` 和当前字典项 ID 查询。双栏页面中点击左侧字典或右侧字典项都必须打开同一标准详情抽屉，并按当前选中对象展示对应审计记录。
- 审计字段必须翻译成中文业务名称，不允许在数据审计区域直接暴露技术字段 key；涉及菜单权限、所属组织、角色等关联字段时，必须翻译成客户能读懂的业务名称，无法识别时用“未知类型(ID)”兜底。关联对象的审计值必须在写入审计时保存业务名称快照，不得在展示时只引用当前关联表，否则被引用记录删除后历史审计会退化成 code 或 ID。
- 所属组织审计必须在写入时保存当时的组织路径名称快照，字段统一为 `organizationName`，格式为“公司/部门/班组”。展示层必须优先展示该快照；当新快照存在时必须隐藏 `primaryDepartmentId`、`departmentId`、`departmentIds`、`departmentName` 等技术关联字段。旧审计记录如果只有组织 ID，不允许使用当前组织表反查并伪装成历史名称，只能按“历史组织ID(ID)”兜底展示。
- 审计事件必须在首次写入时生成不可变快照指纹 `snapshotHash`，指纹基于操作主体、前后快照、操作人、菜单功能、时间等核心审计字段生成；应用层不得更新已有审计事件，后续如需修正只能追加新审计事件。
- 审计展示不得直接暴露原始 ID。
- 涉及文件、图标、Logo、浏览器图标的审计必须保存并展示快照和预览地址；变更前/变更后都要能看到文件 ID、原始文件名、来源、标签、所属分组、预览地址等可读信息，方便审计人员判断原图标和新图标。
- 审计记录使用手风琴行，摘要展示操作人、操作动作、操作时间。
- 展开后按字段展示变更前/变更后内容；无审计记录时文案为“暂无审计记录”。

## 反馈和错误

- 所有成功、错误、校验、接口异常提示必须固定右上角；新增页面必须显式设置 Snackbar `anchorOrigin={{ vertical: 'top', horizontal: 'right' }}`，不得依赖组件默认位置。
- 成功提示和错误提示均使用同一 Snackbar/Alert 标准。
- Snackbar 内部提示沿用系统-用户管理样式：使用 MUI Alert 默认外观，不使用 filled 变体。
- 保存、删除、移出、重置密码等动作必须显示成功或错误反馈。
- API 错误优先展示后端 message，不能只显示泛化的“保存失败”。

## 第一阶段复用策略

- 用户管理页先按组织架构页人员工作台的标准完成本页改造。
- 暂不抽大型通用表格组件，避免影响已经稳定的组织架构页。
- 后续当岗位角色、用户管理和组织架构三处都稳定后，再抽列宽、详情抽屉、审计手风琴、用户表单等小组件或 hook。
