# 租户内显式委托：本轮确认与边界

日期：2026-10-20。知识基线 `0.3.25 / schema 1.2.0`。本记录支持 DEC-0081 的有限政策增量，不是完整工作流、DHR或全库语义验收。

## 用户确认的原始来源

本轮 H012 源码核对发现通用 `WorkflowEngine.transferTask` 会用单人目标快照替换创建时候选来源。主审没有把该实现行为自动当作政策，而是先询问：受限任务的转办目标是否必须来自创建时冻结的候选集合。

用户追问当前三条路径、候选人含义及集合内转办的作用，并提出：

> 你说的候选人是不是就是节点对应的审批人员？如果是的话我觉得意义不大。你觉得是否要考虑显示转办的话可以指定租户下的某个用户呢？

主审解释候选人是节点所配置用户、部门或角色在到达时解析出的具体人员，并说明当时实现：通用任务允许原集合外的同租户有效用户但丢失原来源；普通生产表单在配置审批主体时只允许原候选中的其他用户、开放节点可选有效未锁定用户；DHR只开放专属审批通过与退回整理，通用转办受阻。随后提出显式租户内委托、原来源保留、当前责任独立、转后仅目标人处理并记录原因的方案，并明确普通生产表单是否一起改变需确认。

针对“仅通用工作流”“通用工作流与普通生产表单都允许租户内委托”“先只修来源留存”三种范围，用户实际选择：

> 通用工作流与普通生产表单都允许租户内委托；DHR 保持

该回复是本轮 `user-confirmed` 来源。它不是2026-09-04或2026-09-17就已确认的目标范围；[通用任务原始确认](workflow-task-multi-candidate-user-confirmed.md)和[普通表单原始确认](form-approval-transfer-user-confirmed.md)保留原文。普通表单转办能力在早期共同遗漏的历史纠偏继续适用；本轮改变的是显式委托目标范围，不能把两件事混成同一时间线。

新 DEC-0081 保持 `specified/internal`。既有资产不因文字同步批量提高成熟度，不能据当前规范或源码存在宣称业务运行或独立质量已通过。

稳定 `fact.form-approval-transfer.target-authorized` 保留；原 alias `formProcess.transfer.targetWithinFrozenCandidates` 只描述历史目标限制，现行 alias 改为 `formProcess.transfer.targetAuthorized`。这是同一事实 ID 的当前含义同步，不重命名产品接口/数据库字段，也不让旧 alias 继续暗示受让人必须属于原集合。`task.candidateMembership` 保留为当前有效处理集合的查询别名；原创建来源与当前资格在定义中分别解释。

## 工程选择和历史边界

工程落实（不是用户逐字指定的政策）：复用现有任务、生产表单状态与人员选择器；查询目标与执行时重新验证范围一致。固定源码用共享 `TenantTransferTargets` 验证用户资格；通用 `singleUserSnapshot` 分别保存首次可获得的候选原文本 `originSnapshot` 与当前单人 `userIds`，重复转办保留原文本，`originRecordedAfterPriorTransfer` 标明已经发生过旧转办时的来源限制。字段名、搜索分页/上限、原因长度及具体错误文案属于工程选择。

转办、完成及终止在原 `instance→task` 锁序下局部刷新 JPA 受控实例，防止等待行锁后仍按旧处理人快照授权。该修复对应真实 PostgreSQL 并发反例及回归，落实现有当前办理权和事务原子性，不形成新的业务政策，也不认证全引擎并发。

没有授权恢复或推测此前已经丢失的候选来源。新增留存只能保留当前真实可获得的原件，不把第一次修复后转办前的单人旧快照冒充完整创建来源。完整多租户数据隔离仍见 `question.multi-tenant-workflow-isolation`，本次局部目标资格检查不关闭该问题。

既有 AuditEvent 在原生 PostgreSQL 的 JSONB/时间往返后摘要可能不能按当前方法重算一致；该探针失败与本轮目标政策或图写入 guard 无因果，现行审计查询/导出也没有该读回阻断。主侧单独登记 W5 缺口，不修改摘要算法、旧hash或历史原文；本记录不认证审计摘要重算能力。
