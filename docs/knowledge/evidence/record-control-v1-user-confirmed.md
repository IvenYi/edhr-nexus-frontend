# 记录变更与作废首期补充确认

日期：2026-09-16

来源：用户提供的《记录变更与作废功能开发交接-2026-09-16.md》及本对话后续明确确认。本记录是用户决策的内部证据整理，不是功能实现或验收证明。后续对话中的明确决定覆盖交接文档中相冲突的首期范围。

- 公共流程代码全部由逸文负责；记录控制域只调用公共流程契约，不复制任务或流程引擎。
- 首期仅以表单流水号定位已完成、存在当前有效修订的实例；同页发起 CHANGE 或 OBSOLETE。按批次/SN 检索延期；没有 DHR 或记录本独立入口。
- 同一表单实例最多一笔活动申请；最终确认时重新检查来源状态和当前修订，审批期间来源主状态仍为已完成。退回使旧申请和旧流程终结，再次发起创建新申请编号和流程实例。作废不生成内容新修订。
- 变更拟数据与当前有效数据隔离；申请原因必填，显式选取类型匹配的已发布流程，申请人完成真实签名后一次确认。新修订不继承原表单签名；原签名只作为历史证据，申请及审批签名分别绑定其动作。本期不增加原业务签署人对 Rev.2 重新签署的动作。
- 本期不做岗位角色或菜单权限授权：当前租户内所有已登录用户可以按表单流水号查询并发起两类申请，且均可查看“变更记录”全量历史；“我的变更”列表和详情只允许当前申请人访问，“变更审批”只允许当前候选/处理人以及本人已处理任务访问。人员身份由后端认证上下文取得，不信任前端人员参数。这是首期产品授权边界，不表示当前公共流程候选接口已符合此边界。
- 当前尚无可靠 DHR 实例/放行记录来源，因此本期不实现 DHR 放行状态判断或联动，不得宣称能够阻断外部或历史已放行 DHR；作废后自动标记证据缺项、补开提示/待办、重汇总同样暂缓。
- 菜单位于“记录 / 变更管理”，本期只交付“记录变更、我的变更、变更审批、变更记录”四个入口。当前仓库没有独立的“表单列表、表单填报、表单审批”页面；本期不新增“表单管理”空菜单，也不开发这三个页面。客户可见文案使用“审批”，稳定技术标识保持兼容。该后续用户确认覆盖交接文档中将“表单管理”画为现有并列分组的示意。

未提供运行实现、数据库迁移或发布验收证据；本证据只能支撑 `specified/internal` 知识状态。
