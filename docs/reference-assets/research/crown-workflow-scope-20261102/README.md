# 冠骋流程日志、流程干预的业务范围

核对日期：2026-11-02（Asia/Shanghai）。本轮 L1 调研直接读取本地冠骋原始前后端导出及《edhr探索之旅.docx》，没有运行冠骋、登录其线上系统或提交业务操作；不能把导出快照当作当前所有客户部署。eDHR 的产品实现、开发环境、数据与既有权限政策均未改动。

## 结论：两个集中入口不能直接画等号

冠骋的“流程干预”能从原始前端确认 **6 类分组**；“流程日志”能从原始手册及菜单权限定义确认 **5 类审核分组**。不能把干预的六类照抄为日志的六类，也不能把“表单审核”四个字直接解释为普通填报表单的运行流程。

| 业务 | 流程日志 | 流程干预 | 本轮原始依据与解释 |
| --- | --- | --- | --- |
| 普通表单运行流程／待办 | **尚未确认进入同一集中列表** | **有**，表单流程页签 | 干预 Doc 页签实际查询 `FORM,EDHR`；集中日志权限只有下述五类，没有找到 Doc 分组或完整低代码查询，不能把缺证据写成绝对不支持。 |
| 表单模板、DHR 模板的审核 | **有模板审核分组** | **有**，模板审核页签 | 日志 `Tmpl` 权限；干预走独立文控待办接口，模板类型筛选为 FORM／EDHR；不同于普通表单填报审批。 |
| 工艺路线配置审核 | **有**，工艺审核 | **有**，工艺审核页签 | 日志 Routing 权限；干预查询 `ROUTING`。这里是配置审核，不是生产对象沿路线过站的执行历史。 |
| 产品制程配置审核 | **有**，制程审核 | **有**，制程审核页签 | 日志 ProductProcess 权限；干预查询 `PRODUCT_PROCESS`。 |
| DHR 汇总审核 | **有**，DHR 审核 | **有**，DHR 审核页签 | 原始日志截图直接显示 DHR 审核列表；干预查询 `EDHR_SUMMARY`，后端也创建该类型待办。 |
| 表单／DHR／记录本变更审核 | **有变更审核分组** | **有**，变更审核页签 | 日志 Change 权限及原始截图；干预查询 `FORM_CHANGE`、`DHR_CHANGE`、`NOTEBOOK_CHANGE`。DHR_CHANGE 与 DHR 汇总审核不是同一业务。 |

因此，用户重点问的三类需要分别回答：**表单流程在干预里明确有，集中日志仍缺直接证据；DHR 汇总审核两个入口都明确有；整条作业执行没有出现在已核实的集中分组中，走事务实例路径。**

## 前端及菜单定义的直接证据

[原始来源清单](evidence/source-manifest.json)逐文件固定路径、SHA256、行号范围和用途；[带原始行号的摘录](evidence/source-excerpts.txt)便于复核，下面的 F／B 编号均对应该清单。

- F01：`approval-process-intervention/useDocumentTask.ts:102–140` 定义 doc、tmpl、routing、productProcess、dhr、change 六个页签，`tabList` 只返回可见项。F09 的中文名称依次为表单流程、模板审核、工艺审核、制程审核、DHR审核、变更审核。
- F02：`doc-tab/todo.vue:95–101` 调用所有用户待办接口，明确传 `taskType: 'FORM,EDHR'`。这里的查询码不能写成 `OF_APPROVE`；后者是流程定义类型，不能混为一个字段。
- F03/F04：模板审核调用 `getDocControlTaskTodoAllUserPageList`，筛选模板种类 FORM／EDHR。它不是普通 ProcessTaskTodo 的同名“表单审批”。
- F05–F08：工艺、制程、DHR、变更页签分别传 ROUTING、PRODUCT_PROCESS、EDHR_SUMMARY 及三个 CHANGE 类型。
- B01：原始 Liquibase `upgrade/5214/changelog-menu_permission_5214.xml:675–760` 为 `web_process_log_jg30` 声明 Tmpl、Routing、ProductProcess、Dhr、Change 五类权限；同文件随后为 `approval-process-intervention` 声明 Doc 加这五类，共六类。**这证明菜单权限的业务分组，不能替代未获得的低代码页面完整查询与真实返回行。**
- F01/F10：干预页签叠加功能开关和各自权限，动作另有 Reassign／Withdraw 权限。因此某张截图只显示两个页签，不代表产品源码只支持两类。DHR 页签条件实际写为 `dhrSumDisabled && Dhr权限`；仅保留代码原样，不根据变量名字推断配置语义或部署默认是否开放。
- F11：另有 `process-intervention` 与 `approval-process-intervention` 两种路由；原手册中系统配置下的旧任务转交截图不应直接当成上述六类审核干预页。

## 作业执行及作业内表单的边界

B05–B07 显示事务实例为独立 `em_txn_inst` 模型；`TxnInstSubmitBs:270–279` 启动业务流程实例，`TxnInstListSearchBs:46–67` 提供批次／SN事务列表查询。B02–B04 则显示集中审核类型及其待办投影。两组原始证据支持“整条作业执行”和“审核待办”是不同业务视角，不能因为都有流程图就合并解释。

但还有一个例外不能忽略：B08 的 `FormNodeDelegate:122–147` 会从事务节点创建 `businessType=TXN` 且带事务 ID 的表单，B09 又将创建委托给缺失的底层平台实现。因此，**整条事务未作为独立分组，不等于事务内产生的表单也绝不进入表单流程待办**。当前原始资料不足以确定所有 TXN 来源表单到 FORM／EDHR 待办查询码的映射，保留为证据缺口。
