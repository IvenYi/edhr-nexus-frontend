## 1. 两个状态分开，不等于 DHR 必须继续批准

`user-confirmed` 既有 DEC-0087-02／03：原完成记录、有效修订与变更申请分别保存。例：Rev.1 数量 100，申请改成 90，申请期间正式值仍是 100；批准才产生 Rev.2=90，退回／撤回不改变 Rev.1。旧修订、原签署和审批申请有各自身份，便于解释当时的有效内容。

`inference` 取舍：分开记录可保留完整历史，避免申请被退回时来回改写正式来源，也能区分“填报完成”与“纠正申请在审”。成本是所有关键下游都必须正确读取活动申请，不能只看 COMPLETED 就放行；页面也需清楚展示申请状态。

用户对本轮问题“如果 DHR 引用的表单正在申请变更或作废，你更倾向哪种处理？两种方案都保留原有效修订，区别在 DHR 能否继续提交或批准。”明确选择：

> 原版可查看，暂缓 DHR 汇总提交和审批通过，等申请结束（推荐）

因此当前政策是：原有效修订保留，活动申请另行阻断相关 DHR 的汇总提交及审批通过。它不是把申请当成已生效，不自动退回 DHR，不把同一个生产对象的所有无关动作都锁住。申请结束还须按既有有效性规则复核：退回／撤回且来源未变，可恢复正常处理；批准变更／作废后，旧冻结证据若已过时，仍须人工退回或发起修订，不能仅凭活动申请消失就自动通过。撤回运行入口仍属既有未完成范围。

这个组合的好处是保留历史解释，又降低明知来源有争议仍先批准 DHR、之后返工重审的风险；代价是纠正申请久拖未决会延迟 DHR 收尾。是否暂缓与申请改动大小无关，本轮未新增“轻微修改可豁免”的政策。

`original-evidence`：当前 DhrSummaryService／DhrReviewService／DhrEvidenceImpactService 未直接消费 record_control_request 的 IN_REVIEW 活动申请；现有值／状态比较不等于已实现这项新阻断。新增规则只能是 specified/internal，后续须用真实申请、提交、批准和并发场景验收。

## 2. 作废保留与默认展示分开

本轮用户原话（`user-confirmed`）：

> 保留，但我觉得不应该常规展示出来，而是可以通过某个按钮触发查看作废表单的视图，但这个按钮并不需要放在显眼的位置。然后我们打印的时候，应该也是需要过滤掉作废表单的，等做打印的时候再说吧

已确认的展示规则：DHR 常规视图默认隐藏作废表单，提供不显眼但可发现的入口查看作废表单；保留原实例、历史、作废原因、签署、关联与冻结证据。隐藏只影响呈现，不删除证据，不使必需记录缺失、作废影响或其他审核阻断消失，也不自动扩展为隐藏失败、未完成或已替代记录。

`inference` 工程解释：实时视图按当前状态，指定冻结版本按该版冻结状态识别“作废”。例如 DHR V1 冻结时表单仍有效、后来才作废，不因今天的状态把 V1 的原证据变成“当时已作废”或改写其成员。这是保留既有冻结语义，不是另定作废时间。

打印过滤已记录为用户明确提出、留待打印切片落实的方向。本轮不变更当前打印／ZIP 的实现或既有冻结导出契约；实时／新版打印与历史批准版输出如何标识、过滤及保留完整追溯，须在打印设计时一起闭环，不能从默认隐藏推导立即修改历史档案。按钮具体位置和名称也未在本轮定稿。

## 3. 冠骋：已汇总、审核中、审核结束后还能变更吗

本轮回到原始代码，补查了按钮计算之前的入口校验（`original-evidence`），不只依赖上轮调研文档。13 份文件快照及哈希见 [clarification-source-manifest.json](clarification-source-manifest.json)。

核心调用链：`record-change-container.vue:88` 使用 V1 `useEbrWikiFactory`；该工厂 `requestInstanceByMaterialNo:68` 调用 `canEnterChangeProcess`，返回 false 时不装载 DHR 目录。真实导入来自 `apaas_ebr/utils/instance-status/useInstanceStatus.ts`，不是名字相似的 SI 工具，也不是 V2 普通填报预览规则。

| DHR 状态 | 给定源码中的 DHR 变更入口 |
|---|---|
| 已完成／汇总中，尚未封存 | 此状态校验不拦截；仍需满足选中表单本身的变更／作废资格 |
| 汇总审核中 IN_AUDIT | `canEnterChangeProcess:182` 明确拒绝进入，因此不能从此页面发起其中表单的变更或作废 |
| 已汇总／审批通过 SUMMARIZED，尚未封存 | 入口校验不拦截，V1 按钮规则开放变更／作废，仍走单表申请审批；不能把审批结束等同于已封存 |
| 已封存 ARCHIVED | 状态工具没有在入口直接排除它，但 V1 工厂 `:225`／`:237` 返回关闭变更和作废的按钮权限；不证明存在解封存后重开的完整政策 |
| DHR 已作废 ABANDON | 状态工具明确拒绝进入 |

审批通过后进入 SUMMARIZED 的后端证据是 `crown-back/approve/handler/business/EdhrProcessHandler.java:42`；无审批直接汇总也会设此状态。因此表中“审批结束”特指批准完成，不代表所有可能的流程终止结果。

后端 `OnlineFormChangeBs:101`／`OnlineFormAbandonBs:79` 的显式提交检查面向表单自身；`SummaryApproveHisService:64` 创建审批，未见按父 DHR 状态补同等门禁。按流水号路径在 V1 `:83` 提前进入 doc 分支，不调用上述 DHR 入口校验；其平台查询接口源码不在给定套件中。因此上述结论是**该 DHR 页面路径的静态行为**，不能冒充服务端全入口强制保护，也未运行竞品接口验证。

另有 `SummaryEdhrRollBackBs:56` 的独立“回退”：仅接受 SUMMARIZED，原审批记录活动标记改为 false，DHR 回到 IN_SUMMARY；这证明有重新整理入口，不证明表单变更批准会自动调用它。变更结果处理器仅明确调用平台 `refreshInstStatusByOfInstId`，平台实现缺失，不能确认修改后旧批准是否失效、是否强制重审、通知谁。

**整份 DHR 作废是另一件事。** `edhr/biz/EdhrInstanceAbandonBs.java:59` 直接更新 DHR 的 ABANDON 状态和原因；`edhr/biz/AbandonEdhrBs.java:95` 则收集签名／原因后调用 `service/EdhrInstService.java:118`，后者先处理相关表单，再把 DHR 标为 ABANDON。这些已给业务方法的显式逻辑没有按 IN_AUDIT／SUMMARIZED 分支阻断；但其低代码菜单、权限及平台表单作废实现不完整，也未在这些方法中证实原 DHR 审批的终结或旧批准处置。因此只能确认另有整份作废路径，不能据此保证所有阶段都能完整安全作废，更不能把前表的单表入口限制当成整份作废的全域规则。

V2 `useEbrWikiFactoryV2.ts:460` 将 SUMMARIZED／IN_AUDIT／ARCHIVED 作为普通预览状态，与上述 V1 专用变更入口不同，不可混读。上轮只检查后段按钮显隐不足以回答本轮状态问题；本轮补上前置状态校验，保留上轮原始证据和质量记录，不追记为当时已检查。
