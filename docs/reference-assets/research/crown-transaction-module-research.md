# 冠骋事务模块调研

## 结论

冠骋的“事务”不是批次生产页面旁边的异常处理功能，而是跨生产、检验、放行和仓储等业务的运行编排层。它负责在正确的主体和工序上下文中选择事务定义、启动流程实例、管理当前节点、创建事务表单或子事务、执行配置动作，并把过程写入事务主线和主体关系，供 DHR 完整性检查与正反向追溯使用。

不良处置、报废、返工、批次转 SN 和拆分是事务可承载的业务场景，不是事务模块的完整边界。

本文记录的是竞品事实和内部研发建议，不代表 eDHR 当前已实现能力，也不构成客户承诺。

## 先区分两种“事务”

冠骋源码中的“事务”不能只理解为一张事务实例表：

1. **事务主线事件**：开工、完工、事务创建、事务完成、事务结束、删除等业务动作会产生 `TxnMainlineEntity` 记录。它是生产事件和追溯时间线的一部分，不一定对应一个需要用户处理的可配置流程实例。
2. **可配置事务流程实例**：`TxnDefinitionEntity` 定义流程，`TxnInstEntity` 保存运行中的批次/SN 事务实例，`TxnNodeStatusEntity` 保存当前节点。它可以启动表单、配置动作、子事务、分支和消息，并在完成后继续或结束流程。

两者的关系是：一个生产动作可以只写事务主线；一个可配置事务实例也会在创建、完成和结束时写事务主线。主线是追溯记录，实例是可执行运行对象，不能用其中一个替代另一个。

## 在冠骋产品中的位置

| 使用位置 | 事务如何体现 | 证据类型 |
| --- | --- | --- |
| 批次 / SN 生产工作台 | 工作台同时展示 SOP、待填表单、附录表单和“生产事务”；操作人员可从当前工序可用事务中发起处理。 | 探索资料；移动端 `run.vue`、`transaction-list.vue`、`txn-handler.ts` |

| 批次事务 / SN 事务列表 | 可手工新建、处理、查看、删除或结束事务实例，并关联事务定义、批次/SN 和工序。 | 探索资料；`TxnInstSubmitBs`、`TxnInstCloseBs` |
| 返工执行 | 返工本身既可以是事务流程中的配置结果，也会使用与生产工作台相同的 SOP、表单和事务面板。 | 探索资料；`ConfigNodeDelegate`、返工相关服务 |
| 检验执行 | 系统识别或创建检验事务；检验工作台可继续处理事务节点、填表或再触发子事务。 | 探索资料；`InspectionNodeDelegate`、`InspectionExecuteStartBs` |

## 完整模型

### 1. 定义与适用范围

`TxnDefinitionEntity` 保存事务的状态、范围、属性、业务流程定义、所属模块和标签。事务配置不是简单地把一个按钮绑定到一个工序：

- `TxnUsageRuleEntity` 可将事务限定到产品簇、产品版本、工序和生产/返工类型。
- 对某一范围可创建自定义流程；未自定义时继承事务定义的流程。
- `TxnExcludeEntity` 把全局事务从特定产品簇、产品或工序中排除。
- 查询可用事务时，冠骋会先取启用的定义，再按排除、适用范围和最新个性化流程筛选。
- 工序配置中的触发表定义 `事件 + 动作 + 值`。当前源码明确的事件是开工前、完工后、部分完工后，动作是“执行事务”或“抛出提示”。

因此，事务的适用性由“定义 + 适用规则 + 排除规则 + 工序事件配置”共同决定。

### 2. 实例与流程运行

可执行事务会创建 `TxnInstEntity`。该实例至少绑定事务定义、批次或 SN、父事务、工序节点、流程实例、当前表单、状态、产品、工单、生产类型、模块和事务号。`TxnNodeStatusEntity` 记录当前或历史节点，包括表单实例、配置组件、处理范围、子事务和节点状态。

流程运行引擎是业务流程引擎。参考资料明确列出下列节点，源码已对其中关键节点提供实现：

| 节点 | 行为 | 证据强度 |
| --- | --- | --- |
| 表单节点 | 创建带事务上下文的表单实例；表单完成后更新节点状态并唤醒流程继续执行。 | 源码确认 |
| 事务节点 | 创建子事务实例，可同步等待子事务完成或异步继续；保留父子关系与回调节点。 | 源码确认 |
| 配置节点 | 将当前任务暴露给配置组件处理。探索资料说明返工、批次转 SN/拆分由此类节点承载。 | 组件运行源码 + 探索资料 |
| 条件串行 / 条件并行 | 按条件选择首个匹配分支，或并行推进所有匹配分支。 | 探索资料；底层流程引擎结构可见，但未逐个复核前端设计器限制 |
| 消息通知 | 站内、企微、钉钉、飞书、邮箱等通知。 | 探索资料；存在 `MessageNodeDelegate` |
| 检验、放行、物料上/下料、入/出库、标签 | 由各领域节点或事务模块处理，并共享事务实例 / 主线。 | 源码确认存在领域节点或模块集成；具体业务参数待逐项功能调研时再定 |

事务实例结束时，冠骋会结束仍处于等待/运行的节点与表单，递归关闭子事务，并写入事务结束主线。流程自然结束时也会将实例更新为完成，并在同步嵌套场景唤醒父事务。

### 3. 表单、投影和 DHR 的关系

事务表单不是独立于生产的普通附件。表单节点创建的表单带有 `businessType = TXN`、事务实例、批次/SN、工序、产品、工单等上下文。表单最终完成后：

1. 事务节点状态更新为完成，流程继续；
2. 表单数据可投影为物料消耗、报工、报废、仓储等读模型；
3. 表单和事务状态成为 DHR 完整性检查的依据；
4. 事务创建、完成、结束会形成主线记录，支持追溯解释。

这也解释了为什么事务不能被实现为单纯的弹窗或备注：它是把“人填的证据”和“改变生产状态或关系的动作”串成可推进、可结束、可追溯的运行对象。

### 4. 主线与关系追溯

`TxnMainlineEntity` 记录工单、批次、SN 的开工/完工等生产事件，以及事务实例的创建、完成、结束事件。每条记录带主体、工序、产品、路线、表单实例、事务定义和事务号等上下文。

`TxnRefApi` 不是普通外键关系：它用 `txn_start_id_` 和 `txn_end_id_` 表示关系有效期，用 `txn_subject_id_` 和 `txn_tracking_id_` 表示主体与被追溯对象。关联、解除关联、拆分继承等操作都按事务号记录，因此可查询“某一时刻关系是什么”，而不是只得到当前关系。

## 已确认的关键运行路径

```text
事务定义 / 适用规则 / 例外 / 工序事件
                 |
                 v
当前批次或 SN 的工序工作台 ---- 人工点击 ----+
                 |                             |
工序开工前 / 完工后 / 部分完工后事件 ----------> 事务分派
                                                       |
                                                       v
                                      事务实例 + 节点状态 + 业务流程实例
                                                       |
                         +-----------------------------+-----------------------------+
                         |                             |                             |
                       表单节点                      配置节点                       子事务节点
                         |                             |                             |
                   完成表单并推进                 返工/拆分等                 同步等待或异步继续
                         +-----------------------------+-----------------------------+
                                                       |
                                                       v
                              事务创建 / 完成 / 结束主线 + 主体关系有效期追溯
                                                       |
                                                       v
                         生产读模型、DHR 候选 / 完整性检查、正反向追溯
```

## 对 eDHR 后续生产模块的影响

以下是 `inferred` 的研发建议，尚未成为 eDHR 产品规则。

1. **P0 不实现通用事务编排器，但不应把生产执行数据模型写死。** 工单、批次、工序事件和表单实例应保存执行快照、业务主体、工序、来源事件和幂等键；这样 P1 新增事务实例时不需要推翻生产主链。
2. **P1 建最小闭环而不是复制冠骋全部节点。** 可先支持事务定义、适用范围、手工触发或有限事件触发、表单节点、事务实例、结束/中止、主线记录和 DHR 完整性检查。返工、不良等具体业务应在规则确认后逐个接入。
3. **P2 再处理高耦合节点。** 条件并行、嵌套事务、拆分、库存/投料、检验、放行、标签和外部通知涉及跨模块状态、权限、库存和审计，必须在各自执行契约明确后实现。
4. **不把“工序开始前事务未完成则禁止开工”当作已验证竞品规律。** 参考 UI/探索资料出现该意图，但当前抽查的运行代码确认的是触发和提示，不足以证明存在统一阻断机制。后续若采用该能力，需要先确认产品规则、阻断语义和审计要求。
