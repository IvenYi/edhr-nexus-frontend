# RDO 版本治理与后续演进

## 目的

本文件定义 eDHR 版本型 RDO 的版本管理边界。除非后续经评审的设计明确替代，本规则适用于表单模板、批记录模板、工艺路线、产品配置、文档及后续新增的版本型 RDO。

MVP 和 1.0 有意保持精简的运行模型。后续版本可以增加受控升级能力，但必须保留具体版本的可追溯性，且不得静默修改已经生效的配置或生产记录。

## 冠骋制程配置参考结论

冠骋的制程配置能在同一父级下并行存在多个版本。它通过生产对象保存具体子版本，再创建运行快照来解决选择与追溯问题，而不是限制同类版本的有效时间窗不能重叠。

| 冠骋代码证据 | 可确认行为 | eDHR 采用的结论 |
| --- | --- | --- |
| `order/biz/MfgOrderSaveBs.java` | 新建工单读取 `sourceProcessId` 并通过 `rdoGetVersionById` 获取指定制程版本。 | 工单/生产对象必须选择并保存具体制程子版本。 |
| `order/method/ImportCheckMethod.java` | 工单导入时缺少 `source_process_id__ri_` 会报“制程必须指定版本”。 | 不允许仅引用制程父级；必须传入子版本。 |
| `order/biz/MfgOrderSplitContainerBs.java`、`MfgOrderSplitSNBs.java` | 拆分批次/SN 时写入 `sourceProcessId = baseId:versionId`，并带出路线、DHR 和放行模板引用。 | 批次/SN 继承工单选定的具体制程版本。 |
| `transaction/biz/ContainerWorkStartBs.java`、`SNWorkStartBs.java` | 开工时以 `sourceProcessId` 读取制程，并调用 `getOrCopyProductProcess` 创建运行使用的制程快照。 | 开工时冻结制程及其工艺路线、表单、文档等配置，保留可重建的执行证据。 |
| `product/method/GetProductProcessHistoryOfProduct.java` | 将路线、DHR、放行模板等 RDO 兑换为具体版本，并复制工序表单/文档/事务配置至 `PRODUCT_PROCESS_HISTORY`。 | 生产快照必须保存所有关键引用的具体版本与配置内容。 |

冠骋的 `EdhrAppService`、同步接口中仍有未传版本时查询 `default` 的兼容分支。eDHR 不采用该部分：本产品没有当前/默认版本，未来生产入口必须要求用户显式选择具体生效版本。

## MVP / 1.0 契约

### RDO 结构

- 一个 RDO 由一个父级主档和零到多个相互独立的子版本组成。
- 父级主档仅承担聚合和标识职责，不存在当前版本、默认版本，也不存在隐式的最新版本选择。
- 同一父级下的多个子版本可以同时生效，包括有效时间窗重叠的情况。
- 其他业务对象必须保存所引用的具体子版本 ID，不能依赖父级 ID 解析出某个选定版本。

### 运行状态与引用资格

- RDO 子版本对用户仅展示 `生效` 和 `失效` 两种状态。
- 状态按有效时间窗 `[effectiveFrom, effectiveTo)` 实时计算。只有当前时间不早于 `effectiveFrom`（如有）且早于 `effectiveTo`（如有）时，版本才是 `生效`。
- 尚未到生效时间和已经超过失效时间的版本均展示为 `失效`。这是 MVP/1.0 的两态展示约定，不代表数据被删除或失去历史。
- 新建引用只能选择当前 `生效` 的具体子版本，不能选择未生效或已失效版本。
- 来源版本变为 `失效` 后，既有引用、审计记录、DHR 证据和生产记录仍必须可查、可追溯。
- 旧的持久化生命周期值仅为兼容数据，不得覆盖基于时间窗的计算结果，也不得形成额外的用户可见 RDO 状态。

### 变更行为

- 新建 RDO 子版本不会修改已有的依赖配置、生产记录、DHR 记录或审计历史。
- 需要采用被引用对象的新版本时，用户必须新建或编辑依赖业务对象的一个新版本/草稿，并在其中显式替换具体引用。
- MVP/1.0 不实现自动升级、版本提升、默认版本切换或自动选择最新版本。

## 当前扩展点

下列组件是策略边界。后续生命周期变化必须在这些统一边界上演进，不能重新引入各页面独立的状态逻辑。

| 边界 | 当前职责 | 后续演进规则 |
| --- | --- | --- |
| `RdoVersionStatusResolver` | 按有效时间解析后端 `ACTIVE` / `EXPIRED`，并决定是否可引用。 | 如后续经批准需要增加机器状态，只能扩展此统一策略；不得推导默认/当前版本。 |
| `rdoVersionStatus.ts` | 将后端状态映射为统一的 RDO 标签和列表筛选项。 | 保持展示与后端策略一致；未来详情提示不得暗示系统会自动选中某个版本。 |
| 具体子版本外键 | 将依赖配置绑定到精确的被引用版本。 | 保持为不可变历史引用，并围绕它建立影响分析索引和查询。 |
| 审计事件和生产记录 | 记录操作与所使用的具体版本。 | 增加不可变的执行快照；升级时不得改写既有审计或执行历史。 |

## 后续受控升级能力

下列能力计划在 MVP/1.0 之后建设，不是当前功能。

### 依赖影响分析

用户应能够在停用、变更或替换某个具体 RDO 版本前，查看其被哪些对象引用。结果至少包含依赖对象标识、具体引用版本、生命周期状态，以及是否已产生生产记录。

### 复制升版

当用户需要采用新的被引用版本时，系统应以现有依赖配置为基础创建一个新草稿，并原样保留其原有具体引用。用户在草稿中显式替换所需引用，再按适用的审核/变更路径提交。

### 受控批量替换

面对大量更新，系统可以根据影响分析结果准备多个依赖草稿，必须提供可审阅的影响汇总并要求用户确认。它绝不能原地修改生效配置、历史生产记录、DHR 证据或审计事件。

### 执行时快照

生产执行前，系统应校验本次新使用的每个引用都处于生效状态。执行时应保存实际使用 RDO 的快照，至少包括版本 ID、父级/业务标识、版本号、有效时间窗，以及适用时的不可变内容/hash 引用。这样后续版本升级或失效不会影响 DHR 重建和追溯。

### 生产制程版本选择

工单、批次或 SN 的创建/拆分入口建设时，必须提供“制程配置版本”的显式选择器：仅展示与产品、生产模式、生产方式匹配且当前生效的具体版本，并将所选子版本 ID 保存到生产对象。开工时再基于该版本冻结工艺路线、批记录模板、工序表单和文档配置快照。不得依据有效时间、创建时间或版本号自动选出其中一个候选版本。

## 不可突破的约束

- 不自动升级已经生效的业务配置。
- 不隐式选择最新版本、当前版本或默认版本。
- RDO 变更后，不原地改写历史生产、DHR 或审计数据。
- 不允许新建对失效具体版本的引用。
- 未来任何受控替换都作用于显式的新依赖草稿，并且必须可审计。

## 待确认事项

- 若后续需要超出两种展示状态，必须先完成独立的产品和合规决策，明确迁移方案、引用资格、审计行为和 UI 语义后再实现。
