# 本体驱动的需求影响分析与扩展开发架构

## 1. 文档目的

本文说明业务知识本体在 eDHR 产品开发、项目二次开发和 Codex 协作交付中的定位，并回答四个问题：

1. 如何让 Codex 理解产品、系统和业务逻辑，而不是盲目搜索并修改散落代码；
2. 如何根据一项需求识别受影响的规则、数据、模块、接口、页面、审计和测试；
3. 如何选择配置、作业编排、标准动作、项目插件或产品内核开发；
4. 本体、规则运行引擎、作业编排器和确定性代码处理器如何分工。

本文描述的是研发与交付架构。Codex 是团队在产品外部使用的开发工具，不是 eDHR 产品内的 AI 工作台，也不参与生产运行时的临时决策。

## 2. 核心结论

用户提出的方向是正确的：本体建模不应只用于客户问答，也不应只保存抽象概念。它还应成为 Codex 理解 eDHR 的结构化系统地图，使 Codex 在收到需求后能够沿着业务语义和实现证据分析影响，再完成设计、评估、开发和验证。

需要补充的边界是：本体不会天然知道所有代码依赖。可靠的影响分析必须把业务知识与实现证据和模块责任边界建立可校验的引用。

> 本体不仅是客户知识库或运行时规则来源，也是 Codex 进行需求影响分析的结构化系统地图；但只有当本体概念和规则与实现证据、模块归属及测试证据建立明确链接时，这张地图才足够可靠。

目标不是消灭代码，也不是维护两套互不相干的业务逻辑，而是形成从业务语义到确定性执行的可追溯链路：

    业务概念与关系
      -> 业务规则、状态、事件和动作语义
      -> 规则或作业执行契约
      -> 明确归属的领域模块、标准动作或项目插件
      -> API、数据库、页面、审计和测试证据

结构化知识说明业务是什么、何时发生、为什么发生以及由谁负责；经过测试的代码说明如何可靠地产生业务副作用。两者通过执行契约和证据引用连接，而不是各自维护一套无法核对的真相。

## 3. Codex 需要理解的系统知识

为了让不同开发者使用不同 Codex 会话时仍能形成一致判断，知识基线至少覆盖：

| 知识类型 | 要回答的问题 | 示例 |
| --- | --- | --- |
| 领域概念 | 系统有哪些业务对象 | 产品、产品簇、制程版本、工序、DHR、检验、返工 |
| 业务关系 | 对象如何关联及数量约束 | 产品属于一个产品簇；制程版本绑定路线和 DHR 版本 |
| 生命周期 | 有哪些状态，如何计算和迁移 | 制程版本根据生效和失效时间计算状态 |
| 业务规则 | 什么事件下满足什么条件，产生什么结果 | 工序完工前必须完成指定表单 |
| 业务事件 | 哪些事实变化触发规则或作业 | 工序开工、完工、检验完成、批次创建 |
| 业务动作 | 系统可以确定性执行什么 | 创建表单实例、阻断完工、创建返工任务 |
| 执行契约 | 规则或作业如何调用动作 | 标识、输入输出、幂等、权限、异常、审计 |
| 模块归属 | 哪个领域模块拥有数据和行为 | 生产执行拥有工序状态，DHR 拥有记录实例 |
| 实现证据 | 结论落在哪些实现资产中 | 服务、API、数据表、迁移、页面、测试 |
| 投影边界 | 哪些内容可被谁读取 | 内部研发、客户问答、生产运行时的可见范围 |

面向客户的问答只读取已发布、已验证且允许客户查看的业务知识。内部规划、候选规则、代码归属和实现影响信息仅供研发与交付使用。

## 4. 可靠影响分析所需的链接

每个关键概念、规则、事件、动作和执行契约应尽量建立以下关联：

- ownerModule：拥有该业务事实和行为的领域模块；
- relatedConceptIds：关联的业务概念和关系；
- triggerEventIds：触发规则或作业的业务事件；
- actionContractIds：被调用的标准动作或项目插件契约；
- apiReferences：受影响的接口及请求响应契约；
- persistenceReferences：实体、数据表、索引和迁移；
- uiReferences：客户操作或查看该能力的页面入口；
- auditReferences：应产生的审计类型、字段和追溯关系；
- testReferences：单元、集成、端到端、视觉、迁移和审计测试；
- snapshotReferences：生产对象需要冻结的版本和执行依据；
- downstreamReferences：读取该事实的报表、问答投影或外部集成。

不是每个概念都必须机械填写所有字段，但生产执行、审计、权限、状态机和跨模块规则必须具备完整证据链。缺少链接时，Codex 应将其标记为影响分析盲区或待核实项，并继续通过源码、数据库和测试查证，不得把推断当作确定结论。

## 5. 需求到交付的影响分析流程

    用户提出业务需求
      -> 主 Codex 读取本体、规则、历史决策、开放问题、执行契约和实现证据
      -> 提取已确认事实、合理推断和真正未决问题
      -> 识别受影响的概念、关系、状态、事件、规则、动作和快照
      -> 沿证据引用定位领域模块、API、数据库、页面、审计和测试
      -> 生成 decisionPackage 与影响报告
      -> 选择最小且可维护的扩展路径
      -> 主 Codex 实现并完成基础测试
      -> 本体智能体同步结构化知识和实现证据
      -> 质量智能体独立验证业务、实现、审计和知识的一致性
      -> 发布版本化代码、配置、规则、作业或插件

decisionPackage 不需要用户手工填写。主 Codex 应从正常业务沟通中自动总结概念、约束、状态、事件、动作、验收场景和影响范围，只对真正存在歧义的产品决策向用户提问。

影响报告至少区分：直接影响、传递影响、潜在影响、不受影响，以及兼容与迁移影响。证据不足的路径必须标明不确定性。

## 6. 五类扩展路径

| 扩展路径 | 适用场景 | 典型产物 |
| --- | --- | --- |
| 配置 | 表单、模板、RDO 引用、参数、适用范围和简单条件 | 受控业务配置和版本 |
| 作业编排 | 多步骤、等待人工任务、条件分支、重试和跨步骤闭环 | 版本化作业定义 |
| 标准动作 | 多个项目复用的确定性领域能力 | 产品模块中的注册动作处理器 |
| 项目插件 | 单一客户专属动作、设备协议、算法或系统集成 | 独立版本化插件或连接器 |
| 产品内核开发 | 新标准领域对象、状态机或跨模块基础能力 | 领域模块、接口、迁移和完整测试 |

判断原则如下：调整已有业务事实或参数时优先配置；已有动作需要不同顺序、分支或等待时使用作业编排；缺少可复用的确定性动作时开发标准动作并注册；客户特有且不应进入标准产品时放入项目插件；引入新通用领域能力或改变核心不变量时修改产品内核。

作业编排不是所有定制的唯一入口。它只能编排已注册、受权限和审计约束的动作，不能直接执行任意 SQL、脚本或未注册 HTTP 请求。

## 7. 如何避免业务逻辑继续散落

### 7.1 建立明确的领域所有权

每项关键业务事实只能有一个权威所有者。例如，生产执行模块拥有工序运行状态，DHR 模块拥有表单实例和记录，审计模块拥有不可变审计事件。其他模块通过公开契约读取或请求动作，不复制状态计算。

### 7.2 统一业务事件入口

工序开工、完工、检验完成、返工创建等事件应由明确服务产生并进入统一事件契约。控制器、页面组件和监听器不能各自重新实现同一业务判断。

### 7.3 规则集中定义，动作集中注册

可结构化的条件、选择和阻断规则进入规则资产；有副作用的行为进入受控动作处理器。规则或作业只引用稳定动作标识，不复制处理器代码。

### 7.4 为项目定制保留稳定扩展点

项目专属能力通过插件 SDK、动作注册表、事件订阅、外部连接器和明确的数据访问边界接入。Codex 开发项目需求时应优先在这些扩展点工作，避免直接在标准控制器、公共监听器或多个页面中插入客户条件。

### 7.5 用自动化门禁检查架构漂移

后续可逐步增加以下检查：规则引用的动作必须存在执行契约和注册处理器；关键知识引用的文件、接口和测试路径必须存在；新增生产事件必须登记事件所有者和审计语义；项目插件不得跨越禁止访问的数据边界；运行时只读取已发布且版本匹配的资产；生产对象必须保存适用版本和执行快照。

## 8. 示例：装配完工后检验，不合格进入返工

需求：装配工序完成后必须检验；检验不合格时进入返工。

Codex 首先识别概念：工序、检验结果、生产批次、表单、作业和返工；关系：产品制程版本关联路线，路线包含工序，工序绑定 DHR 表单；事件：请求完工、检验完成、返工完成；规则：工序完工条件、必填表单完成检查、作业触发条件；动作：创建表单、阻断完工、创建人工任务、创建返工任务。

随后沿证据定位制程配置、生产执行、DHR、检验、返工、作业和审计模块，以及本体、规则、作业定义、动作契约、API、页面、测试和必要的迁移。

如果检验表单和返工动作已经存在，主要通过配置、规则和作业定义完成；如果返工动作缺失且只适用于一个客户，用项目插件实现；如果返工是多个客户都需要的标准能力，则开发标准领域模块或标准动作，再由作业编排调用。无论采用哪条路径，工序完工服务仍负责最终一致性和阻断，作业定义不能绕过领域不变量。

批次开始执行后冻结所用制程、规则和作业版本，后续升级不改变该批次的历史执行逻辑。

## 9. 本体与运行引擎不是两套互相矛盾的逻辑

可运行的结构化规则由规则引擎直接读取并确定性求值，例如是否允许完工、应选择哪个版本或是否触发作业。多步骤流程由作业运行时按已发布定义推进。具体副作用仍由代码处理器完成，例如写数据库、创建表单实例、扣减库存、调用设备或记录审计。

这不是维护两份同样的业务逻辑：本体和规则保存业务语义、条件、结果及动作引用；作业定义保存步骤、等待、分支和动作组合；动作处理器保存可靠执行副作用的工程实现；执行契约规定参数、结果、幂等、权限和审计；测试证明组合后的实际行为符合业务决策。

数据库事务、并发控制、设备协议、复杂算法或外部系统错误处理不应强行改写成自由格式本体规则。这些工程细节由领域模块或插件实现，但其业务用途、输入输出、调用者和影响范围必须登记到知识基线中。

## 10. 边界与保护措施

1. 本体不是自动完整的真相；没有实现证据的知识只能作为业务定义或候选推断。
2. 源码、数据库、API、调用链和测试仍需核对，不能仅凭旧知识修改系统。
3. 生成式 AI 不参与生产决策；生产只读取已发布、版本化规则和作业并调用已注册处理器。
4. planned、specified 或未验证能力只进入内部知识投影，不向客户暴露。
5. 运行时只读取具备实现、测试和执行契约证据的规则。
6. 工单、批次和 SN 保存版本引用及执行快照，升级不得改写历史语义。
7. 影响分析必须表达不确定性，Codex 不得静默补全关键业务规则。
8. 生产阻断、状态机、审计、权限、迁移和执行引擎按 L2 门禁完成本体核对和质量回归。

## 11. 分阶段落地建议

### 第一阶段：让 Codex 看懂现有系统

完善核心概念、关系、规则、事件和模块归属；为已有规则补充代码、接口、数据库、页面、审计和测试证据；把 decisionPackage 和影响报告作为需求开发的标准输入；收拢明显重复的状态计算和业务判断。

### 第二阶段：建立受控规则和动作目录

实现规则校验、版本、发布和运行投影；定义标准事件与动作执行契约；建立动作注册表、幂等、权限、异常和审计规范；为项目插件提供稳定 SDK 和边界。

### 第三阶段：完成最小作业编排垂直链路

支持表单、人工任务、条件、标准动作和项目插件节点；实现作业版本、实例状态、等待、重试和执行快照；打通一个真实生产场景的配置、发布、执行、审计和追溯。

### 第四阶段：增强自动影响分析和交付效率

自动检查知识引用、代码所有权和测试覆盖；根据 Git 差异提示需要更新的知识和证据；根据知识关系生成候选影响报告和回归测试范围；让不同团队成员的 Codex 会话通过同一仓库基线形成一致的业务决策和扩展方案。

阶段可以随真实生产需求交叉推进，但不能为了形式化建模阻塞 MVP。主智能体连续完成功能切片，本体智能体在规则稳定后并行沉淀，质量智能体只在收尾阶段独立验证。

## 12. 验收标准

架构逐步落地后，一项重要业务需求应满足：Codex 能识别相关概念、规则、事件、动作和历史决策；影响报告能定位主要模块、API、数据、页面、审计和测试；实现方式能归类为配置、作业编排、标准动作、项目插件或内核开发；新代码位于明确领域模块或扩展点；规则、作业和动作处理器具备可校验执行契约；客户问答只解释已发布能力；生产只使用发布版本和执行快照；本体、代码、测试和审计证据可相互追溯；无法确认的影响被明确列出。
