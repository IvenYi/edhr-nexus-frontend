# 电子表单追溯与统计：方案简版

供朋友评审 · 2026-10-05

**本分支交付首次最终完成的追溯投影闭环。**客户用普通字段建表，再配置来源，让已正式生效的数据进入追溯查询、报工、报废及消耗报表。批次/工单最终产出联动、受控修订／作废（A12）、长期记录本、复杂谱系、AI 和客户试用未覆盖；不代表正式生产发布。运行与实际验证见[开发说明](../development/form-traceability-projection-running.md)。

**最新MVP范围已确认：追溯支持可复用查找项目录，业务统计保持预设报表；客户自定义业务报表留到二期。**以下目录路径是待实现目标，不能当作当前页面已经支持；二期保留扩展空间，不提前搭建自由公式或任意跨表查询引擎。

## 1. 想解决什么问题

客户照常建立文本、数字、下拉选择等普通字段。需要查询或统计时，再告诉系统：**要查什么、数据在哪里。**

查找与追溯、业务统计是两个并列可选任务：一张表单可以只配置批次号、设备号、工序等字段供查找，完全不生成业务统计明细；也可以只做统计、两者都配或都不配。画布入口同时覆盖两项任务，查找不隐藏在统计的高级设置里。

例如输入物料批号找到字段记有该编号的相关记录和原表单；实际是否使用这批物料需有明确业务事实。按报废分类查看数量则属于业务统计。用户“所有相关的报表”的意图应保留，同时分清原始表单/证据与业务报表入口；结果页面和导航仍待设计，“所有相关”限已有权限。

统计模型和规则由我们预先做好。客户负责选字段、核对结果。没有查询或统计需求的表单，照常使用。

## 2. 客户实际怎么配置

2026-10-03已确认：直接在画布点选字段或子表是主要配置入口，集中入口留给熟练后的总览与调整；页面有主次并渐进展示。此前集中配置优先的建议已替代。2026-10-05已开始改造，当前普通字段和整子表均有侧栏入口；使用时快照继续保留，客户易用性尚待试用。

首期来源形态已进一步确认：**子表是配置体验重点，主表多个分散字段组成一条业务明细也同时覆盖**。子表优先不表示只做子表。建议子表按列配置后逐行配对；主表从当前字段发起具体业务用途，再引导补齐这笔明细的其他字段。两者具体交互仍待评审，内部数据对象不要求客户先行建模。

在当前实现中，画布选中字段或整个子表后，左侧“字段配置 → 查找与统计”可以配置：

1. **按需要勾选用途。**“用于查找与追溯”和“用于业务统计”并列；只查找时选该字段的查询含义，不要求数量或单位。无需配置的字段保持普通填报。
2. **选择来源。**子表配置一次列含义，各行共用；主表先选报工、报废或消耗等预设用途，说明当前字段含义，再补齐同一笔业务的其他来源。另一笔业务另配，只有可配对来源存在时才询问加入哪一笔。未完整配置可保存草稿，补齐后启用。当前v1子表仍需每行唯一字段，系统行身份尚待确认实现。
3. **核对并保存。**右上角“用途总览”集中核对来源；另一个“模拟预览”页签可填写多行模拟值，模拟值不保存。顶部“保存”统一保存侧栏和总览配置。生产实例使用这张表时，系统校验已启用用途并保存当时快照。

当前字段、整子表侧栏和全表总览修改同一份配置，支持撤销和多行模拟预览。互相定位及客户可维护查找目录仍待后续实现；当前查找项仍为产品固定目录，不能把新界面当成完整MVP目录链路。无需先把整张表归入某一种业务场景。实际验证和剩余差异见[交互改造记录](../development/form-projection-interaction-2026-10-05.md)。

配置通常在建模板或改版时完成；模板仍可按原方式编辑，已启动实例继续使用其创建时保存的配置。现场人员填表时，继续填写原来的字段。

部分字段应可配置从生产上下文自动带入。建议画布点选字段后分别设置取值来源与数据用途；带入是取值来源，不是第三种报表用途。同一字段语义兼容时可带入并用于检索/统计。系统统计归属来自实际执行上下文，字段显示和用户修改不能替代它；未配检索用途也不影响统计归属。带入时机、原始证据持久化、缺上下文、刷新/编辑与多设备选择仍待定。

## 3. 用一个例子讲清楚

假设表单确实记录了：**生产批次 P 使用物料 M 的批次 L，实际用量 10 件。**这些编号已对应到正确的业务对象，以下数值仅用于演示。

| 系统需要的信息 | 客户选择的来源 |
| --- | --- |
| 生产批次 | 当前生产任务 |
| 使用物料、物料批号 | 表中的“物料名称”“物料批号” |
| 实际用量、单位 | 表中的“使用数量”“单位” |

填报完成后，有流程的表单还需等流程最终结束，系统按最终值生成一条消耗记录。之后可以：

- 在**消耗报表**查看这 10 件及来源表单。
- 在**批次追溯**查看 P 使用了哪个物料批次。
- 在**表单追溯**按 L 找到这份表单。

这些入口查看的是同一条事实，数量仍然只计算一次。表单已由生产执行和作业关联到 DHR 时，也能沿这条实际关系回查。DHR 可以持续收录执行证据；相同批号文字不会自动建立 DHR 归属。

如果表上只有批号、没有用量，可以配置按批号找表，不能凭空生成消耗数量。只有文字编号时，也要区分“查到这个词”和“确认使用了这个业务对象”。

只配置设备号查找的表单，应在已明确的索引生效范围和权限内被找到，并显示准确实例和字段位置，不产生报工/报废/消耗统计明细。同字符串不同类型不混查，命中不自动证明设备使用关系或工序身份。当前`formTrace`仍沿最终完成链路；独立索引是否覆盖进行中记录及更新时机另待确认，不能从统计完成时机推定。上述均为验收期望。

另一个验收期望：批次B001、工序P10启动表单，统计事实归属由真实执行上下文确定，所配置的自动带入字段可以显示对应信息；不依赖额外手填批次/工序字段或配置检索用途。具体自动带入交互和生命周期仍待定。

批次最终产出按配置为最终产出的工序正式报工数量确定，工单汇总所属批次；不能把几道工序相加。报工来源字段要表达约定的产出含义，不强制取名或映射为良品数量。不良和报废按各自用途单独统计，不自动加减最终产出，也不需要额外的质量表单才能计算产出。没有采集或没有正式生效数据不代表实际数量为零；质量比率、对账和倒扣属于另行确认的需求。当前分支还没有批次/工单产出联动。

## 4. 新增客户需求时，怎样少维护

例如，报废记录已经有“报废分类”，查询和统计就共用这个含义，不再增加一种“追溯报废分类”字段类型。

2026-10-05已确认将可复用的“查找项目录”纳入MVP，配置和使用分为三步：

1. 管理员定义查找项，例如“灭菌锅次”，类型限产品支持范围；常用项由产品预置。
2. 制表人员选中普通字段或子表列，关联该查找项。不同名称、不同表单的字段可关联同一项。
3. 查询人员在追溯页面输入锅次，查看有权限的来源表单和命中位置。

定义的是查询含义，具体查询值在查询时输入。仅用于查找时无需补齐数量或单位；命中不自动建立正式实体关系。支持类型、操作符、目录生命周期、多条件匹配及历史补索引仍需设计，独立索引时机/状态范围和结果页面继续按Q15/Q16确认。

业务统计仍由我们提供模型及统计属性，客户关联来源并查看预设报表；新查找项不能自动变成所有指标的分组项。自定义业务报表排二期，具体指标组合、布局、权限及开放范围另行设计；保留扩展空间，不要求MVP先建设报表编辑器。

这种扩展针对显示、筛选、分组。新的业务动作仍按新需求开发。

新增业务用途允许二次开发，目标是开发成本低、容易维护；不要求全业务零代码，不提前建设庞大通用规则引擎。建议共用配置和投影基础流程，由各用途独立实现业务语义，新增普通用途主要补定义、业务代码和测试。用途按业务事实定义，新报表优先复用已有事实；这项具体分工仍是建议。

用户认可不同表单提供指标、汇总到同一报表行的方向，需明确统计对象、范围和来源。例如同一范围表A良品90、表B不良5可以并列回查，不自动扣产出或计算良率；B无正式数据时不填0，A仍可展示。这是期望行为，尚非已实现声明。建议各来源先按目标粒度聚合再合并，避免多对多放大；同次事件的跨表单关联方式仍待定。

AI 可以作为后续助手，先提出字段对应关系供人核对；人工配置始终可用，首期无需依赖 AI。

竞品源码和产品可用于对照目标与能力，不照搬其交互。我们设计自己的低学习成本画布配置及易维护二开方式；本轮未验证竞品产品UI，不把用户交互评价或历史记录升级为本轮原始UI证据。

## 5. 安速康的真实表单能否适用

已核对的样本说明，需要支持几种不同情况：

| 表单情况 | 方案如何处理 |
| --- | --- |
| 清洁记录有酒精批号，没有用量 | 支持按批号找表；不生成酒精消耗数量 |
| 组件记录横向摆放多组物料、批号、数量 | 每组一起配置，预览检查对应关系 |
| 多道环节重复填写合格、不合格数 | 先确认哪一处用于正式报工，避免重复相加 |
| 复核记录没有统计需求 | 只保留表单及真实业务归属 |

样本支持这个方向，但还没有证明全部表单都已覆盖。报废单统计哪个阶段的数量、不良总数能否按原因拆分、长期记录本何时生效，都需要先确认口径。

**首期建议先打通表单查询、报工、报废、消耗，以及必要的批次和既有 DHR 关联。**不良原因统计在数量口径明确后接入。灭菌、检验、放行的完整过程追溯，以及长期记录本，还需要各自业务模块配合。

## 6. 怎样落地，怎样判断真的好用

先用代表性表单跑通“配置 → 填报完成 → 报表查询 → 回看原表”，再请没有参与设计的客户制表人员独立配置和修改。

重点观察：能否理解每项用途、能否选对来源、能否发现错配，以及需要多少次求助。多行、多列和重复数量的表单也要参与试用。

**目前能确认的是设计方向；低学习成本需要实际试用证明。**评审时最值得讨论的是：这样的配置过程是否容易理解，以及还有哪些真实表单难以表达。

配置项现在按查表、正式业务明细和必要时的分组逐步出现；这个顺序来自开发者试用反馈，尚未用客户使用频率数据验证。
