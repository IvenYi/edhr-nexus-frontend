# eDHR 业务知识本体模型

## 目标

将 eDHR 中散落在前后端代码、数据库字段、页面说明和业务文档中的业务知识，整理为结构化、可查询、可解释的业务知识模型。该模型服务于两类场景：

1. 研发和实施人员查看业务关系、规则、来源和影响范围。
2. 客户通过问答页面理解当前产品已经发布的业务逻辑。

内部规划、待开发能力和技术路线只属于研发知识库，不进入客户知识视图。

本模型不是让客户在运行环境中自由修改业务规则的后台，也不把大模型作为生产执行引擎。

## 核心判断

“本体建模”这个方向是准确的，但实际落地应采用四层模型：

```text
概念本体：有哪些对象和关系
业务事实：当前租户有哪些真实对象和配置
业务规则：什么事件下什么条件成立、产生什么结果
执行适配：如何调用确定性的生产服务完成动作
```

本体回答“是什么”，规则回答“何时允许或阻断”，执行适配负责“怎么可靠地做”。四层不能混成一张自由格式的图。

## 维护方式

前期不提供用户修改本体和规则的页面。它们属于产品研发资产，由产品升级、标准功能开发或客户二开维护，进入代码评审和发布流程。

运行环境只读取随产品版本发布的知识模型。数据库可以保存编译后的查询投影，但不能成为一套脱离代码版本、由用户随意编辑的第二套真相。

每次产品发布生成一个知识模型版本，例如：

```text
eDHR 0.3
  ontologyVersion: 0.3
  ruleSetVersion: 0.3
  executionContractVersion: 0.3
```

生产批次仍然保存使用的产品制程版本、规则集版本和执行快照。这不是为了支持客户编辑，而是为了让产品升级后仍能解释历史业务为什么这样流转。

## 智能体协作

`docs/knowledge/` 是机器可读的业务知识权威基线，本文是便于人员阅读的架构投影。两者不一致时，必须核对已确认的业务决策和实现证据并修正偏差，不能让人员阅读文档静默覆盖结构化基线。

用户只负责确认产品决策和真正的业务歧义，不负责填写 YAML、证据索引或智能体交接表。主智能体在正常业务沟通中自动提取已确认结论，区分推断和未决问题，并生成符合 `docs/agents/agent-handoff-contract.md` 的决策包。

主智能体还应在同一决策包中按 L1 或 L2 风险维护需求影响分析和扩展路径选择。本体作为结构化系统地图帮助定位业务关系和实现证据，但影响分析不是自动完整依赖图，也不是新增独立审批流程。L1 只保留精简摘要，L2 才完整分析传递影响、兼容迁移、快照、审计和权限；同一功能切片连续调试时增量更新一次，不得重复建模或阻塞无依赖编码。具体效率边界以 `AGENTS.md` 为准。

长期协作职责如下：

- 主智能体负责业务沟通、业务实现和基础测试。
- 业务知识本体建模智能体依据已确认决策维护 `docs/knowledge/`，核对概念、关系、规则、决策、证据和执行契约的一致性，但不修改业务运行代码。
- 质量验证智能体独立审查需求、知识模型、实现和证据，并按风险执行 CRUD、接口、端到端、视觉、审计、迁移和回归验证；默认只报告问题，不参与修复。

业务语义发生变化时必须完成本体门禁；代码、数据库、接口、交互或客户可见行为发生变化时必须完成质量门禁。适用门禁的结果满足 `AGENTS.md` 定义的完成不变量后，任务才能宣告完成。角色通过每项任务按需实例化，长期上下文由 Git 版本化的知识资产和角色契约保持，而不是依赖某个永不结束的对话。

## 核心概念

| 概念 | 类型 | 说明 |
|------|------|------|
| 物料 | 业务事实 | 产品管理的来源；类型为产品或半成品时派生为产品 |
| 产品 | 业务概念 | 物料管理派生出的生产对象，不独立维护主数据 |
| 产品制程版本 | 业务配置 | 产品下可并行存在的具体制程配置 |
| 工艺路线版本 | 业务事实 | 产品制程版本选择的路线 |
| 工序 | 业务概念 | 工艺路线中的执行节点 |
| DHR 模板版本 | 业务事实 | 产品制程绑定的 DHR 目录定义 |
| DHR 目录项 | 业务概念 | DHR 下可被工序绑定的表单目录项 |
| 表单模板版本 | 业务事实 | DHR 目录项实际引用的受控表单版本 |
| SOP 文档版本 | 业务事实 | 工序执行时需要查看的指导文件 |
| 工序绑定 | 配置事实 | 工序与表单、SOP 和规则的关系 |
| 生产批次/SN | 运行事实 | 执行具体产品制程版本的业务主体 |
| 执行快照 | 运行事实 | 开工时冻结的路线、表单、SOP 和规则引用 |

## 关系模型

```text
物料 --派生为--> 产品
产品 --拥有多个并行版本--> 产品制程版本
产品制程版本 --绑定--> 工艺路线版本
产品制程版本 --绑定--> DHR 模板版本
工艺路线版本 --包含--> 工序
工序 --引用--> DHR 目录项
DHR 目录项 --指向--> 表单模板版本
工序 --引用多个--> SOP 文档版本
产品制程版本 --被显式选择于--> 工单/批次
批次 --冻结为--> 执行快照
```

关键关系必须有来源、版本、适用范围和证据，不只保存两个 ID。问答需要知道“这个表单为什么出现在这个工序”，所以需要沿着 `制程版本 -> DHR版本 -> 目录项 -> 表单版本 -> 工序绑定` 追溯。

### 当前产品制程配置投影

产品管理首版不另建一份用于展示的“知识图”数据。它直接把上述关系保存为可追溯的业务事实，后续知识探索和问答读取同一份关系投影：

| 知识关系 | 当前业务事实 | 关键引用 |
|----------|--------------|----------|
| 产品拥有制程版本 | `ProductProcess` -> `ProductProcessVersion` | `productVersionId` |
| 制程版本绑定路线和 DHR | `ProductProcessVersion` | `routeVersionId`、`dhrTemplateVersionId` |
| 工序属于路线版本且被配置 | `ProductProcessOperationBinding` | `routeNodeKey`、`productProcessVersionId` |
| 工序引用 DHR 中的表单 | `ProductProcessOperationFormBinding` | `dhrTemplateItemId`、`formTemplateVersionId` |
| 工序引用 SOP | `ProductProcessOperationDocumentBinding` | `documentVersionId` |

因此“产品 A 的制程 V2.0 为什么在装配工序显示某张表单”可以确定性地查到：产品制程版本选择的 DHR 版本、该 DHR 目录项、目录项指向的表单版本，以及装配节点的绑定记录。产品管理界面只负责维护这些关系；未来的知识探索、问答和生产执行快照都必须从这些事实读取，而不是解析页面文案或另存一套关系。

## 规则模型

规则采用结构化事件、条件、结果，而不是只保存一段自然语言：

```yaml
id: operation.complete.required-form
name: 工序完工前检查必填表单
status: implemented
trigger: operation.complete
scope: process-version
condition:
  - operation.formBinding.requiredBeforeComplete == true
  - formInstance.status != completed
result:
  type: block
  reason: required-form-not-completed
explanation:
  template: 工序完工前必须完成表单 {form.name}
```

规则的 `status` 决定它进入哪一种读取投影，而不是决定它是否存在。内部知识投影可以读取全部状态，便于研发维护“已实现什么、未来计划什么”；客户知识投影和运行时投影只读取当前产品发布版本中已经 `verified`、具备执行契约的规则。`planned`、`specified` 和 `unverified` 只能在内部知识库中查询，不向客户问答暴露。

建议状态：

| 状态 | 问答可见 | 运行时可执行 | 说明 |
|------|----------|--------------|------|
| planned | 仅内部 | 否 | 已识别、尚未设计完成 |
| specified | 仅内部 | 否 | 已完成业务定义，尚未实现 |
| implemented | 内部及待发布环境 | 需验证、发布后 | 已有代码和数据结构 |
| verified | 是 | 是 | 已通过场景测试并纳入可执行发布版本 |
| deprecated | 按权限 | 否 | 客户只在确有历史关联时看到必要说明 |

## 当前已确认能力与规划能力

| 能力 | 知识模型记录 | 当前是否进入执行 |
|------|--------------|------------------|
| 产品来源于产品/半成品物料 | implemented | 是 |
| 产品下多个制程版本并行 | implemented | 是 |
| 制程绑定工艺路线版本 | implemented | 是 |
| 工序引用 DHR 目录中的多个表单 | implemented（配置关系） | 产品管理可维护；运行期校验后续接入 |
| 工序引用多个 SOP | implemented（配置关系） | 产品管理可维护；运行期消费后续接入 |
| 表单结束前完成 | planned | 暂不执行，后续补充 |
| 表单共享 | planned | 暂不执行，后续补充 |
| 表单按钮和字段权限配置 | planned | 暂不执行，后续补充 |
| 工序事件触发事务 | planned | 暂不执行，后续补充 |
| 工序开始前事务校验 | planned | 暂不执行，后续补充 |
| 以当站工序作为最终产出 | planned | 暂不执行，后续补充 |
| 物料齐套校验 | planned | 仅记录，不做 UI 和运行逻辑 |

规划项必须有业务说明、前置依赖和验收场景，但不能出现在当前版本的客户页面、客户问答或可执行配置面板中。这样既不会丢失未来设计，也不会把尚未实现的能力误传给用户。功能完成后，开发者将它从内部知识投影推进到客户知识投影和可执行投影，并补充对应的执行适配器和测试。

## 运行架构

```text
产品制程选择
  -> 查询已发布知识模型和业务事实
  -> 校验产品、路线、DHR、表单和 SOP 关系
  -> 生成产品制程执行快照
  -> 生产服务按快照执行
  -> 规则引擎返回允许/阻断及解释
  -> 审计记录事件、规则版本和快照版本
```

一期不需要引入独立图数据库。建议使用现有关系型数据库保存业务事实和关系表，使用 JSONB 保存规则条件和解释模板，再生成一层面向问答的关系投影。只有当跨域关系查询明显超过关系表的可维护范围时，再评估图数据库。

## 产品布局

### 业务知识探索页

默认是只读的三栏工作台：

```text
左侧：业务域和概念树
中间：关系图 / 业务流程 / 规则链路
右侧：选中对象的属性、关系、规则、证据、影响范围
底部：可展开的来源和审计证据
```

顶部显示当前知识模型发布版本、环境和查询范围。节点显示名称、类型和状态标签。点击“工序”时，中间可以切换为业务流程视图，显示 DHR、表单、SOP 和待实现规则的关系。

### 业务问答页

这是客户可见页面，只使用客户知识投影。页面分为问题历史、回答区和证据区。每个回答必须附带：

- 使用的知识模型版本；
- 命中的规则 ID；
- 关系路径；
- 业务事实和源码/文档来源；
- 当前适用的产品和知识模型版本。

问答层可以使用大模型做意图识别和自然语言组织，但所有事实先通过结构化查询获得；没有证据时必须明确回答“当前产品知识库中未定义”，不能自行补全业务规则，也不能泄露内部规划信息。

### 内部知识维护页

这是研发、产品和实施人员使用的页面，可以查看规划项、依赖、实现状态、代码证据和待办，但不等同于客户问答页面。规划项可以高频调整，维护它不会改变客户当前看到的业务逻辑，也不会改变生产执行。

## 实施顺序

1. 固化核心概念、关系和能力状态，不开发用户编辑器。
2. 将当前产品管理、工艺路线、DHR 模板、表单模板和 SOP 的关系接入模型。
3. 用产品制程版本的“选择路线 -> 绑定 DHR 表单/SOP -> 生成执行快照”做第一个端到端试点。
4. 为已实现流程增加规则解释和证据查询。
5. 再逐项补充表单完工校验、表单共享、事务、最终产出和物料齐套校验。

这样未开发功能不会丢失，也不会提前进入生产逻辑；产品升级时只需要同时更新知识模型、执行契约和对应实现，并保留旧版本解释历史。
