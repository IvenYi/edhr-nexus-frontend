## 目标

将 eDHR 中散落在前后端代码、数据库字段、页面说明和业务文档中的业务知识，整理为结构化、可查询、可解释的业务知识模型。该模型服务于以下场景：

1. 研发和实施人员查看业务关系、规则、来源和影响范围。
2. 客户通过问答页面理解当前产品已经发布的业务逻辑。
3. 为可执行的通用业务规则层提供稳定的事实、关系和规则语义；各运行切片的可用性仍按实现、测试和执行契约逐项判定。

内部规划、待开发能力和技术路线只属于研发知识库，不进入客户知识视图。

## 核心判断

“本体建模”这个方向是准确的，但实际落地应采用四层模型：

```text
概念本体：有哪些对象和关系
业务事实：当前租户有哪些真实对象和配置
业务规则：什么事件下什么条件成立、产生什么结果
执行适配：如何调用确定性的生产服务完成动作
```

本体回答“是什么”，规则回答“何时允许或阻断”，执行适配负责“怎么可靠地做”。四层不能混成一张自由格式的图。

## 维护方式

前期不提供用户修改本体和规则的页面。它们属于产品研发资产，由产品升级、标准功能开发或客户二开维护，进入代码评审和发布流程。

运行环境只读取随产品版本发布的知识模型。数据库可以保存编译后的查询投影，但不能成为一套脱离代码版本、由用户随意编辑的第二套真相。

每次产品发布生成一个知识模型版本，例如：

```text
eDHR 0.3
  ontologyVersion: 0.3.6
  ruleSetVersion: 0.3.6
  executionContractVersion: 0.3.6
```

生产批次仍然保存使用的产品制程版本、规则集版本和执行快照。这不是为了支持客户编辑，而是为了让产品升级后仍能解释历史业务为什么这样流转。

## 智能体协作

`docs/knowledge/` 是机器可读的业务知识权威基线，本文是便于人员阅读的架构投影。两者不一致时，必须核对已确认的业务决策和实现证据并修正偏差，不能让人员阅读文档静默覆盖结构化基线。

已确认决策的当前术语、概念、关系、事实和规则应在同一功能切片内同步；部分替代须定位到声明及适用范围，保留旧决策其他内容和原始证据。代码用于证明实际行为，已确认决策用于确定规范含义，生产快照用于解释当时的执行依据；三者的差异需要明确记录。多人分支协作同时记录 Git 契约基线，合并验收核对双方知识增量，具体流程见 `AGENTS.md` 和统一交接契约。

用户只负责确认产品决策和真正的业务歧义，不负责填写 YAML、证据索引或智能体交接表。主智能体在正常业务沟通中自动提取已确认结论，区分推断和未决问题，并生成符合 `docs/agents/agent-handoff-contract.md` 的决策包。

当前 MVP 以功能开发为主，全项目累计选择 1–2 个代表性业务功能验证本体路径。普通功能继续必要知识同步，不例行输出试点评估或新计划；只有真实功能需要且已有证据不能覆盖的新关键路径，才在当前范围内低频引导。智能体在已授权范围连续实施，不逐步骤审批；超范围不自动扩张，必要业务修复与验收照常。具体复用、停止和验证边界见 `DEC-0076-02` 及下文试点节奏。

明确授权的全量存量审计涵盖固定目标提交下全部当前术语、概念、关系、事实和规则及支撑的决策、证据、实现锚点、执行契约、未决问题、验收场景和差异记录，没有 ID 的 Markdown 证据和说明按文件登记。按域分批不缩小覆盖范围；历史和废弃资产核对适用时点、来源与替代链，不强行改写当前含义或补造过去的契约读取与审计。盘点清单只说明覆盖分母，语义审查、修复闭环、运行验收分别保留逐项依据；未决与证据缺口不能计入一致通过。优先检查投影、表单绑定、执行快照、生产阻断和审计，分别明确表单原始记录、流程工作数据、业务投影、追溯关系、DHR 证据与审计历史的所有权和版本边界。未合入分支须按其提交及实际集成候选另行核对。

主智能体还应在同一决策包中按 L1 或 L2 风险维护需求影响分析和扩展路径选择。本体作为结构化系统地图帮助定位业务关系和实现证据，但影响分析不是自动完整依赖图，也不是新增独立审批流程。L1 只保留精简摘要，L2 才完整分析传递影响、兼容迁移、快照、审计和权限；同一功能切片连续调试时增量更新一次，不得重复建模或阻塞无依赖编码。具体效率边界以 `AGENTS.md` 为准。

长期协作职责如下：

- 主智能体负责业务沟通、业务实现和基础测试。
- 业务知识本体建模智能体依据已确认决策维护 `docs/knowledge/`，核对概念、关系、规则、决策、证据和执行契约的一致性，但不修改业务运行代码。
- 质量验证智能体独立审查需求、知识模型、实现和证据，并按风险执行 CRUD、接口、端到端、视觉、审计、迁移和回归验证；默认只报告问题，不参与修复。

业务语义发生变化时必须完成本体门禁；代码、数据库、接口、交互或客户可见行为发生变化时必须完成质量门禁。适用门禁的结果满足 `AGENTS.md` 定义的完成不变量后，任务才能宣告完成。角色通过每项任务按需实例化，长期上下文由 Git 版本化的知识资产和角色契约保持，而不是依赖某个永不结束的对话。

关键关系必须有来源、版本、适用范围和证据，不只保存两个 ID。问答需要知道“这个表单为什么出现在这个工序”，所以需要沿着 `制程版本 -> DHR版本 -> 目录项 -> 表单版本 -> 工序绑定` 追溯。

DHR 汇总采用完整证据范围与目录展示分离的模型（2026-09-25，DEC-0063/0068/0071/0072，specified/internal）。目录、作业、自定义实际实例及受控附件按生产对象持续自动归集，状态不控制可见性；普通整理和提交仍限生产正常完成，终止政策不变。未完成、失败、作废、替代及处置历史保留，COMPLETED 不等于检验合格；适用核查包含而不限于必填目录。作业/工序实例由执行上下文绑定生产对象，内容误填、自定义上下文误选与附件误关联分别核验。

### 生产作业模板配置投影

作业模板属于“生产 / 生产配置 / 作业模板”，而产品管理、产品簇和工艺路线仍属于数据主数据菜单。流程中心保留审批流程和流程实例。作业模板本体不引入父子业务版本；只有流程配置具有草稿、已发布和历史版本。新建作业模板首次进入流程配置时，前端临时显示含开始和结束边界节点的 V1 草稿，用户保存或发布后才落库；临时或首次持久化草稿默认不在开始和结束节点之间创建连线。同一模板只保留一个编辑中草稿；草稿画布可定义表单填写、消息通知、人工确认和条件分支节点及连线。条件节点使用有序 conditionBranches 和唯一 conditionDefaultBranch：每个条件分支独立保存结构化 AST、字段目录版本和字段显示快照，按数组顺序求值并命中第一个满足分支，否则走唯一默认分支；条件节点每个分支出口最多一条线，普通节点和开始节点最多一条出口，流程不支持并行节点。输入只接受 conditionBranches[].conditionRule 与 conditionDefaultBranch；config.conditionRule、分支 rule 以及固定 condition-true/condition-false 出口均不属于当前契约，旧结构不提供兼容读取或转换。上述配置和发布语义不代表运行时字段真实来源、条件求值、实例快照或节点推进已经实现。发布会冻结该版本并自动创建继承配置的下一草稿。若草稿被放弃，用户复制任一已发布流程时系统创建继承配置的下一号草稿，使后续变更无需手工新建版本。适用规则引用作业模板并在未来运行时解析其当前已发布流程版本，不能手工绑定草稿或历史流程；无当前已发布流程的作业仍在适用规则选择器展示，但不可选并提示“该作业尚未发布作业流程版本”。

```text
作业模板 --拥有零到多个--> 作业流程版本
作业模板 --拥有零到多个--> 作业适用规则
作业适用规则 --运行时解析--> 当前已发布流程版本
生产上下文 --按适用规则自动匹配--> 作业模板
作业实例 --冻结--> 作业模板 + 当前已发布流程版本 + 命中规则快照 + 流程配置快照
```

作业模板、流程版本和适用规则的新增、编辑和删除均需审计，并保留变更前后快照；对既有但没有审计事件的作业模板，迁移必须写入来源为 SYSTEM、操作者为“系统”、动作为 `BASELINE` 的历史基线事件。该事件仅建立迁移时的追溯起点，不得伪称为原始用户创建。已发布流程版本本身不可单独删除。作业模板删除只受适用规则引用阻断：存在任何适用规则时禁止删除；没有适用规则时，无论模板是否存在草稿、历史流程或当前已发布流程，都允许在同一事务中删除模板及其全部流程配置。该删除规则取代“存在已发布流程即禁止删除父模板”的历史语义。适用规则的优先级固定由 `ruleType` 派生：`EXCEPTION` 例外排除高于 `SCOPED` 指定范围，高于 `GLOBAL` 全局适用；用户不能输入、修改或选择优先级，客户页面不展示优先级。作业适用规则不存在用户可控的启用或停用状态，所有保存的 WORK 规则均为有效规则；共享实体字段保留不得改变审批流程绑定规则的既有语义。作业定义列表显示绑定规则数量，并在 hover 中展示规则及范围；点击整行按既有 RDO 规范打开详情与数据审计，流程配置、编辑和删除由操作栏承载。作业定义和作业适用规则是并列页签，流程配置不承载适用规则。作业适用规则查询仅按作业名称或编码、适用方式、产品簇、产品和工序投影与筛选，状态列和启用停用筛选不进入该投影，未限定的范围显示为“不限”。新增或编辑适用规则时，弹窗只允许选择有当前已发布流程的作业，并显示其当前已发布流程及只读预览入口；无当前已发布流程的作业仍展示但不可选，提示“该作业尚未发布作业流程版本”。弹窗根据作业、适用方式和范围实时生成规则摘要；草稿、历史流程与可编辑优先级均不进入该配置投影。生产执行根据上下文按适用规则匹配作业，不在产品或工序配置中手工引用。作业按当前产品簇和适用规则实时匹配，新匹配只对后续工序生效，已过站不补做。已创建实例即使未执行业务节点，仍保留原批次归属及原快照；转簇、失配和发布不移除或重置。当前OPERATION_START工程边界为PENDING查询候选、合法START事务重匹配并创建缺失实例，IN_PROGRESS/COMPLETED不补入，查询不落库。state.operations中的works代表已创建实例，snapshot中的计划单独不算实例；实例创建时冻结当前已发布图、命中规则和产品簇匹配事实。制程首次START冻结及DHR同事务建立上下文和目录快照的时点保持，不能将制程冻结解释成后续全部作业候选已固定。独立作业实例模型、条件事实与规则版本的完整执行契约及通用求值证据仍未闭环，不能由现有快照推定通用规则层已完成。

### 表单流程与绑定字段权限投影

表单流程模板不绑定具体表单，因此可以复用于多个表单。表单流程版本只保存流程节点、连线和可选的主体来源。字段权限按权限配置组治理：填报阶段一个权限组可包含多个填报主体，审批阶段每个审批节点本身就是一个权限组，节点内多个审批主体共享该组的默认权限和字段例外；不再按单个主体平铺配置。未配置填报主体/权限组时所有已认证用户可填报，未配置审批主体时所有已认证用户可审批。开放范围不通过展开全量用户实现，仍受认证、流程实例、节点和任务状态约束。流程设计页不配置具体字段，也不再使用流程字段、字段槽位或字段映射作为新配置入口。

表单流程的审批主体和填报权限主体使用同一个公共主体选择模型。第一版只支持系统中已有稳定主数据与成员关系的用户、部门和角色，不提供用户组、部门负责人或业务责任人空壳选项；当前 Role 在产品中承担“岗位角色”语义，不另拆岗位维度。部门主体默认覆盖本部门及下级，也可配置为仅本部门，展示和持久化都必须明确范围。部门和角色不在流程发布或业务启动时冻结人员名单：审批节点到达时按最新关系解析候选人，填报权限在用户访问时按最新关系判断。公共主体解析器及通用工作流多候选任务关系已实现：节点进入时创建一个逻辑任务并冻结候选人与来源，任一候选完成后关闭其他候选。

普通表单流程审批节点支持转办标准动作：流程配置可调整按钮的显示名称、样式和显隐；原因由系统固定必填，不配置审批意见必填或签名字段事件。当前规范按DEC-0081仅当前有处理权者可发起，目标统一为同租户有效且未锁定的其他用户，可在节点到达时冻结的原候选集合之外，且不得转给自己。转办只改变当前责任，不推进节点、不修改表单数据、不产生审批结果；原待办移除、仅目标出现待办，节点到达时的approvers候选ID、restrictedApprovers限制标记及执行冻结快照中的原节点主体配置保留，当前受让人另存，再次转办仍按同租户范围，退回重建时清除旧转办投影。普通表单不据此宣称已有逐用户主体命中来源或未解析主体原件。通用工作流另外保留含sources/unresolvedSubjects的原解析文本originSnapshot，并与当前责任分开，保持一个逻辑任务；两条路径均不重建历史缺失来源。普通表单继续复用生产执行事务、结构化历史和不可变审计；新政策的实际实现与独立验收须取本轮证据，不以原实现成熟度或旧测试证明。DHR不开放通用转办，其他字段权限、退回、外层同步及记录控制契约不因此整体闭环。

### 记录控制审批流程与标准按钮投影

本领域的现行中文产品动作名固定为“表单变更、表单作废、转办、重新分配、退回”。上下文明确时前两者可简称“变更、作废”；“更正、普通转办、管理重新分配”不再作为并列现行产品动作名。稳定英文枚举、Java 类型、数据库字段、接口字段和权限码保持兼容，不因中文显示术语调整而重命名。该边界不影响 CAPA 的“纠正措施”或普通语义中的请求拒绝。

记录控制审批流程独立于表单流程模板，仅服务于首切片的表单变更（CHANGE）和表单作废（OBSOLETE）申请确认后的审批路径。申请人在记录控制入口准备申请内容、完成申请人电子签名、显式选择匹配的已发布审批流程并点击确认时，业务语义上已经发起审批；系统创建流程实例、冻结流程定义和版本引用，并直接进入首个审批节点。开始节点只表示流程边界，不是用户任务，不产生待办，也不配置保存（SAVE）或提交（SUBMIT）按钮。公共流程阶段一已经实现类型匹配的当前已发布候选查询和显式版本启动 Java 端口：启动绕过绑定规则，按幂等键复用完全匹配请求或拒绝冲突，保存审计关联与流程快照摘要，越过开始节点并创建排除申请人的首审批任务。记录控制申请入口已经在事务中复核来源资格、当前修订和活动锁，生成申请人签名、启动公共流程并回写冻结引用；共享终端中登录账号与真实签署人不同时，内部返回和同签署人幂等重放不得误用外部详情授权阻断。

审批节点固定提供审批（APPROVE）、退回（RETURN）和转办（TRANSFER）。动作语义及显隐由系统固定，模板配置只允许调整审批按钮显示名称、样式和电子签名要求；审批、退回可配置审批意见必填，转办不提供审批意见必填配置。记录控制模板不配置发起填报权限、表单校验或具体签名字段绑定。普通表单流程的开始节点保存、提交规则不受本投影影响。当前模板配置和发布校验不代表申请入口、申请人签名校验、流程实例创建或首审批节点推进已经实现。

转办按钮是审批节点的标准动作呈现配置，不等于运行时已经执行转办。转办仍由审批任务运行时按授权候选范围和原因校验，只改变当前任务处理人并保留当前节点、流程路径和业务结果，同时写入流程日志及不可变审计；该运行时动作与流程按钮配置分别维护。

2026-10-29用户确认的`DEC-0091`关闭记录控制审批重新分配是否额外签名的未决选择：重新分配必须完成电子签名，缺少有效签名不得执行，已登录、专门权限或原因不能替代签名；原目标资格、原因、路径不变及审计约束继续适用。普通转办、申请撤回和DHR专属路径不由此扩展，现行按钮身份/凭证按`DEC-0074`核对。该次调研时只有specified/internal规则和知识同步，不代表当时重新分配运行时、DTO强制字段或验签已经交付；原未决内容和当时提交证据保留于`docs/knowledge/evidence/workflow-reassignment-signature-confirmed.md`。

2026-10-30后续实施授权见`DEC-0092`：既有流程实例入口显示为“流程日志”，保留实例身份、技术路由、查询、详情和日志能力；新增“流程干预”查询运行任务并执行必须电子签名的重新分配。转办从任务详情发起，记录控制仍限授权候选并排除申请人自审；申请人受限撤回从申请详情进入，只有本轮尚无批准或退回决定时才允许，流程域原子失效全部待办，记录控制域同步消费WITHDRAWN结果，来源当前有效修订不被修改。普通任务的DEC-0081租户内转办与保留原授权资格的重新分配分别解释。运行日志只读与不可变审计并存，实际签署人资格按DEC-0074保持；不扩大DHR通用干预、归档或禁止的流程动作。实际源码、主侧198项聚焦检查（含25项真实PG集成）、任务竞争及签名/业务回滚断言已集中核对，责任保持规则、只读日志及WITHDRAWN派生结果记为implemented/internal；活动申请普通日志读取仍限申请关联范围，专门干预权限承载管理查询。新干预签名通用列表和单条读写均受保护，旧运行实例/任务/日志CRUD写入关闭。该实现不回填上一段调研时点，不以工程测试代替独立质量、CSV或生产发布，知识0.3.25与P0阶段不自动提升。

阶段一共享类型已经声明审批、退回、转办、撤回、重新分配、结果事件和业务详情投影，受限撤回也具有独立 Java 端口；类型与端口本身不等于对应运行时完成。后续记录控制运行时已接通最终审批通过/退回的同步结果投递：公共流程只在终态生成确定性结果事件，记录控制审批动作在同一事务中幂等消费并落地业务结果，落地失败回滚最终审批动作；中间审批节点不改变申请状态。`RECORD_CONTROL_REQUEST` 签名是专用受控证据，通用签名列表在分页前排除，通用单条读取和创建、覆盖、更新、删除全部拒绝。活动申请详情仅申请人、当前候选或处理人及本人已处理任务相关人员可见，无关用户拒绝；已结束历史仍向当前租户认证用户开放。变更审批待办与已办使用记录控制专用数据库分页，在分页及计数前限定 CHANGE/OBSOLETE、任务状态和认证用户处理人/候选关系，前端不从通用任务页进行客户端过滤。本期不新增岗位、角色或模板级功能权限，但上述数据级隔离和签名不可变边界始终强制。转办、撤回、重新分配等能力仍按独立实现证据判断。显式启动沿用 `WorkflowActionLog` 记录流程开始，阶段一不新建 `WorkflowEventLog` 第二套运行日志表。2026-09-15 本地重建已验证 0080 迁移、三列、幂等唯一索引、6 个权限码及 ADMIN 关联；非管理员权限矩阵、唯一索引并发争用和不可变合规审计关联仍需发布级验证。

## 规则模型

规则采用结构化事件、条件、结果。以下仅展示条件 AST 片段；完整记录、事实 ID、成熟度和证据以 `docs/knowledge/schema.yaml` 及对应规则文件为准，不在架构文档另存一份可执行规则：

```yaml
condition:
  all:
    - fact: fact.catalog.formbinding-required
      operator: equals
      value: true
    - fact: fact.catalog.forminstance-status
      operator: not-equals
      value: completed
```

规则的 `status` 表示成熟度，`visibility` 指定可进入的读取投影。内部投影可以读取全部状态；客户和运行时投影同时检查成熟度、visibility、证据及执行契约。`planned`、`specified` 和 `implemented` 规则只能为 `internal`；`verified` 也不是自动对外或自动执行。具体约束由 `schema.yaml.projectionRules` 校验。

建议状态：

| 状态 | 问答可见 | 运行时可执行 | 说明 |
|------|----------|--------------|------|
| planned | 仅内部 | 否 | 已识别、尚未设计完成 |
| specified | 仅内部 | 否 | 已完成业务定义，尚未实现 |
| implemented | 仅内部 | 不进入知识运行投影 | 已有实现证据；不等于对应产品代码没有在运行 |
| verified | 按 visibility 和发布范围 | 按 visibility、执行契约及发布范围 | 具备所要求的验证证据，仍须通过投影约束 |
| deprecated | 按权限 | 否 | 客户只在确有历史关联时看到必要说明 |

```text
产品制程选择
  -> 查询已发布知识模型和业务事实

  -> 生成产品制程执行快照
```

这是客户可见页面，只使用客户知识投影。页面分为问题历史、回答区和证据区。每个回答必须附带：

## 实施顺序

1. **P0：语义落地与影响分析基础。** 建立稳定 ID、受控事实类型、操作符和右值语义、实现锚点及最小 provenance，扩展正式校验器，优先复用、补齐表单流程版本引用与作业流程表单填写节点绑定的已有试点。不要求所有数据库字段进入事实目录。
2. **P1：关系语义与可查询影响图。** 整体实现收敛以 P0 退出证据为前提，补充 domain/range 的意图、反向关系、查询投影、结构化实现索引和冲突检查；有证据的稳定切片可以提前准备。
3. **P2：知识发布与历史解释。** 当产品出现真实的版本回放、审计解释或跨版本运行需求时，增加发布 manifest、时间版本和历史查询能力。生产规则消费前所需的最小不可变版本与执行依据保障提前落实，不等待完整 P2。
4. **P3：标准互操作与受控推理。** 外部知识交换、跨产品复用、标准工具接入或复杂推理需求驱动整体建设，并保持现有业务事实为唯一来源。稳定 ID 到 IRI 的映射以及 JSON-LD/SHACL 小范围试点可按具体价值在 P0/P1 提前实施；只对有业务证据的顺序、单位、枚举和基数建模，不因增加格式而宣称阶段完成。
5. **通用规则层与领域切片并行交付。** 在事实语义稳定的范围逐项实现规则求值和执行适配，生产前闭环类型、操作符与自定义谓词、空值与异常语义、权限、事务、审计和适用的幂等/失败处理，并冻结规则集、事实目录、执行契约、配置版本及必要事实依据。RDF/OWL/SHACL 不能替代这些运行契约。

每次升级必须在 `decisionPackage.ontologyRoadmap` 中声明当前阶段、进入依据、退出条件、明确不做事项和暂缓的下一阶段；提前试点还须明确依赖缺口、所有权、回滚方式和验证范围。阶段状态没有退出证据时不得标记为 `verified`。格式映射、数据校验、知识查询和生产执行按各自证据验收，局部成果不自动扩大为整阶段完成。

当前提前试点政策由 `DEC-0076-01` 对 `DEC-0038-04` 作部分替代：旧声明保留首次 `0.3.16` P0 切片未引入标准工具的历史，不再用作所有后续 P0/P1 切片中标准映射或 SHACL 校验试点的全面禁令。`DEC-0038` 的其他约束及原始证据继续保留；历史 P0 质量门禁已经关闭，但其证据不能替代当前切片或全库语义审计。

### 由 AI 逐步引导的试点

本期试点按全项目当前 MVP 累计 1–2 个代表性业务功能管理，不按阶段、模块或会话重置。优先使用已有表单版本引用与绑定切片，只有证据匹配当前目标才计入；一个功能已覆盖目的即可停止新增，第二个只补不同关键能力。达到目的后持续复用，真实需求变化才重新判断必要性；不为凑数启动新试点，也不将已有语义证据当成通用执行通过。

仅对需要低频引导的选定功能，主智能体在同一决策包的 `ontologyRoadmap.pilotPlan` 中维护步骤与证据。以下类别用于区分验收目标，不要求本期每类都安排试点；同一业务功能可组合目标，但分别验收：

| 试点目标 | 进入依据 | 必须交付的证据 |
|---|---|---|
| 语义基础 | 规则与事实含义已确认，需要建立稳定引用和来源 | 类型、关系、规则、来源和适用测试可逐项核对，缺口有明确处置 |
| 关系查询 | 相关语义稳定，有真实关系路径和影响查询需求 | 查询路径、实现锚点、代表性结果和不确定范围可复核 |
| 历史解释 | 有真实版本并存、历史执行或回放需求 | 不可变版本与历史依据可定位，跨版本查询或解释经过适用验证 |
| 标准映射与校验 | 有具体交换、标准工具或数据约束需求，相关语义足够稳定 | ID 映射、适用约束、代表性正反例、导出/校验验证和回滚方式 |
| 通用规则执行 | 边界明确的规则集合和真实业务需求，运行契约可以闭环 | 真实事实读取、确定性求值、动作适配、执行依据和适用权限/事务/审计/失败场景的测试 |

引导依次说明功能目标与当前阶段、候选规则和影响范围、进入条件及缺口、最小实现步骤、每步实际验证和收尾结论。只完成语义或标准试点时不声称业务执行已接入；执行试点也不要求先引入 RDF/OWL/SHACL。阶段或交付范围变化时更新原计划，已有授权仍连续有效，真实未决问题只暂停依赖部分。

全量存量审计与具体试点是两个可追踪成果：审计建立每个资产在新契约和当前决策下的结论，试点验证选定路径能实际工作。试点数量不缩小审计范围，完整审计不阻塞无依赖功能；本轮契约和入口建设不代表这两个成果完成。正式审计建议在 PR #3 合并后按实际 `edhr-dev` 提交固定基线，并相对原 `db8d361` 清单映射增量；合并前可准备或只读核对，合并事件不自动启动后台审计。交接入口见 [试点引导及全量审计说明](../development/ontology-guided-audit.md)。

这样未开发功能不会丢失，也不会提前进入生产逻辑；产品升级时只需要同时更新知识模型、执行契约和对应实现，并保留旧版本解释历史。
