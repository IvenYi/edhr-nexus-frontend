# 表单变更与作废设计

日期：2026-09-11
最近校准：2026-09-15
状态：设计收敛稿
适用范围：eDHR 0-1 的表单变更、表单作废、审核入口和菜单。DHR 仅作为受影响对象和追溯入口，不另定义一套动作名称。

## 0. 统一术语

本文及后续产品、交接、界面和验收沟通统一使用以下动作名称：

| 标准用词 | 使用规则 |
| --- | --- |
| 表单变更 | 完整名称；上下文已明确时可简称“变更” |
| 表单作废 | 完整名称；上下文已明确时可简称“作废” |
| 转办 | 当前任务处理人将任务交给授权范围内的其他人员；不加“普通”前缀 |
| 重新分配 | 具备专门权限的管理人员重新指定当前任务处理人；不加“管理”前缀 |
| 退回 | 审批节点的退回动作，不以“拒绝”作为同义动作名 |

历史文件名、Java 类名、数据库字段、接口枚举和权限码中的 `correction`、`CHANGE`、`OBSOLETE`、`TRANSFER`、`RETURN` 属于稳定技术标识，可以继续保留，但不得直接作为中文产品用词。竞品原始材料中的原词仅用于忠实记录其产品，不构成本产品术语。

## 1. 结论

eDHR 不做冠骋那套“系统管理 → 表单变更、按流水号查单、三条入口共用一层审批、审核中把表单打成 IN_AUDIT、通过后原地改当前版本”。那套交互能跑，但对医疗器械生产记录不够清楚，也不够好用。

P0 只做两类受控动作：

- 表单变更：已完成记录需要改内容。申请人提交新修订，审核通过后新修订成为当前有效版本；旧修订只读保留，永不覆盖。
- 表单作废：这张记录整体无效。审核通过后当前有效修订作废，历史修订仍可追溯。作废不改字段值。

两条路径共用审核引擎，不共用业务对象、状态回滚和落地动作。菜单按质量工作台组织，不按对象类型复制页面。

## 2. 为什么不照搬冠骋

冠骋源码和探索资料能确认这些事实，但不能当成本产品目标：

- 变更按钮只出现在专用表单变更页，填报、详情、工作台默认看不到。
- 表单变更、DHR 变更、记录本变更共用 handler；变更和作废也共用审批叠加层。
- 提交时把表单打成 `IN_AUDIT`，通过后才改数据或作废。
- 表单变更生效方式是改当前版本、原值保留。
- 旧立即变更 / 立即作废仍在，未填报表单还能不走审批直接作废。
- 产品说有变更列表，前端页未钉死。
- 变更配置是低代码页，不在硬编码菜单里。

对医疗器械生产记录，这些会带来四个问题：

1. 入口藏在系统管理或按流水号查找，现场和质量人员不容易找到该改哪张记录。
2. 变更和作废语义不同，共用一层状态会把“审核中”和“已完成”搅在一起。
3. 原地改当前版本，检查时难证明旧值仍是当时有效记录。
4. 立即作废、必填表单前端补实例、封存隐藏按钮都是实现副作用，不能写成产品承诺。

## 3. 产品原则

1. 已完成记录不能直接编辑。允许的受控路径只有变更和作废。
2. 变更形成新修订，不覆盖旧修订。当前有效修订只有一个；历史修订只读。
3. 作废是记录级动作，不改字段。作废后当前修订失效，历史仍可查。
4. 变更和作废都是独立申请单，不是表单填报流上的一个按钮。
5. 审核中只锁定来源记录，不把来源记录改成审核中。来源记录继续显示原“已完成”状态，并带“变更审核中”或“作废审核中”标记；是否经过审核由完成方式和流程审计记录区分。
6. 退回不落地。变更退回后新修订作废，来源记录回到提交前有效修订；作废退回后记录保持原状态。
7. 未完成记录不走变更。填报中、已提交待审、已退回的表单继续走原填报/审核流。
8. 未填报或误创建的记录可以走作废，但不能走立即作废。P0 一律审批。
9. 放行前变更是 P0；放行后变更、签名失效、重新放行是 P1。
10. 记录本变更是 P1。P0 不复制第三套入口。
11. P0 不预绑定默认审核流程。提交变更或作废时，申请人必须从有权限且动作类型匹配的已发布流程版本中显式选择；提交后冻结该版本引用。
12. P0 支持顺序及并行审核，全部通过后汇合。这是审核引擎待开发能力，不改变作业流程单出口约束。不支持加签、跳过、强制跳转或流程终止。

## 4. 对象模型

新增独立申请对象，不把变更字段塞进 `FormInstance`。

```text
RecordCorrectionRequest
RecordVoidRequest
CorrectionRevision
ImpactAssessment
```

功能矩阵对象清单同步为：

```text
Record:
FormInstance, FormFieldValue, FormAuditTask,
RecordCorrectionRequest, RecordVoidRequest, CorrectionRevision, ChangeReviewTask
```

### 4.1 RecordCorrectionRequest

| 字段 | 说明 |
| --- | --- |
| id | 申请单 ID |
| requestNo | 变更单号 |
| sourceType | `FORM` 或 `DHR_EVIDENCE` |
| sourceRecordId | 来源表单实例或 DHR 证据项 |
| sourceRevisionId | 提交时的当前有效修订 |
| proposedRevisionId | 待审核的新修订 |
| dhrInstanceId | 影响的 DHR，可空 |
| batchId / workOrderId / productId | 业务上下文 |
| reasonCode | 受控原因：录入错误、数据补正、设备读数变更、检验结论变更等 |
| reasonText | 必填原因 |
| impactScope | 影响评估摘要 |
| status | 见状态机 |
| workflowInstanceId | 审核流程实例 |
| workflowDefinitionId / workflowVersionId | 提交时选择并冻结的流程定义和已发布版本 |
| submittedBy / submittedAt | 申请人、时间 |
| signatureIds | 申请人、审核人签名 |

### 4.2 RecordVoidRequest

字段与变更申请同级，但不包含 `proposedRevisionId`。作废只指向当前有效修订，落地动作是把来源记录和当前修订标为作废。

### 4.3 CorrectionRevision

| 字段 | 说明 |
| --- | --- |
| id | 修订 ID |
| formInstanceId | 所属表单实例 |
| revisionNo | 从 1 递增 |
| snapshotHash | 该修订完整数据哈希 |
| basedOnRevisionId | 基于哪一版修改 |
| status | `DRAFT` / `IN_REVIEW` / `EFFECTIVE` / `SUPERSEDED` / `VOIDED` |
| effectiveFrom / effectiveTo | 生效区间 |
| requestId | 产生该修订的变更申请 |

规则：

- 表单首次完成时生成 revision 1，状态 `EFFECTIVE`。
- 变更申请创建 revision N+1，提交后为 `IN_REVIEW`。
- 审核通过后，N+1 变为 `EFFECTIVE`，旧修订变为 `SUPERSEDED`，不删除、不覆盖。
- 作废通过后，当前有效修订变为 `VOIDED`；被替代的历史修订保持 `SUPERSEDED`。
- 任何查询默认展示当前有效修订；审计和详情可展开完整修订历史。

### 4.4 和现有状态机的关系

表单实例状态保持业务生命周期，不借用 `IN_AUDIT` 表达变更审核：

```text
打开 -> 已完成（未绑定表单流程，提交校验通过后直接完成）
打开 -> 已提交 -> 审核中 -> 已完成（已绑定表单流程，流程完成后完成）
已提交 -> 已退回 -> 打开
打开 / 已完成 -> 已作废（仅在作废申请审核通过后；已提交记录只有在未形成活动表单流程且属于误创建时才可按资格规则申请作废）
```

说明：

- 无流程表单提交成功后直接进入 `COMPLETED/已完成`，不创建表单流程实例或审核任务；有流程表单只有在流程完成后进入同一终态。
- 变更通过前后，来源表单的主状态都保持 `已完成`；变化由当前有效修订引用表达，不增加 `变更待处理` 或 `已变更` 主状态。完成方式（`WITHOUT_WORKFLOW` 或 `WORKFLOW_COMPLETED`）和流程审计记录用于区分是否经过审核。
- 申请单自己的状态不写进表单实例主状态。UI 上表单保持 `已完成`，旁边按活动申请显示 `变更审核中` 或 `作废审核中` 标记。
- DHR 实例主状态不变。DHR 证据项增加 `有效 / 已替代 / 已作废 / 待重汇总`。

变更申请状态：

```text
草稿 -> 已提交 -> 审核中 -> 已批准 -> 已应用
审核中 -> 已退回 -> 草稿
已提交 / 审核中 -> 已撤回（当前审核轮次尚无批准或退回决定）
```

作废申请状态：

```text
草稿 -> 已提交 -> 审核中 -> 已批准 -> 已作废
审核中 -> 已退回 -> 草稿
已提交 / 审核中 -> 已撤回（当前审核轮次尚无批准或退回决定）
```

放行后变更属于 P1 的独立受控路径，不向 DHR 主状态机增加临时变更状态。P0 若来源记录已进入已放行/已归档 DHR，只允许发起作废评估或阻断变更，并提示走放行后变更。

## 5. 谁可以发起，从哪里发起

### 5.1 角色

| 角色 | 发起变更 | 发起作废 | 审核 | 说明 |
| --- | --- | --- | --- | --- |
| 生产操作员 | 否 | 否 | 否 | 现场发现错填，提交给班组长或质量，不直接改已完成记录 |
| 生产主管 / 班组长 | 是，限本工序/本班组已完成表单 | 是，限误创建、未填报、明显错单 | 否 | 填写原因和拟变更内容 |
| QA 审核员 | 是 | 是 | 是 | 记录审核中发现的错误 |
| 质量工程师 | 是 | 是 | 按流程配置 | 评估对 DHR / 放行的影响 |
| 放行审核人 | 否 | 否 | 放行后变更才参与，P1 | P0 不在放行页直接改记录 |
| 质量负责人 | 是 | 是 | 是 | 高风险、放行后、影响放行结论时 |

P0 权限按角色 + 数据范围控制，不按“知道流水号就能改”。

### 5.2 入口

主入口放在记录所在上下文，不放在系统管理。

| 入口 | 动作 | P0 |
| --- | --- | --- |
| 表单详情 / 已完成只读页 | 发起变更、发起作废 | 是 |
| 表单列表 | 对已完成/可作废行发起 | 是 |
| DHR 目录项 | 对该证据对应的表单发起变更或作废 | 是 |
| DHR 详情 | 查看进行中的变更/作废和影响 | 是 |
| 工作台待办 | 只处理审核任务，不发起 | 是 |
| 表单变更菜单 | 查询、继续草稿、查看申请 | 是 |
| 表单作废菜单 | 查询、继续草稿、查看申请 | 是 |
| 按流水号全局查找 | 辅助定位，不是唯一入口 | 是，作为变更/作废页的查询能力 |

明确不做：

- 系统管理下的“表单变更”。
- 填报页把已完成表单重新变成可编辑。
- 未填报表单的立即作废按钮。
- 为表单、DHR、记录本复制三套几乎相同的发起页。

## 6. 菜单与信息架构

记录管理下只保留一个“记录控制”分组，不叫变更管理，也不按对象拆页。

```text
记录管理
  表单管理
    表单填报
    表单审核
    表单列表
  DHR 管理
    DHR 填报
    DHR 汇总
    DHR 审核
    DHR 列表
  记录控制
    表单变更
    表单作废
    变更与作废审核
  记录打印            P1
```

工作台继续放“我的待办”。变更审核、作废审核都出现在工作台待办，`变更与作废审核` 页是质量人员按申请单处理的队列，不是第二套待办系统。

前端模块同步为：

```text
record-center    表单填报、表单审核、表单列表、DHR填报、DHR列表
dhr-summary      DHR汇总、DHR审核、DHR详情
record-control   表单变更、表单作废、变更与作废审核
```

不再使用 `change-control   表单变更、DHR变更、变更审核、变更列表`。

流程中心只保留一类可复用的审核流程模板，分类为：

- 表单变更审核
- 表单作废审核

不单独做“变更配置”低代码页，也不做按表单、分类或默认规则预绑定。P0 在提交时展示申请人有权使用、动作类型匹配且状态为已发布的流程版本，由申请人显式选择一条；没有候选流程时阻断提交。提交成功后冻结流程定义和版本引用，后续发布新版本不得改变运行中的申请。

## 7. 页面设计

### 7.1 表单变更

页面不是空白查询页，而是申请工作台。

上半部分：定位来源记录。查询批次/工单、产品、表单名称、表单流水号、DHR 编号、当前状态。默认只出已完成且当前有效的表单；已完成包含无流程直接完成和流程审核完成两种来源。

下半部分：变更申请列表。列：变更单号、来源表单、批次、产品、原因、状态、当前修订、拟修订、申请人、提交时间、当前审核人。

行操作：

- 草稿：继续编辑、提交、删除草稿
- 审核中：查看；当前审核轮次尚无批准或退回决定时可撤回
- 已批准/已应用：查看、打开修订对比
- 已退回：继续修改并再提交

从列表或表单详情点“发起变更”后进入变更向导：

1. 确认来源记录、当前修订、是否已进入 DHR、是否已放行；已完成记录可以来自无流程直接完成或表单流程审核完成。
2. 填写原因分类和原因说明。
3. 在只读原文旁编辑拟变更内容，系统自动生成字段级前后对比。
4. 显示影响范围：关联 DHR、是否需重新汇总、是否影响已完成审核、是否阻断放行。
5. 选择一条有权限且类型为“表单变更审核”的已发布流程版本；无候选版本时不能提交。
6. 申请人签名，提交后冻结流程版本引用并生成变更申请和 `IN_REVIEW` 修订。

拟变更内容保存在新修订草稿中，不写回来源表单当前有效数据。

### 7.2 表单作废

结构同变更页，但没有拟修订编辑器。

向导：

1. 确认来源记录和当前状态。P0 允许已完成记录，以及未填报且没有活动表单流程的误创建记录；已完成包括无流程直接完成和流程审核完成。不允许已提交或审核中的活动表单、已作废记录、已在另一张作废/变更审核中的记录；活动表单作废待后续流程终止/受控取消能力定义后再开放。
2. 填写作废原因。必填表单还要说明替代方案：补开新实例、从 DHR 移除、暂不替代。
3. 显示影响：DHR 目录项将失效、完整性检查将出现缺项、若已放行则阻断并提示 P1 放行后路径。
4. 选择一条有权限且类型为“表单作废审核”的已发布流程版本；无候选版本时不能提交。
5. 申请人签名后提交并冻结流程版本引用。

P0 必填表单作废通过后，不由前端偷偷补新实例。系统在影响评估里生成“需补开表单”待办，由生产/质量按原制程补开。

### 7.3 变更与作废审核

一个审核队列，用类型筛选，不拆两个一级菜单。

页签：待我处理、我已处理、全部申请。

列表字段：申请单号、类型（变更/作废）、来源记录、批次、产品、原因、状态、提交人、提交时间、当前节点、是否影响 DHR、是否影响放行。

审核详情必须同时看到：

- 来源记录只读原文
- 变更时的新旧修订对比
- 作废时的影响评估
- 原因、签名、流程意见
- 关联 DHR / 放行状态

审核人动作：审批、退回、转办。通过后系统执行落地，不让审核人再手改表单。

流程相关动作另行区分：

- 申请人撤回：仅当前审核轮次尚无批准或退回决定时可用；撤回不是审核决定。
- 转办：当前任务处理人把任务转给授权候选范围内的其他人员，必须填写原因。
- 重新分配：具备专门权限的管理人员处理人员离岗、账号停用或任务卡死，必须填写原因；记录原处理人、目标处理人和管理操作身份。
- 转办和重新分配只改变当前任务处理人，不改变节点、流程路径或业务结果。
- P0 不提供流程终止、强制跳转、跳过节点、加签或管理员直接批准。

### 7.4 表单详情和 DHR 目录

已完成表单详情默认只读，顶部操作：

- 发起变更
- 发起作废
- 查看修订历史
- 查看进行中的申请

DHR 目录项对已完成证据显示同样动作。进行中的变更/作废在目录项上显示标记，审核完成前该证据不可当作已关闭项放行。

## 8. 主路径

### 8.1 放行前变更

```text
已完成表单
-> 从详情、列表或 DHR 目录发起变更
-> 创建新修订草稿，填写原因和拟变更内容
-> 系统生成前后对比和影响评估
-> 申请人选择一条类型匹配的已发布审核流程版本
-> 申请人签名提交
-> 来源记录保持已完成，标记变更审核中，锁定不可再发起另一张变更/作废
-> 审核人在工作台或审核页处理
-> 通过：新修订生效，旧修订被替代，投影按新修订重算或冲销后重投影
-> DHR 未审核：标记待重汇总；DHR 审核中：阻断放行并要求重新汇总
-> 退回：新修订作废，来源记录解除锁定，数据不变
-> 撤回：在当前审核轮次尚无决定时结束申请，新修订作废，来源记录解除锁定，数据不变
```

### 8.2 作废

```text
可作废且无活动表单流程的记录
-> 发起作废，填写原因和替代方案
-> 申请人选择一条类型匹配的已发布审核流程版本
-> 申请人签名提交
-> 来源记录标记作废审核中并锁定
-> 审核通过：记录和当前修订作废；已投影数据冲销；DHR 目录项失效；完整性检查记缺项
-> 如需替代，生成补开表单待办，不自动造实例
-> 退回：解除锁定，记录保持原状态
-> 撤回：在当前审核轮次尚无决定时结束申请，解除锁定，记录保持原状态，不产生作废结果
```

### 8.3 放行后变更

P1。已放行或已归档 DHR 下的记录不能走 P0 变更向导。页面提示：

- 该记录已进入已放行 DHR
- 需要质量负责人评估是否重新审核、签名失效、重新放行
- 请走放行后变更

## 9. 落地规则

审核通过后的系统动作必须可解释、可重放、可审计。

变更通过：

1. 新修订变为当前有效。
2. 旧修订保留完整快照、签名和哈希，状态改为被替代。
3. 原投影批次标记失效或生成冲销批次，再按新修订投影。
4. 主线追溯、关系边、统计读模型按投影批次重算，禁止无审计物理删除。
5. 未审核 DHR 标记待重汇总；已审核未放行 DHR 退回汇总中。
6. 已放行 DHR 不在 P0 自动解冻。

作废通过：

1. 表单实例变为已作废。
2. 当前有效修订变为作废。
3. 投影冲销，追溯默认隐藏失效链路，审计视图可看完整历史和作废原因。
4. DHR 目录项失效；完整性检查记必需证据缺失。
5. 不物理删除表单、投影、DHR 成员、签名或审计。

## 10. 审核流程选择与运行约束

P0 不做按表单、记录分类、产品风险或默认规则预绑定。流程中心提供两类审核流程模板：`表单变更审核` 和 `表单作废审核`。提交时的选择规则如下：

| 场景 | 候选流程与处理 |
| --- | --- |
| 放行前表单变更 | 只展示申请人有权限使用的“表单变更审核”已发布版本，由申请人显式选择 |
| 放行前表单作废 | 只展示申请人有权限使用的“表单作废审核”已发布版本，由申请人显式选择 |
| 没有类型匹配的已发布版本 | 阻断提交，并提示先发布对应类型的审核流程 |
| 草稿、历史或已停用版本 | 不进入候选列表，也不能通过接口提交引用 |
| 已放行 / 已归档 | P0 拒绝内容变更；作废只允许进入影响评估，不执行 P0 作废落地 |

提交后冻结 `workflowDefinitionId` 和 `workflowVersionId`，流程后续改版不影响运行中的申请。提交人不能自审。P0 支持顺序及并行审核；并行分支全部批准才汇合，任一退回则本轮退回、其余待办失效。撤回检查覆盖本轮所有分支的决定。审核人数量和角色由所选流程版本配置。

## 11. 流程日志、干预与审计

流程运行数据和合规审计必须分层，不能用一张可编辑日志表同时承担运行与审计责任：

| 对象 | 作用 | 关键内容 |
| --- | --- | --- |
| `WorkflowInstance` | 一次变更/作废审核运行 | 业务对象、冻结的流程版本、状态、开始/结束时间 |
| `WorkflowTask` | 当前及历史节点任务 | 节点、候选人、实际处理人、处理结果、意见、签名引用 |
| `WorkflowEventLog` | 供界面展示和运维排查的流程时间线 | 提交、到达节点、同意、退回、撤回、转办、重新分配、完成 |
| `AuditEvent` | 不可变合规证据 | 操作人、操作身份、原因、对象、前后值/引用、时间、来源和关联事件 |

P0 页面能力：

- 审核详情展示完整流程日志，不提供修改或删除入口。
- 申请人可在规则允许时撤回自己的申请。
- 当前任务处理人可转办；具备专门权限的管理员可重新分配当前任务。
- 所有撤回、转办和重新分配必须写入 `WorkflowEventLog` 与不可变 `AuditEvent`。
- 表单填报/审批流程同样复用该日志和任务模型，但 P0 不提供“终止流程”，避免无法定义表单终止后的业务结果。

P0 提供流程干预查询与重新分配；P1 扩展超时升级和补偿重试，不默认开放跳过、强制跳转或直接批准。

### 11.1 P0 运行页面与动作边界

流程中心提供审核流程模板、流程日志和流程干预三个页面。P0 流程干预页只查询运行实例和当前任务并执行重新分配；P1 扩展异常诊断、超时与补偿，不能因此把 P0 管理入口后置。转办位于任务详情，撤回位于申请详情。所有入口复用同一权限和任务状态校验。

变更撤回后拟修订作废，来源有效修订不变；作废撤回后来源记录保持原状态。撤回取消本轮待办，解除本申请的锁，不推进外层作业，不生成表单完成或作废结果。退回后再提交需重新检查来源版本、权限和流程可用性，创建新审核轮次与新拟修订，保留旧轮次及已作废拟修订。

转办和重新分配成功后旧处理人失去该任务的处理权，目标人员取得权限；不得绕过数据范围、人员有效性和申请人不能自审的约束。提交、决定、撤回与重新分配必须以任务/申请版本检查防止并发双重处理；业务落地和审计原子提交，投影事件使用幂等键。

### 11.2 开发前需补齐的边界

处于已提交或审核中的活动表单不能发起 P0 作废。因为 P0 不提供流程终止，作废审核通过后不能留下仍在运行的原表单流程；后续若开放该入口，必须先定义受控取消、待办失效、事件日志和审计语义。未填报且无活动流程、已完成记录的设计可独立推进。

本次仅为设计，不包含运行实现或迁移。表单差异渲染、审核并行、日志干预、修订落地、投影与 DHR 联动均需开发与验收；不可把本文当作已经上线的能力证明。

## 12. 和冠骋的差异，按设计取舍

| 点 | 冠骋 | eDHR |
| --- | --- | --- |
| 入口 | 系统管理表单变更，按流水号查 | 记录详情、列表、DHR 目录、记录控制菜单 |
| 对象页 | 表单/DHR/记录本三套发起页 | P0 一套变更、一套作废，用 sourceType 区分 |
| 审批层 | 共用 BUSINESS_APPROVE，提交时改 IN_AUDIT | 独立申请单，来源记录只加锁和标记 |
| 生效 | 改当前版本，原值保留 | 新修订生效，旧修订只读保留 |
| 作废 | 可与变更共用叠加层；未填报可立即作废 | 独立作废申请，P0 全部审批 |
| 必填作废后 | 前端可能补新实例 | 生成补开待办，不自动造单 |
| 变更列表 | 产品有、页未钉死 | 变更申请列表、作废申请列表就是记录 |
| 变更配置 | 低代码页，git 中无 JSON | P0 提交时显式选择类型匹配的已发布流程版本 |
| 放行后 | 规则含糊 | P0 阻断，P1 专做放行后变更 |

## 13. 非目标

- 不实现完整 QMS 变更控制、文件变更、工艺变更、供应商变更。
- 不实现记录本变更。
- 不实现放行后变更、签名失效、重新放行。
- 历史批注增强后置；字段标红与前后值对比属于 P0。记录控制向表单模块提供稳定 fieldId、明细行 ID/字段路径、变更类型、前后值及修订 ID，由表单模块定位渲染，不按显示名称匹配。
- 不把变更审批做成表单填报流节点。
- 不保留立即变更、立即作废。
- 不在系统管理下放表单变更。
- 不做审核流程预绑定、默认命中或自动代选。
- 不做流程终止、强制跳转、跳过节点、加签或管理员直接批准。

## 14. 开发验收场景

1. 已完成表单发起变更时，只能选择“表单变更审核”的已发布流程版本；未选择或无候选版本时不能提交。表单原填报流程是否存在，不改变变更审核流程的选择要求。
2. 变更提交后，来源表单仍为已完成并显示审核中标记；审核通过后新修订成为唯一当前有效修订，旧修订只读保留。
3. 作废提交后，来源表单保持原主状态并显示审核中标记；审核通过后才变为已作废，字段值和历史修订不被物理删除。
4. 当前审核轮次尚无批准或退回决定时，申请人可以撤回；有决定后撤回被拒绝且不改变任何业务结果。
5. 转办只能选择授权范围内人员；重新分配需要专门权限。两者都不改变流程节点和业务结果。
6. 变更/作废的提交、审核、退回、撤回、转办、重新分配和落地同时形成可读流程时间线与不可变审计事件。
7. 已发布流程版本后续发生改版时，运行中的变更/作废申请仍使用提交时冻结的版本。
